# 2.G-a — Phase 2 gate fixes, round A: undo by value, memory

Phase 2 gate performance fixes, and a cost estimate for a fidelity nit.

## Rob's direction (2026-10-05)

- **No limit, no background job** for undo by value: a beachball for a
  genuinely huge undo is acceptable. Fix obvious waste and record what is
  left. ADR-0014 decision 3 is unchanged; no new decision, no new refusal.
- **The dead reading kept per structural command** (about 10 MB of heap a
  save) **is acceptable**: not bounded. Suggested for the phase report: a
  line in decision 3's Cost on the heap per save.

## What changed

1. **Passes over many rows skip the row cache**
   (`Document::read_rows_uncached`, document/mod.rs). Through the cache,
   every row read paid an eviction (a linear scan of the 256 cached rows):
   sampling showed most of a column undo's time there, and the grid's rows
   were evicted. These now parse as a save does (`each_physical`): a
   column's cells (`cells_at`), a column delete's taken cells
   (`TakenCells`), a row delete's check when redone by value
   (`values_of`), and Duplicate Row's copies.
2. **A row delete redone by value checks a chunk at a time**
   (`Rows::values_in_chunks`, 4,096 rows), instead of holding every row
   twice, as `Value`s and as `String`s. It compares `&str`s, validating
   each field's text once (`check_row`). Same results: the same refused
   row and column, the same trailing-empty-cells rule (ADR-0012 dec. 4).
3. **Values put back move into the inserted rows** rather than being
   cloned (`InsertedRow::new`/`exactly` and `insert_new` take a `Vec`).
4. **A field put back by value keeps no copy of its text when its text is
   its bytes** (`RawField.text: Option<Arc<str>>`, decided by comparing
   them): most fields (unquoted, valid UTF-8, or ASCII in a single-byte
   encoding). One allocation fewer per field. Quoted fields, invalid bytes
   and other decodings keep their text; the bytes are always kept
   (ADR-0014 decision 8).
5. **Nit: a saved reading's index had twice the capacity it needed.** The
   save sized its starts for `rows` and `from_starts` pushed the end, which
   doubled the vector. Now `with_capacity(rows + 1)` (walk.rs), and
   `shrink_to_fit` in `RowIndex::from_starts` (a no-op when exact): 3.9 MB
   less heap per save of the reference file.
6. **Nit: the recovery journal drops an edit and its immediate undo**, and
   a redo straight after its undo (`EditHistory.record`). It used to keep
   the command (up to 64 MB of values) after the undo history let it go.
   Safe for recovery: replaying the pair changes nothing, and Recover
   changes keeps no redo history (`rebuild`). Only the last entry is taken
   out, and only by the same command (lineage, cell changes, and row,
   column or batch object by identity) going the other way; an undo whose
   edit was saved (trimmed by `savedThrough`) stays. **Not across a
   save's snapshot** (gate review fix): cell typing and undo/redo carry on
   during a save, and an entry at or before the snapshot of a save still
   running (or written but not yet trimmed, `saveWrote`) is in that file
   while its undo or redo isn't, so the pair stays until `savedThrough`
   trims the first. Without this, Recover lost the undo (or redo) made
   during the save. Tests: `testAnUndoDuringASaveOfItsEditStaysInTheJournal`,
   `testARedoDuringASaveOfItsUndoStaysInTheJournal`,
   `testAnUndoAfterASaveWroteButBeforeItTrimmedStays` (UndoTests).
   **UX change:** an edit
   and its undo no longer make a failure offer Recover Changes (nothing to
   recover); `testAFailureWithNoEditsOffersNoRecovery` now sets a cell back
   by hand instead.

## Measurements (reference file, M5 Pro, release)

**Probe** (scratch program, not committed; fresh process each): delete
rows 1..n (or column 1), save, undo, redo through `Document::apply`. Heap
is malloc's size in use, all zones.

| Case | Undo | Heap after undo | Redo | Peak RSS |
|---|---|---|---|---|
| 10k rows | 11.3 → 10 ms | 37 → 31 MB | 21 → 17 ms | 264 → 246 MB |
| 100k rows | 109 → 96 ms | 227 → 192 MB | 213 → 168 ms | 684 → 399 MB |
| 999,999 rows | 1.18 → 0.95 s | 2,129 → 1,794 MB | 2.46 → 1.74 s | 4.83 → 1.97 GB |
| 1 column | 716 → 222 ms | 227 → 192 MB | 1.25 s → 390 ms | 1.28 GB → 584 MB |

**Delete a row, save, 8 times, commands kept:** heap +10.2 MB per save
before (15.4 → 86.9 MB; 10.3 MB once dropped), +6.2 MB after (12.9 →
56.4 MB; 6.3 MB once dropped). The rest is the dead reading (4 MB index,
field counts, diagnostics, cache), which Rob accepted.

**Benchmark `undo_after_save/*`** (new, `leal-bench/benches/row_edits.rs`,
own function, no budget; warm, so faster than the probe's first undo).
Before: main at 5b5e534 with this bench file copied in.

`rows_10k` 9.40 → 8.20 ms; `rows_100k` 91.1 → 80.9 ms; `column` 608 →
260 ms.

**What remains (accepted):** undoing a 999,999-row delete after a save
takes about 1 s on the main thread and holds about 1.8 GB while the
command is in the history: about 136 bytes a field (a `Value`, an
`Arc<RawField>`, its own bytes), 12 fields a row. Going lower needs one
shared buffer per restored row with fields as spans into it, which changes
`Value` and all its readers: not cheap, so not done. The 1 GB file costs
about ten times as much.

## Fidelity estimate (not implemented; Rob's decision)

**The nit** (saving.rs `carry_over`, and a cell undo after a save): the
undo writes the cell's on-screen text, so invalid bytes come back as
U+FFFD and an unusually quoted field (`"abc"`, `"a""b"x`) is requoted.

- **Approach:** `CellChange.old` also keeps the old field as a `RawField`
  (2.4c's `put_back`), only when an unedited field's bytes differ from its
  text as a save would write it. `RowEdits.cells` holds a `Value` (text or
  raw) instead of `Arc<str>`; view and writer take `ViewCell::Raw` for
  edited cells as they do for inserted rows; `carry_over` uses `put_back`
  instead of `value()`. FFI: inline changes (≤ 256 cells) go to Swift as
  `ValueChange` strings and come back through `Command::from`, losing the
  bytes, so `ValueChange` needs an opaque `Arc` field (like `CellBatch`),
  or every command stays in Rust.
- **Memory:** about 0 for plain fields; about 100 bytes plus its bytes per
  field kept; at worst a paste or clear doubles its old values (up to
  `PASTE_BYTE_LIMIT`, 64 MB, more).
- **Effort and risk:** about 2–3 days with fidelity property tests
  (invalid bytes, odd quoting, across save → undo → save); about 10 files
  (edit/{command,overlay}.rs, document/{editing,view,saving,pasting,
  columns}.rs, saving/walk.rs, leal-ffi editing.rs and tests). Medium-high
  risk: edit store, writer and FFI shape. Cheaper alternative: record the
  invalid-bytes case as a decision in ADR-0012 decision 4.

## Rust notes

- **`Option<Arc<str>>`** (value.rs): an `Arc` is never null, so `None`
  costs no space. `text()` turns the stored bytes back into `&str` with
  `std::str::from_utf8`, which always succeeds because `read` stores
  `None` only when the bytes are valid text; `unwrap_or_default` avoids a
  panic path anyway.
- **Taking a `Vec` by value** (`InsertedRow::new(gap, values: Vec<Value>)`):
  the caller hands over ownership, so the row keeps the same heap block; a
  `&[Value]` forced a copy (`to_vec`). In `insert_new`, `.zip(values)`
  consumes the outer `Vec`, moving each row out.
- **Closures as callbacks** (`values_in_chunks`): `each: impl FnMut(…)`
  may change what it captures (`checked`, the rows done so far), and
  `read_error: impl Fn(ReadError) -> E` lets one function serve callers
  with different error types. `std::mem::take` hands a chunk over and
  leaves an empty `Vec`.
- **Dropping a snapshot before a change** (`duplicate_rows`):
  `edits.overlay()` is an `Arc` snapshot; the store changes the overlay in
  place with `Arc::make_mut`, which copies it if anyone else still holds
  it. So the snapshot is dropped first.
