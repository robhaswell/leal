# 2.0a Scrolling headroom

**The 3× rule now passes in this Mac's `just perf` run.** Main-thread work
per scroll frame on the reference file is p50 1.4–1.6 ms and p99 2.2–2.6 ms
in all six reference-file runs, against 2.8 ms. Rob's unlocked run had p50
2.7–3.6 ms and p99 5.8–7.0 ms. Late frames and footprint are no worse than
in Rob's run (they are lower). The drawing design is unchanged (ADR-0001
option B as built in 1.6), so no ADR is needed for what lands here.

**The margin is thin if the clock is low.** This run's main thread ran at
2.6–3.1 GHz; Rob's ran at 2.2–2.4 GHz. If CPU time scaled with the clock
alone, the worst p99 here (2.6 ms) would be about 3.1 ms at 2.4 GHz. That
is an estimate, not a measurement. Most of what is left is AppKit
rebuilding the visible layer on every scroll step. A prototype that removes
it (strips of rows that scrolling moves) halves the frame again, but it
changes the grid's drawing design, so it is proposed in
[ADR-0011](../adr/0011-grid-strips.md) and kept off this branch (branch
`task/2.0a-strips`). See "Next step".

## What the main thread did per frame (measured first)

Two kinds of measurement, both on the bench build (`LEAL_BENCH`), launched
with `open`, reference file, vertical flings at the fast profile:

- **Time Profiler**, attached for 12 s of flings (`xctrace record
  --template 'Time Profiler' --attach <pid>`), main thread, samples sorted
  into categories by the frames on their stacks.
- **Per-frame probes** (temporary, not committed): the main thread's
  instructions spent in `GridView.draw`, the gutter's draw, the core reads

So the slowest frames were the ones that scrolled into a new 64-row tile
(about 0.8 ms to read it on the main thread) and laid out a screenful of
new values, on top of the AppKit rebuild that every frame pays. The tile
reads and the layout are now done off the main thread, ahead of the
scroll. What every frame pays is now mostly AppKit's.

Two more findings:

- **AppKit redraws the whole visible grid about every 1.25 s** (every ~150
  frames) while scrolling, whatever the scroll speed. It isn't a
  `needsDisplay` from Leal (checked by logging every call's stack); it is
  inside AppKit's display-list handling. Those frames are about 0.7% of
  all frames, so they set the p99. They now cost 1.2–3.8 ms (before:
  3–5 ms), because the lines they need are cached.
- **The clock.** CPU time a frame tracks the core's clock as much as the
  work: the same build gave p99 2.2 ms at 3.0 GHz and 2.6 ms at 2.6 GHz.
  Leal can't raise it (the bench already declares a latency-critical
  activity, as real scrolling does); the lever is less work. Leal's main
  thread now retires about 5.2 M instructions a frame, against 12.5–13 M
  before.

### How each works

- **Batched drawing.** In a scroll view AppKit records the grid's drawing
  and replays all of what is in view on every frame, so every call costs
  again each frame. A strip's cells now hand their glyphs to a
  `GlyphBatch`, which draws them with one `CTFontDrawGlyphs` per font and
  colour: the glyphs and positions `CTLineDraw` would have drawn (taken
  from the line's runs when it is made). A line with runs in more than one
  font or colour (a value with control-character symbols, or a fallback
  font next to the system font) is still drawn by `CTLineDraw`, since its
  own runs may touch. The rows' shading is two fills (one per colour) and
  the separators one.
- **Tiles read ahead.** When a region is drawn, `CellTileCache` reads the
  row blocks above and below it and the column blocks either side on a
  background queue, through a reader `DocumentModel` makes from the
  document as it is (`backgroundTileReader`, the handle and header offset
  of the moment). Results come back to the main actor; `removeAll` (a
  reload, a new interpretation) drops any still in flight. A tile still
  missing when it is drawn is read there and then, as before, and a
  failed read ahead is simply not stored, so that read reports the error
  through `DocumentModel.call` as before.
- **Lines laid out ahead.** After each draw, `LineReadAhead` takes the
  rows past the visible area in the direction it moved (a screen or four
  frames' travel, at most a screen or two frames' travel a time),
  computes each cell's `LineRequest` exactly as the draw does (the same
  `charactersThatFit` cut and cache key), and lays the lines out on a
  background queue with the same code (`CellPainter.makeCellLine`, cut to
  the column as `drawText` cuts it). The lines go into the line cache, so
  the draw finds them; rows whose cells aren't read yet are read ahead
  first. The gutter does the same for its numbers (`NumberReadAhead`).
- **Smaller things.** The palette is made once per appearance (and again
  on `NSColor.systemColorsDidChangeNotification`); find's mark and the
  hatching colours are in it. Find's mark offsets come from one
  `CTLineEnumerateCaretOffsets` pass per line, made with the line when it
  is laid out ahead. The fitted (ellipsis) line's width is kept.

### Fidelity

What is drawn is unchanged; nothing in the core changed (F1–F6 untouched).
`GridDrawingTests` checks each replacement against what it replaces:

- batched text draws the **same pixels** as `CTLineDraw`, cell by cell, at
  three column widths, with and without the core's truncation, for values
  including fallback fonts (Korean, Japanese), right-to-left text, combining
  marks, emoji, control characters and long values cut to the column;
- the single-call fills and separators draw the same pixels as one call
  each;
- caret offsets equal `CTLineGetOffsetForStringIndex` at every index;
- lines laid out ahead, off the main thread, have the same glyphs,
  positions, widths and fitted lines as the ones the draw makes;
- reads ahead happen off the main thread, once, skip rows not indexed,
  are dropped when the cache is emptied, and leave a failed read to the
  draw; the grid lays out the rows ahead of a scroll.

The existing rendering, selection, find and document tests pass unchanged
(`just app-test`: 145 passed, the 10 new ones among them).

### Memory

The line cache holds up to 2,500 lines (was 1,500) and the gutter's 1,000
numbers (was up to 2,000 in a dictionary emptied at once). A first version
with 4,000 each added about 10 MB of heap while scrolling; at these sizes
the heap is the same as `main`'s (`just perf`: settled 10.8 MB without a
search and 19.7 MB with one, net of the AppKit baseline, against Rob's
7.6–14.3 and 19.4–19.7 MB). Footprint is lower than in Rob's run: peak
while scrolling 213–216 MB after indexing (Rob: 220–232), 216–220 MB with
a search (233–238) and 422–542 MB on the 1 GB file (775–809).

## Tried and not kept

- **Tiles (1.10's patch)** not retried.
- **Caret offsets from glyph positions.** Core Text's caret offsets aren't
  where the glyphs start: with kerning it puts the caret part-way, so
  "Toronto" at index 1 is 6.89 pt by glyph and 7.53 pt by caret. Replaced
  by `CTLineEnumerateCaretOffsets`, which matches exactly.
- **Bigger caches** (4,000 lines each): no faster than 2,500 / 1,000, and
  10 MB more heap.
- **A glyph table for ASCII text** instead of Core Text layout: not built.
  It can't be shown to draw the same (kerning, contextual forms, the
  tabular-digit feature) on every macOS font version, and laying out ahead
  off the main thread gives the same saving exactly.
- **Strips of rows that scrolling moves** (`GridStrips`): it works and
  helps a lot, but it is a drawing-design change: ADR-0011, below.

## Next step: ADR-0011 (proposed)

What every frame still pays is AppKit rebuilding the visible grid's and
gutter's layers from their recorded drawing (about half the frame), and
the periodic full redraws. The prototype on branch `task/2.0a-strips`
(one commit on top of this branch, behind `-LealStrips YES`, not for
landing) draws the grid's cells and the gutter's numbers into strips four
rows tall, each its own `CALayer` (drawn asynchronously), in layer-hosting
views over the two clip views; a scroll moves them, and only strips coming
into view are drawn. Against this branch, same binary, alternating:

| | This branch | Strips |
|---|---|---|
| Reference file, vertical flings: CPU p50 / p99 | 1.59–1.60 / 2.35–2.44 ms | 0.97–0.98 / 1.76–1.90 ms |
| … instructions p50 / p99 | 5.5 / 8.9 M | 2.2 / 6.2 M |
| Reference file, full benchmark: CPU p50 / p99 | 1.63 / 2.58 ms | 0.93 / 1.68 ms |
| Footprint peak, reference file | 212 MB | 238 MB |
| 200-column file, full benchmark: CPU p50 / p99 | 1.59 / 2.88 ms | 1.15 / 4.07 ms (512 pt column tiles) |

So strips would give about 1.5× more headroom on the reference file, but
need care: wide grids (more than about 4,096 pt) are worse with column
tiles and should keep this branch's drawing; footprint rises by 10–30 MB;
the in-cell editor (phase 2) must sit above the strips. The ADR has the
details and the open questions for Rob.

## Rust notes

No Rust changed in this task: everything is in the Swift app (the grid's
drawing and the bench). Two Swift concurrency points a Rust reader might
recognise:

- Work handed to a background queue must be `Sendable`, Swift's version of
  Rust's `Send`. `TextLine` is marked `@unchecked Sendable`
  (`CellPainter.swift`): it is built on one thread, then handed to the main
  thread, which alone uses it after that, much like moving a value into a
  channel. `@unchecked` means the compiler takes our word for it, so the
  comment beside it says why it holds.
- `@MainActor` is like a type that can only be touched from one thread;
  results from the background come back with `Task { @MainActor in … }`,
  as a Rust program would send them back over a channel to the UI thread.
