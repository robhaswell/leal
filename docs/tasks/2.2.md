# 2.2 Serializer

The core can now save (DESIGN §3.7, ADR-0012). A save writes the file Leal
read, byte for byte, with **splices**: each edited row's changed bytes in
place of its old ones. Everything outside a splice is copied from the
snapshot as it is, so an unedited byte can't change. It runs as a job with
a handle (ADR-0005 decision 6), on its own thread, and the main thread
never waits for it (DESIGN §3.9): edits carry on while it runs, and no
file is touched under the document's lock. It writes a new file next to
the user's, gives it the old one's metadata, and puts it in place: swapped
with the old one, which is then checked, where the volume can swap (APFS);
renamed over it where it can't (HFS+, exFAT, FAT). Then it **rebases** the
document onto the file it wrote (ADR-0008 decision 1): a new snapshot, a
new reading whose rows read at once, the same undo lineage. The watcher
expects the save's own swap, so Leal's save is never an outside change.

Also in this task:

- **The check before writing** (ADR-0008 decision 9, ADR-0012 decision 1):
  the file opened afresh and looked at with `fstat`; refused, each with its
  own reason, if it changed elsewhere, isn't there, is being moved, isn't
  writable by Leal, is locked, or isn't a regular file. Checked again under
  the watcher's lock just before the swap (with its metadata copied again
  if that changed meanwhile), and once more after it, on the file swapped
  out, where the volume swaps.
- **Metadata, best-effort, by an explicit policy** (ADR-0012 decision 1).
- **Attributes** (ADR-0004 decision 11, ADR-0005 decision 1, ADR-0008
  decision 8, ADR-0012 decision 3): `com.apple.TextEncoding` and Leal's
  interpretation attribute written or removed on every save, with the new
  file's fingerprint, never copied stale. One part is left for 2.5.
- **Save As from an incomplete document** (ADR-0008 decision 6,
  ADR-0010): the complete rows Leal trusts, cut at a row boundary, with the
  edits, and how many rows were written.
- **4 GiB** (ADR-0012 decision 2): refused before the new file goes
  anywhere.
- **Undo across a save works by value** (ADR-0012 decision 4).
- **The F1–F5 property tests** against the save oracle, the reopen
  property, and two benchmarks.
- **FFI** for 2.5.

Out of scope, as the brief says: encoding non-ASCII edits in single-byte
encodings (2.3), row and column inserts and deletes (2.4), and the app's
Save, Save As and Revert (2.5).

The review's findings and what changed for each are under "Changes after
review", at the end. The sections before it describe the code as it is
now.

### The save, step by step

`Document::save(self: &Arc<Self>, SaveRequest) -> SaveJob` starts a job
on a thread of its own (`leal-save`, P1: a save the user asked for never
pauses for them). The job:

1. **Takes its turn.** One save of a document at a time: a later one waits
   (`SavePhase::Queued`) and can be cancelled meanwhile. Waiting saves
   aren't served in the order they were asked for: whichever looks first
   (every 20 ms) goes next. 2.5 starts one save at a time anyway. While any
   save runs, the file isn't read again (`DocumentError::Saving`), and a
   drive that comes back isn't reconnected until it ends: the save then
   checks again, and `SaveJob::restarted` says if it read the file again.
2. **Waits for the index pass** to finish (`Indexing`), checking for a
   cancel every 20 ms: every row is indexed, and for a file on a removable
   drive or a share the copy is complete (or has stopped: an incomplete
   document).
3. **Takes a snapshot of the edits** (an `Arc` of the overlay and its
   version) under the writer lock, for microseconds, and lets go. The phase
   becomes `Writing` and `SaveProgress::snapshot_version` the edits'
   version (`Document::edit_version`) while the lock is held, so an edit
   made after the app sees them is after the snapshot.
4. **Save only, the checks before writing:** an incomplete document is
   `Incomplete`; an unmounted volume `Unavailable`; a move still within the
   watcher's window `Moving`; then the file opened afresh: `diverged`
   (the watcher saw a change) or not the one Leal opened or last saved
   (inode, size, modification time) is `ChangedElsewhere`, unless the user
   agreed; nothing there `Missing`; immutable or append-only `Locked`; not
   writable by Leal (`faccessat(W_OK, AT_EACCESS)`) `NotWritable`; not a
   regular file `NotAFile`. Save As refuses a locked file or anything other
   than a regular file at the destination (looked at without following a
   link, after the destination's own link is resolved), and keeps an
   existing file's metadata. Every edited value must be encodable (until
   2.3, `EncodingNotSupported`).
5. **Writes the new file** in a recorded folder on the
   destination's volume, in file order, making each edited row's splices as
   it reaches it: the snapshot's bytes 1 MiB at a time with a checkpoint
   before each chunk (DESIGN §3.10 rule 3), and a checkpoint every 256
   edited rows. On a removable drive or a share every byte is also teed to
   a copy on the internal disk. It stops with `TooLarge` as soon as the
   output passes 4 GiB, and checks that it wrote exactly the length it
   expected. It keeps the first 64 KB and, when the encoding was guessed,
   the whole file's encoding census.
6. **Metadata and attributes** (`Flushing`), by the policy below; then
   `F_BARRIERFSYNC`; then the document's next snapshot of the new file (the
   tee copy, or a clone of it, or, if the volume can't clone, a copy read
   back a MiB at a time with a checkpoint before each); then the new file
   is closed, and its identity noted.
7. **Into place** (`Replacing`), under the watcher's lock only (edits carry
   on): events the kernel has queued are looked at first; for Save,
   `diverged` set during the save, or the file not as checked, refuses. If
   the file's status-change time moved since step 4 (its permissions, flags
   or attributes changed, not its contents), it is checked again (`Locked`,
   `NotWritable`) and its metadata copied to the new file again. Then the
   new file goes into place the way the destination's volume allows
   (`getattrlist(ATTR_VOL_CAPABILITIES)` on its folder):
   - **it can swap** (`VOL_CAP_INT_RENAME_SWAP`: APFS):
     `renamex_np(RENAME_SWAP)`, and the file swapped out is compared with
     the one checked (opened with `O_NOFOLLOW`). If another app changed it
     in between, or it isn't a regular file, it is swapped back and the
     save refused. If it can't be looked at, or can't be swapped back, the
     save has still succeeded, and that file is kept, never deleted: moved
     next to the file as "a (replaced, kept by Leal).csv" (`Saved::kept`),
     or left in Leal's hidden folder, which is then never cleaned up;
   - **it can't** (HFS+, exFAT, FAT): a plain `rename` over it, with no
     check after; the one just before still holds;
   - **nothing there** (Save As): `RENAME_EXCL` where supported (APFS,
     HFS+), and otherwise a look that nothing is there, then `rename`
     (exFAT, FAT).

   `EPERM` is `Locked`, `EACCES` `NotWritable`. From here the save has
   succeeded, whatever fails: no error is returned. The new file's identity
   comes from a fresh open and `fstat`, or, if that fails, from step 6; the
   watcher watches it as if just opened. A cancel no longer does anything.
8. **Rebase:** a new reading of the snapshot, made with no lock held, split the way the old one was
   (as a reopen would read it with the attributes just written and the
   user's choices; the old way regardless if that differed). Its rows are
   the old index's, shifted by each edited row's change in length (cell
   edits never move a row boundary), so every row reads at once; the index
   pass runs again in the background only for the diagnostics and the
   review (it is one pass, about 60 ms per 100 MB). Its edits are an empty
   `EditStore::rebased` in the old lineage. Then, under the writer lock
   only for this, the edits made since the snapshot are **carried over by
   value**, in one change: each cell they touched (or that the snapshot had
   edited in their rows) is set to what it reads as now. The new reading
   replaces the old one, with a new generation. The lock goes; then the old
   file a swap left behind is deleted, and the first screen read. If the
   snapshot can't be mapped, the save still succeeded: `Saved::reread` is
   `None`, `reread_error` says why, `edits_during_save` names the cells
   edited since the snapshot, and the document keeps reading the old
   snapshot with its edits (a later save writes the same bytes).

A cancel or a failure anywhere before the new file is in place deletes the
new file, its folder, its record and any tee copy, and the user's file is
as it was.

### The splice rules (for cell edits)

These are the save oracle's (`leal_testkit::save`) and the property tests
compare the two splice for splice:

- An unedited row: no splice.
- Each edited field whose bytes change: `replace(field span, bytes)`,
  where the bytes are the value encoded and quoted if it needs it, if the
  field was quoted, or if the file quotes every field.
- Edited hatched cells (ADR-0005 decision 2): one `insert` at the end of
  the row's bytes (before its line ending) of a delimiter and the cell's
  bytes for each cell from the row's end to the last edited one (padding
  cells have none). Quoted if the file quotes every field.
- ADR-0004 decision 6: a row whose bytes would be empty (its only field
  emptied) is `""`. ADR-0004 decisions 7 and 10: in a file without a BOM,
  a first field starting with `EF BB BF`, `FF FE` or `FE FF` is quoted.
  Either makes the splice the whole row, line ending included. Fixes are
  listed as the oracle lists them: the `""` rows, then the BOM-like field.
- The CR/LF split (ADR-0004 decision 10) can't arise from cell edits: an
  edited row never starts with LF and keeps its own line ending. 2.4 adds
  it with row inserts and deletes.

"The file quotes every field" needs every row parsed, so it is worked out
only when it matters (a hatched cell, or a blank line's one field, is
edited: every other field carries its own quoting), once, when the writer
first reaches such a row. It stops at the first unquoted field.

### The metadata policy (ADR-0012 decision 1)

In this order, so nothing earlier can block anything later (an access
control list that denies writing attributes or permissions comes last):

1. **Each extended attribute on its own**, if the system keeps it for a
   safe save (`xattr_preserve_for_intent(…, XATTR_OPERATION_INTENT_SAVE)`,
   which drops quarantine and the attributes tied to the contents, `#C`),
   or it is on the keep-list: `com.apple.FinderInfo` (type, creator,
   label, the custom-icon bit) and `com.apple.ResourceFork` (an old custom
   icon), which the system leaves to copy engines and says not to keep.
   Never Leal's own two, nor `com.apple.decmpfs` (the old file's
   compression header), nor the ones the system sets or derives itself:
   `com.apple.macl`, `com.apple.provenance`, `com.apple.rootless` and
   Spotlight's `com.apple.metadata:kMDLabel_*`. Tags (`_kMDItemUserTags`)
   and comments the system keeps. One that can't be set (`EPERM`, `EACCES`,
   `ENOTSUP`, `E2BIG`, `EINVAL`; any other error fails the save) is skipped
   and named in `Saved::skipped_metadata`.
2. **Leal's two attributes**, written or removed.
3. The owner and group (where Leal may; "owner" if not), the creation
   date, the mode, and the flags: only `UF_SETTABLE`, never
   `UF_COMPRESSED`, `UF_DATAVAULT`, the locking flags or any `SF_*`.
4. **The access control list**, last, with `acl_get_fd_np` and
   `acl_set_fd_np`; an empty one if the old file had none, so entries the
   new file inherited from its folder don't stay. Not
   `fcopyfile(COPYFILE_ACL)`, which the tests showed also applies the old
   file's quarantine.

The new file is made as any new file is (`0666` less the umask, which says
what mode a new file gets here; the umask can't be read without changing
it), then set to `0600` until it is finished. A new file (Save As to a new
place) gets that mode back.

## Decisions and interpretations

- **The core does the safe save** (ADR-0012 decision 1, accepted).
  NSDocument's guards come with it: the writable and locked checks, the
  metadata policy, and the swap-and-check.
- **Undo across a save works by value** (ADR-0012 decision 4, accepted).
  After a save, a hatched cell (and any padding before it) is a field of
  the file, and a cell edit can't make a field go away. So once a store is
  `rebased`, a command that means "missing" is satisfied by an empty field,
  and making a field missing empties it (`document/editing.rs`, `holds`).
  Undo then redo restores the value; undo leaves `a,,` where the row was
  `a` before the save, and a field saved quoted stays quoted. F3 holds from
  the last save.
- **4 GiB refused** (ADR-0012 decision 2, accepted): checked as the file
  is written, before it goes anywhere. Computing the length first would
  mean making every splice twice; the user sees the same thing.
- **A BOM file that had `com.apple.TextEncoding` keeps it, updated**
  (ADR-0012 decision 3, accepted).
- **Edits during a save carry over by value.** The core keeps no
  commands, only the edits; what matters is what each cell reads as, so the
  carry-over sets each cell touched since the snapshot (or edited in the
  snapshot's version of those rows) to its value now, on the new base. A
  command made during the save then undoes and redoes there as any other
  (a test does it). `Saved::edits_during_save` names the cells (the
  document is still dirty). For NSDocument's change count, 2.5 uses tokens,
  not counts: it notes `changeCountToken` with `edit_version` after each
  edit, and after the save applies the token noted at
  `SaveProgress::snapshot_version`, and resets the recovery journal at the
  same point. An edit
  during a save to a row the save didn't write (Save As from an incomplete
  document) is lost with that row and named in `skipped_edits`.
- **`reinterpret` is refused while a save runs** (`DocumentError::Saving`,
  FFI `LealError.Saving`), the header toggle included: the save replaces the
  reading when it ends. A drive found back while a save runs isn't
  reconnected then; the save checks again as it ends (on its own thread,
  before the job finishes), and `SaveJob::restarted` says if the file was
  read again. The FFI relabels its cached first screen only for its own
  restart (`Restarted { from, to }`, applied only if the cache is `from`'s),
  so a check racing a save's end can't label the old screen with the new
  generation.
- **Find during a save:** a search keeps searching the reading it started
  on, as after a re-read; 2.5 restarts Find when the generation changes,
  as it already must after Treat As. Not cancelling it in the core keeps a
  save from touching jobs it didn't start.
- **Swap or rename by the volume's capabilities, not by trying.**
  `getattrlist(ATTR_VOL_CAPABILITIES)` on the destination's folder decides,
  measured on this Mac: APFS swaps and renames exclusively; HFS+ renames
  exclusively but can't swap; exFAT and FAT do neither. Trying a swap isn't
  safe: FAT's driver returns success for `RENAME_SWAP` and does a plain
  rename, so the "file swapped out" is gone and the round-2 code then failed
  a save that had replaced the file. (Round 2's notes said "exFAT on this
  Mac swaps": that was the same false success.) Where the volume can't
  swap there is no check after; the one under the watcher's lock just
  before still holds, and `Saved::placed` says `Renamed`. A Save As to a
  new place uses `RENAME_EXCL` where supported, and replaces a file that
  appeared there meanwhile only on `EEXIST`; elsewhere it looks that
  nothing is there, then renames.
- **Never an error once the file is in place.** From a successful swap or
  rename on, the save has succeeded: its identity is a fresh look, or the
  one noted before it was closed, and the watcher re-establishes the rest.
  The old file a swap took out is deleted only once it is known to be the
  one checked (or, for Save As, a regular file); otherwise it is kept and
  reported (`Saved::kept`).
- **`F_BARRIERFSYNC`, not `F_FULLFSYNC`, before the swap.** Atomicity needs
  ordering: the new file's bytes reach the disk before the rename that
  makes them the file, so a crash leaves the old file or the whole new one.
  A barrier gives that without waiting for the drive's cache to empty
  (`F_FULLFSYNC` can take tens of milliseconds). The trade-off: after a
  power cut in the second after a save, the old file may come back rather
  than the new one. Where a barrier isn't supported (`ENOTSUP`, `EINVAL`,
  `ENOTTY`), `F_FULLFSYNC` (stronger, so nothing is lost), and where that
  isn't either, `fsync` (Rust's `sync_data` would be `F_FULLFSYNC` on
  Apple systems, so it isn't used). The tee copy on the internal disk is
  Leal's own scratch file and isn't flushed at all.
- **What a crash can do.** On APFS and HFS+, which journal the rename, a
  crash leaves the old file or the new one, never half of each. On exFAT
  and FAT, which don't journal, a crash during the rename can leave the
  directory as their own repair finds it; Leal can't do better there. A
  crash between a swap and its check leaves the file swapped out in Leal's
  recorded folder, and the next launch's cleanup deletes it, even if it was
  another app's version the check would have kept.
- **Save As never replaces anything but a regular file** (`NotAFile`):
  `rename` would replace a pipe or a device, and a swap a folder.
- **The hidden `.leal-save-<id>` folder** is used only when the app gives
  no folder, or one on another volume (the folder's `st_dev` is checked).
  A sandboxed app may not be allowed to make it next to the user's file, so
  2.5 always passes the item-replacement folder; the fallback is for the
  CLI and tests. Its record means a crash leaves nothing after the next
  launch.
- **The rebased reading's field-count mode** is the old index's until the
  new index pass gives the new file's own (a few dozen milliseconds later):
  a hatched edit that changed which count is most common shows in the
  grid's column count then.
- **Single-byte files until 2.3:** an ASCII edit saves; any other value is
  refused, naming every such cell, before anything is written. `save::encode`
  is the one place 2.3 changes.
- **Attributes: all of ADR-0008 decision 8 but one part.** In the core,
  because the attributes must be on the new file before it goes into place.
  - `com.apple.TextEncoding`: recorded if the file had one when opened,
    if the user chose the encoding, or, without a BOM, if a reopen would
    guess another one from the first 64 KB or from the whole file; with a
    BOM, only if the file had one. Otherwise removed.
  - The interpretation attribute: recorded, with the new file's
    fingerprint, if the delimiter or header was the user's choice or came
    from the attribute, or a reopen's first paint (with the encoding as
    recorded) would guess either differently. Otherwise removed.
  - **Not in (SEAM(2.5)):** the interpretation attribute when a reopen's
    *whole-file review* would suggest another delimiter. For files up to
    64 KB first paint sees the whole file, so it is covered (and the
    properties check it). For larger files it needs the review of the new
    file, about half a second per 100 MB. The rebased reading runs that
    very review anyway, so 2.5 can write the attribute when it suggests a
    delimiter, at no cost to the save.
- **What a safe save can't keep:** a hard link to the file keeps the old
  contents; a symbolic link is followed, so the link survives and its target
  is replaced; the owner is kept only where Leal may set it.
- **Benchmarks:** `save/one_edit` is budget-only (it flushes 100 MB, so it
  is the runner's disk's time); `save/write_no_disk` is the same save's
  work into a writer that keeps nothing, compared between commits.

When the job ends, a callback registered in `save` (not only `wait`)
replaces the document's cached first screen if the new one's generation is
newer, and watches the new reading's jobs for panics; if the save's end
read the file again (a drive back, `SaveJob::restarted`), it relabels the
cached screen as `checkOriginal` does for its own restart. A panic in the
save job fails the document, as in any of its jobs.

## What 2.3, 2.4 and 2.5 need

- **2.3:** `save::encode` returns the encoded bytes (or which character
  can't be); `SaveError::EncodingNotSupported` becomes F5's `Unencodable`,
  and the property's TODO(2.3) branch goes.

## Rust notes

- **`self: &Arc<Self>`** (`Document::save`). A method can ask for its
  receiver as an `Arc` rather than a plain reference. The save's thread
  needs the document for as long as it runs, maybe longer than the caller
  keeps it, so it clones the `Arc` (a reference count, not a copy) and
  moves the clone into the job. The FFI's `Document` holds its core
  document in an `Arc` for the same reason.
- **Moving state into the thing that changes together**
  (`Reading.source`, commit 1). Putting the source in the `Reading`, which
  is swapped as a whole (`RwLock<Arc<Reading>>`), means a reader that took
  a reading also has the bytes that reading's index points into: they
  can't come from two different files.
- **A trait for "where the bytes go"** (`Sink` in `document/saving.rs`).
  The writer walks the file once and calls `copy` and `splice`; one `Sink`
  writes the new file, another (tests) only lists the splices. The same
  walk serves both, so what the tests check is what the save writes.
  `&mut dyn Sink` is a reference to "some type that implements `Sink`",
  decided at run time.
- **`OnceLock`** (`SaveShared::error`, `SaveJob::result`). A slot written
  at most once and then read by reference forever, so `wait` can return
  `&SaveError` (borrowed from the job) without cloning an `io::Error`,
  which can't be cloned.
- **`Cell`** (the checkpoint counter, and `checked`, `changed`, `redone`
  and `put` in `save_now`). Changing a value through a shared reference,
  safely, because it is never shared between threads: the two closures
  passed to `replace_with` both need to see `checked`, and only one of them
  could borrow it mutably. A `Cell<Option<T>>` holds even a value that
  can't be copied (`Existing`, `Put`): `set(Some(…))` puts it in, `take()`
  takes it out and leaves `None`.
- **`thread_local!`** (`FAIL_SWAP_BACK` in `source/write.rs`, tests only).
  A static each thread has its own copy of: a test sets it on its own
  thread, and tests running at the same time on other threads don't see
  it.
- **`std::mem::forget`** (`TempFolder::keep`). Ends a value's life without
  running its `Drop`: the folder's `Drop` deletes it, which `keep` must
  not do. Its fields are taken out first, so nothing is leaked.
- **An `AtomicBool` as a turn** (`Document::take_turn`, `Turn`).
  `compare_exchange(false, true)` sets the flag only if no one else has,
  in one step no other thread can come between; the `Turn` guard clears it
  when dropped, however the save ends.
- **Drop as clean-up** (`Staged`, `Turn`, `Acl`). The new file's folder is
  a `TempFolder`, whose `Drop` deletes it, with whatever file is in it:
  every early `return` or `?` deletes what the save wrote; after the swap,
  the old file. `Acl` frees the C library's access control list when it
  goes out of scope.
- **`extern "C"`** (`sys.rs`: `xattr_preserve_for_intent`, `acl_get_fd_np`
  and friends). The `libc` crate doesn't declare every macOS function, so
  `sys.rs` declares these itself, as C's headers do; calling them is
  `unsafe`, one call per block, each with its `SAFETY` comment.
- **`#[cfg(test)]` and `#[cfg(not(test))]`** (`ChunkHook`,
  `chunk_bytes`). The test hooks exist only in test builds; the product
  build has a hook type that can't be made (`Infallible`), and the chunk
  size is a constant there.
- **`let … else` and `if let … &&`** (throughout `stream`). Binding a
  pattern or leaving the function, and chaining a pattern with conditions,
  keep the many "skip if" paths flat.
