# 2.4a Rows

Insert and delete rows in the core, with undo, redo and replay, every
reader going through the piece list. Not saved yet: a save with rows
inserted or deleted is refused (`SaveError::RowsChanged`) until 2.4c.
Design: `docs/tasks/2.4.md` (§1, §2, §4's row commands, §5 without the
column restart, §7); ADR-0014 decisions 1 and 3.

## What was built

- **Row ids and the piece list** (`edit/rows.rs`). `RowId(u64)`: an
  original row's is its physical row, an inserted row's 2³² + n from a
  per-store counter. `Piece::{Original, Inserted}` (16 bytes),
  `Segment::{Original, Inserted}(Range<u32>)`, `Slot`. `RowMap` keeps
  pieces in `Arc`'d leaves of ≤ 512 with two top arrays (each leaf's first
  logical row and first key); continuing neighbours merge, and a map that
  is one `Original { 0, N }` piece goes back to the identity, which costs
  the readers nothing. An edit rebuilds the edited leaf and one either
  side, then the top arrays. The fixed interface is there:
  `len, slot, segments, logical_of, physical_at_or_after,
  logical_of_inserted, rows_within`, plus `originals_in`, `next_live`,
  `live_end_before` and `shift` for the walks.
- **The overlay** (`edit/overlay.rs`) keys `RowEdits` by `RowId`, holds
  `inserted: BTreeMap<u32, Arc<InsertedRow { gap, fields }>>` and the map.
  The store's log is `(RowId, count)` runs with running row totals; the
  version counts rows, so a big delete is a big catch-up. Each store has a
  `BaseId` (new per split and per save's rebase).
- **Commands** (`edit/command.rs`, `edit/structural.rs`).
  `Edit::InsertRows { at, rows }` / `DeleteRows { at, rows }` with an
  opaque `Arc<Rows>` (pieces, the rows' `RowEdits` and `InsertedRow`s, and
  for original rows a `RowSource`: the reading the delete was made on).
  `inverse` swaps the two. In the same base a command applies by identity:
  the rows must be absent (insert) or exactly the pieces, edits and
  inserted rows recorded (delete), so an undone delete brings back the
  original bytes. In another base (after a save, or `replay`) it works by
  value: `Rows::values` reads original rows lazily from the kept reading,
  a delete first checks the rows read as recorded.
- **Document** (`document/structural.rs`): `insert_rows(at, rows)`,
  `delete_rows(at, count)`, `can_change_rows`, `can_insert_rows(at)`.
  Refusals: `StillReading` (index not complete, a removable drive's copy
  not done, or the head stale), `Saving` (checked under the writer lock),
  `NoSuchRow`, `AfterUnterminatedQuote` (rule 10, O(log P): an open quote's
  row, if present, must be the last row; also checked by cell edits that
  reopen it once rows follow).
- **The seam.** Every walk of §2's table takes logical rows through
  `RowMap::segments`: `read_rows_of` (grid, `cells`, number sample,
  inspector, editor, by-value checks), `row_count`, `estimated_row_count`,
  `progress` and the index callback, `column_count` (0 with every row
  deleted), `first_screen`, marks (`row_has_diagnostic`, `row_flags`,
  Previous/Next), each kind's Previous/Next (physical search from
  `physical_at_or_after`, deleted hits skipped by whole stretches, inserted
  runs in between checked), Copy (now and the job; estimate), cell edits
  (logical row → `Slot` → `RowId`), `edit_conflicts` (logical rows,
  deleted dropped). `RowView` gains inserted rows (`ViewCell::New`).
- **Find** (`document/search.rs`, §5). Original rows keep their physical
  row as key; a chunk takes its edits and live stretches in one look and
  skips the deleted. Inserted rows are searched in `find` (in memory), kept
  in logical order with their own running counts. Catch-up recounts each
  touched `RowId` (0 if gone) and recomputes inserted rows' logical places
  in the map the counts are right for (`Found::map`). Queries add both
  sums; steps merge the two lists, an inserted match waiting until the
  file's rows before it are searched.
- **FFI**: `insert_rows`, `delete_rows`, `can_change_rows`,
  `can_insert_rows`; `EditCommand.structural: Option<Arc<StructuralEdit>>`
  (opaque, with `inserts`, `first_row`, `row_count`);
  `EditRefusal::{StillReading, Saving}`; `SaveFailure::RowsChanged`. Row
  numbers in the FFI's docs are logical now.

## Deviations from `docs/tasks/2.4.md`

1. **The header row is searched and left out**, rather than starting the
   search at physical row 1: which row is logical row 0 changes with
   deletes and inserts, so Find counts it like any row and subtracts its
   matches (`Found::header_cells`) in every answer.
2. **`physical_at_or_after` of an inserted row is its gap**, not the next
   live original row: it splits the live originals at that logical row,
   which is what every caller needs, in O(log P) without a scan.
3. **`RowView::{id, cell_id, same_shape}` and `save::ColumnQuoting` are not
   added**: nothing in 2.4a uses them (they would be dead code under
   clippy). 2.4b adds `cell_id` with `CellId`, 2.4c `id` and `same_shape`;
   `ViewCell::New` is in.
4. **Rows can't change after a save until the saved file's index pass
   ends** (`StillReading`): the rebase serves rows from a shifted index
   while it re-indexes. 2.4c's `RowIndex::from_starts` can make it
   complete at once.
5. **`has_edits`** stays true while any row is inserted or deleted, even
   if a new row reads as a deleted one did (the edit property checks the
   save oracle's bytes only when the rows are the file's, in order).
   Inserting and deleting the same rows again is no edit.
6. **An empty inserted row has one empty cell**, as a blank line reads
   (the oracle needs at least one value).

## Tests

- `edit/rows/tests.rs`: the map against a `Vec<Slot>` model over 100,000
  random inserts, deletes (some of 300 rows) and undos on 20,000 rows,
  reaching over 4 leaves of pieces: every answer at random places each
  step, and all of them every 5,000; undo of everything gives the
  identity. Plus out-of-order runs refused, every row deleted, an empty
  file, row ids.
- `edit/overlay.rs`: the run log, versions counting rows, edits moved out
  and back, inserted rows.
- `document/tests/rows.rs`: every reader after inserts and deletes
  (grid, window, counts, inspector, copy now and job, flags, the first
  screen after a header toggle); undo and redo restore the same rows and
  edits, out-of-order commands refused, undo-all leaves `has_edits()`
  false; the header row is logical row 0; every row deleted; marks and
  each kind's Previous/Next with inserted and deleted rows; nothing after
  an open unterminated quote; `StillReading` while indexing; Find
  catching up (a finished and a running search, a 500-row delete through
  the catch-up job, an inserted header row, then everything undone) equal
  to a fresh search, forward and backward, ordinals and highlights;
  replay by value, and a delete refused when its rows read otherwise.
- `document/tests/saving.rs`: `Saving` during a save (and for undoing a
  row command), `RowsChanged` with nothing written (Save and Save As), a
  delete applied by value after the save.
- **The edit property** (`tests/edits/properties.rs`) now replays the
  strategy's row inserts and deletes, plus runs of 1–3 inserted and 1–4
  deleted rows, undo and redo of them (the oracle set back to its snapshot
  before or after), mixed with cell edits; every reader is checked against
  the oracle's edited view, and a search started before the edits must
  agree. The replay property replays row edits too. 20,000 cases
  (`just test-deep`) pass; making the readers skip inserted rows fails it
  at once.
- FFI: insert, edit an inserted cell, delete, refusals, undo, redo and
  replay through `EditCommand`.

`just check`: 869 tests. `just test-deep` (20,000 cases): 869 passed.
`just app-test`: 215 passed (a first run lost two removable-drive tests
to the disk-image helper's 20-minute limit during a slow build; they pass
on a rerun). `check-no-test-exports` and `check-no-bench` pass on the
Release app.

## Benchmarks

`row_edits` (new, reference file, 1M rows; M-series laptop, quick run):

| benchmark | median |
|---|---|
| `row_edits/screen` (no row edits) | 16.6 µs |
| `row_edits/screen_100k_row_edits` (~90 segments) | 16.2 µs |
| `row_edits/insert_row_100k_row_edits` (insert + undo) | 13.1 µs |
| `row_edits/delete_1k_rows_100k_row_edits` (delete + undo) | 18.7 µs |

Insert and delete are far inside the 16 ms budget; the screen read
through ~200,000 pieces costs no more than without them (half its rows
are inserted rows, read from memory).

`just bench-compare main` passed on its first attempt, no regression or
budget failure. The rows path with no row edits: `edits/screen` +0.5%,
`rows/screen` +2.2%, `find/every_row` −0.6%, `marks/*` and `navigate/*`
−0.3% to −6.8%. `edits/set_cell_100k_edited_rows` +8.4% (739 ns: a cell
edit now resolves its row through the map and checks the quote rule's
row count). A first run had flagged `navigate/next_nul_wide` at +22%:
`RowView::filled` looked each column up through the new own-cell match;
it walks the fields again, and `first_with` gained an allocation-free
path for an unedited row.

## Rust notes

- **`Arc` leaves for cheap snapshots** (`edit/rows.rs`). The piece list is
  a `Vec<Arc<Leaf>>`. Cloning the map clones the vector of pointers, not
  the pieces, so a reader's snapshot costs a few hundred reference counts
  even with 100,000 edits. An edit builds new leaves for the part it
  changes and leaves the others shared.
- **Trait objects** (`edit/structural.rs`). `RowSource` is a trait; a
  delete command holds `Arc<dyn RowSource>`, which is the document's
  reading behind a pointer to "something that can read rows". The `edit`
  module doesn't need to know what a reading is, and the reading stays
  alive as long as the command does (ADR-0014 decision 3).
- **Manual `PartialEq` and `Hash`** for `Rows`: two payloads are equal if
  they are the same rows of the same file, and their shared values are
  compared with `Arc::ptr_eq` (the same allocation) first.
- **Lock guards in loop conditions** (`search.rs`, `step_forward`). A
  `while let x = mutex.lock().f()` keeps the guard alive for the whole
  loop body; taking the value in a `let` statement first lets go of the
  lock before the row is read.
- **Keeping two borrows apart** (`EditStore::change_rows`): the
  overlay is borrowed mutably through `Arc::make_mut` while the cell count
  is kept in a local and written back after, so the borrow checker sees
  two separate borrows.
