# 2.6 App: paste and clear

Status: built; awaiting review. Paste (⌘V) and Clear (Delete) in the grid,
on top of the core's cell batches (2.1) and the undo history and journal
(2.5.2).

## What was built

**Core** (`crates/leal-core`):
- `edit/paste.rs`: `parse_tsv`, clipboard text as cells (below).
- `document/pasting.rs`: `Document::paste(rows, columns, columns_shown,
  text)`, `clear_cells(rows, columns)`, `can_paste()`,
  `can_clear_cells(..)`. Each makes one `Edit::SetCells` command through
  the same code as typing (`change_in`), so overlay, undo/redo, replay,
  saving and Find's catch-up treat it as cell edits.
- New limits and refusals (`edit/command.rs`): `CELL_BATCH_LIMIT`
  (100,000 cells), `PASTE_BYTE_LIMIT` (32 MB), `EditError::TooManyCells`,
  `TooMuchText`, `PastLastRow`, `PastLastColumn`.

**FFI** (`leal-ffi/src/document/editing.rs`): `paste`, `can_paste`,
`clear_cells`, `can_clear_cells`, `cell_batch_limit()`,
`paste_byte_limit()`, `paste_shape(text)` (to select the pasted block), the
four new `EditRefusal`s, and **`CellBatch`**: a command of more than 256
cells (any batch, `set_cells`' too) keeps its changes in Rust (`EditCommand.cells`), as `StructuralEdit`
does for rows. Handing Swift 100,000 `ValueChange`s took ~115 ms, five
times the edit; now Swift sees only `count`, `first`, `rows` (first/last
row) and `longest(undone, perColumn)` (the values that may widen a column).

**App**:
- `GridView`: `paste(_:)`, `delete(_:)` (Edit > Delete), and
  `deleteBackward`/`deleteForward` (⌫, ⌦) → `onPaste` / `onClear`; menu
  validation through `validateCellItem`. A held Delete clears once.
- `Window/CellCommands.swift`: running them (commit an open edit first;
  one undo step named "Paste" / "Clear Cells" via `asOneStep`), enabling
  with the reason as tooltip, refusals, and the words (`PasteText`).
- `Document/DocumentCells.swift`: the model's calls; `cellArea` turns the
  selection into logical rows (after the header row) within the file's
  rows and the grid's columns (⌘A runs to the last row).
- `EditCommand` helpers (`cellCount`, `firstChange`, `changedRows`,
  `valuesShown`) used by `valuesChanged`, the undo name and the recovery
  report, for both inline and batched commands. `valuesChanged` now works
  from the row span, and widens columns from each column's 16 longest
  values of a batch (measuring all 100,000 took 46 ms).
- DESIGN §3.6 and §4.2 updated; the shortcut sheet's line too.

## Decisions (for Rob)

1. **Clipboard format: always TSV.** The tab-separated type if present,
   else plain text, both read as TSV: cells split by tab, rows by CRLF/LF/
   CR; a cell starting with `"` and closed by `"` before a tab, line
   break or the end is quoted (`""` → `"`, may hold tabs and line breaks);
   anything else is literal (so `"Hi" she said` stays as typed); one final
   line break dropped. **CSV is not detected**: a CSV line pastes as one
   cell, commas and all. Guessing would be wrong for text with commas.
2. **One value** fills every selected cell; **a block** goes in once from
   the selection's top-left cell (no tiling over a bigger selection), and
   is then selected. A short line of the text changes only its own cells.
3. **Past the last row or column: refused** with an alert ("The copied
   cells run past the last row. Paste them higher up, or insert rows
   first."), not extended. The last column is the grid's (`columnCount`),
   so a block may reach a short row's hatched cells but never beyond the
   widest row shown. Extending would need row inserts (structural).
4. **Refused while reading or saving** (`StillReading`, `Saving`, as for
   rows and columns: the row count isn't known yet, and a ⌘A selection
   runs to an unknown end), and while Reload replaces the document. Cell
   typing is still allowed then; Rob may want paste of one cell to be too.
5. **Hatched cells** (ADR-0005 decision 2, the open question for the
   gate): pasting `""`, or clearing, leaves a missing cell missing (no
   edit); clearing an edited hatched cell makes it missing again, so the
   row's bytes come back. Pasting a value pads the row as typing does.
6. **Refusal UI:** wait-it-out refusals (reading, saving) are the menu
   item's tooltip, a beep and a VoiceOver announcement, as for 2.5a's row
   commands. Others (doesn't fit, too many cells, too much text, after an
   unterminated quote) can't be shown before the clipboard is read, so an
   ordinary alert says why (existing `present`). No other new UI. Clear's
   too-many-cells is also its tooltip.
7. **Line breaks inside pasted values are kept as pasted** (an Excel
   multi-line cell's LF stays LF in a CRLF file); the saver quotes the
   value. The editors' typed line breaks use the file's ending instead.
8. **Limit: 100,000 cells and 32 MB** per paste or clear (a one-value
   paste counts value × cells). ⌘A then Delete on the reference file
   (12M cells) is refused at once ("Leal clears up to 100,000 cells at a
   time. To empty a whole column, delete it and insert an empty one.").
   No off-main-thread path: at the limit it costs ~25 ms (below).
9. **2.1's far columns** ("Left for later"): a paste can't go past the
   grid's last column, so it never pads a row further than the widest row
   already shown, and can't widen the grid through row 0. The first
   screen's and `Document::rows`' full-width rows are unchanged.

## Benchmarks

Core, reference file (`just bench`, `edits/…`, with 100,000 edited rows
in place; M-series, other agents running):

| Benchmark | Time |
|---|---|
| `edits/paste_100k_cells` (10,000 × 10 block + undo) | 44.3 ms |
| `edits/clear_100k_cells` (same cells + undo) | 38.8 ms |
| `edits/set_cells_10k` (unchanged code; was 2.72 ms in 2.1) | 3.89 ms |

App, Release, 10,000 × 10 file, whole main-thread call incl. undo
registration, journal and redraw bookkeeping (`PasteTests`, printed):
clear 100k cells **21.9 ms**, its undo **18.5 ms**, paste 100k **24.8 ms**.
Before `CellBatch` and the width change: 138 / 61 / 182 ms (FFI lifting
~115 ms, width measuring 46 ms).

## Manual checks for Rob (on screen)

1. Copy a 3×2 block in Numbers or Excel; click a cell in Leal, ⌘V: the
   block goes in from that cell and is selected. Edit > Undo says "Undo
   Paste"; undo and redo.
2. Copy one cell; select a range; ⌘V: every cell gets the value.
3. Select cells, press Delete (and Fn-Delete): they empty; "Undo Clear
   Cells". On a short row the hatched cells stay hatched.
4. Paste a block near the bottom or right edge: an alert says it runs
   past the last row/column; nothing changes.
5. ⌘A on a large file, Delete: Edit > Delete is off with the limit as
   its tooltip; the key shows the alert.
6. While a big file is still "Indexing…", or during a save: Paste and
   Delete are off with a tooltip; the keys beep.
7. In the in-cell editor and the find bar, ⌘V and Delete edit the text,
   not the cells.
8. Paste a multi-line cell from Numbers into a CRLF file, save, open in a
   text editor: only that field changed, quoted.

## Rust notes

- `Pasted<'a>` holds `Cow<'a, str>` cells: "copy on write". A cell is
  usually a *borrowed* slice of the clipboard text (no copy); only a
  quoted cell with `""` inside needs an *owned* `String`. The `'a` is a
  lifetime: it tells the compiler the cells can't outlive the text they
  borrow from (`edit/paste.rs`).
- `parse_tsv` returns `Result<Pasted, usize>`: `Err(count)` when there
  are too many cells, so the caller turns it into `TooManyCells` with
  `map_err` (`document/pasting.rs`, `pasted`).
- `paste` and `clear_cells` run inside `change_rows(|reading| …)`: a
  closure (an inline function) called while the document's writer lock
  is held, so they call `change_in` (which expects the lock held) rather
  than `change` (which takes it, and would wait on itself forever).
- `CellBatch` is a `uniffi::Object`: Swift gets a handle to a Rust value
  behind an `Arc` (a shared, reference-counted pointer), not a copy of
  its 100,000 values. `#[derive(PartialEq, Eq)]` lets `EditCommand` (a
  record compared by value) still compare equal.
- `longest` keeps each column's longest values in a `BTreeMap` (a sorted
  map) of small sorted `Vec`s, using `partition_point` (a binary search
  for where a value goes) and `truncate`.
