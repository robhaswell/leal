# 1.10 Viewer milestone

Every viewer budget in DESIGN §1 is now measured on the app as it ships,
and `just perf` measures them all again and prints the table. The results
are in [`docs/perf.md`](../perf.md). This Mac is not the reference machine,
and the screen was locked throughout, so the table is a lower bound on how
Leal does, not a verdict for a base M1 Air. Rob needs to rerun it (see
"For Rob").

Also done:

- **The plain index's chunks** (1.5 open question) were too long for rule 3
  on a base M1 Air and are now 256 KiB.
- **The 1.6a opportunity**: tiles that scrolling moves instead of AppKit
  redrawing the visible grid. They cut the median frame by about a third
  but gave ten times as many late frames, so they were not kept. The patch
  is in [`1.10-tiles.patch`](1.10-tiles.patch).

## Measuring as the app ships

PLAN 1.10 and the 1.6a notes ask for the app launched with `open`,
sandboxed, as it ships: a shell launch puts the main thread on other cores
at other clocks. Everything here does that.

- **Launch, open, index and memory** use the Release app, the one `just app
  release` builds, which `just check-no-bench` and `just
  check-no-test-exports` pass. It has no scripted runs, so it is measured
  from outside: its signposts through `log stream --signpost`, its memory
  through `heap -s` and `ps`.
- **Scrolling and opens in a running app** need the app to drive itself, so
  they use the bench build (`LEAL_BENCH`), Release configuration, also
  launched with `open`.
- No input is sent to the system. The runner finds the PID of the instance
  it launched (the one process of that app bundle that wasn't running
  before), and quits only that one: SIGTERM, then SIGKILL after 5 s, after
  checking the PID still belongs to the app. Leftover temporary folders are
  removed by the next launch, as after a crash (DESIGN §3.1).

Instruments was used headlessly (`xctrace record --template 'Time
Profiler' --all-processes`, then `xctrace symbolicate` and `export`) to
see where the cold open's 100 ms go, and `malloc_history` with
`MallocStackLogging=lite` for the heap. Neither is part of `just perf`:
signposts and `heap` give the same numbers without a trace.

## Results

See [`docs/perf.md`](../perf.md) for the table and its caveats.

Summary (M5 Pro, screen locked, 3 runs each; medians and ranges):

| Budget | Measured | Verdict here |
|---|---|---|
| Launch to empty window < 300 ms | 110 ms (92–195) | pass |
| Open to first rows < 150 ms | 95 ms cold (94–99); 36 ms in a running app | pass |
| Full index < 500 ms | 120 ms (119–131) | pass |
| Scrolling, no dropped frames at 120 Hz | 7–51 late of ~7,530 | **fail** |
| … while background work runs | 48–59 late of ~7,500 | **fail** |
| … stress, nothing pausing (1 GB file) | 2–3 late of ~7,555 | **fail** |
| Heap, reference file < 40 MB | 28 MB settled; 39–42 MB peak scrolling, 44–50 MB with a search | **fail** (peak) |
| Idle < 30 MB resident | 10.9 MB footprint (RSS 65–68 MB) | pass |

**The failing budgets, and why they aren't fixed here** (CLAUDE.md: a
missed budget is reported, not worked around):

- **Scrolling.** The main thread does 12.7 M instructions a frame, p99
  CPU 7.2–7.8 ms, and 55–73 frames a run take longer than 8.3 ms. Every
  run's main thread ran at 1.76–1.95 GHz, because the screen was locked
  and no app was frontmost. In the stress run, busy background threads
  pushed the clock to 4.25 GHz, and the same work took 0.7 ms a frame with
  2–3 late frames: 5.1 times the CPU time at 2.3 times less clock, about
  2.0 instructions a cycle against 4.3, so the locked screen's main thread
  was most likely on an efficiency core (an inference from the counters;
  review finding). An unlocked run with Leal in front should change that,
  but that isn't proven. What would cut the work itself
  is the 1.6a replay, about half of each frame; the one well-understood fix
  was tried and made dropped frames worse (below). There is no contained
  fix left for 1.10. The "while background work runs" runs are worse
  mainly because the find highlights add 1.7 M instructions a frame (14.4
  M against 12.7 M); the search runs on the background pool and pauses
  while the scroll counts as input.
- **Heap peak.** After opening the reference file the heap is 28 MB, but
  most of that is AppKit's and Core Animation's for the window: 21 MB with
  a two-row file, 2.5 MB with no window. The core's own share is the row
  index (3.8 MB, one allocation) and the diagnostics (about 1 MB), from
  `malloc_history`. While scrolling, the heap rises by 10–14 MB for a
  moment (the drawing's allocations: display lists, laid-out lines, cell
  tiles) and falls back to 26–32 MB. A running search adds 12 bytes per
  matching row (`Found.rows: Vec<u32>` and `ends: Vec<u64>`): 12 MB when,
  as here, every row matches, and 120 MB on the 1 GB file, whose runs
  peaked at 261 MB. The peaks aren't one thing with a contained fix, and
  whether the budget counts the frameworks' allocations for the window is
  a question for Rob (below).

The full table, details per run, and the cold open's breakdown (Time
Profiler) are in docs/perf.md. Raw numbers: `target/perf/perf-1790890416.json`
(not committed; `leal-perf --report` prints its table).

## The plain index's chunks (1.5 open question)

1.5 left open whether the plain index's 1 MiB chunks keep to rule 3 (DESIGN
§3.10: chunks of at most about 5 ms) on its worst file, blank lines, where
every byte is a row. The app indexes with diagnostics, in 256 KiB chunks,
but a copy job whose document's index stopped builds a plain index of its
own (`own_index`), and the CLI and tests use one.

Measured with a new line in the `worst` benchmark group: 8 chunks of blank
lines, the slower of two warm runs, three runs.

| Chunk | Longest chunk (M5 Pro) | At 2–3× slower (M1 Air estimate) |
|---|---|---|
| 1 MiB (before) | 3.57, 4.05, 3.70 ms | 7–12 ms: **over** |
| 256 KiB (after) | 0.95, 1.09, 0.94 ms | 2–3.3 ms |

So `CHUNK_BYTES` is now 256 KiB, the size the index with diagnostics
already used. Cost on the reference file: `index/run` 42.9 → 44.6 ms
(+3.8%, more publishing), `index/build` 41.6 → 40.7 ms. Both are far inside
the 500 ms budget. `DIAGNOSTICS_CHUNK_BYTES` stays a separate constant (it
has its own reason, and code names it), now equal to `CHUNK_BYTES`.
`source::STREAM_CHUNK_BYTES` stays 1 MiB: it is the read size from a
removable drive, which the index already takes in pieces of its own chunk
size; its doc no longer says the two are the same.

## The 1.6a opportunity: tiles

1.6a found that about half of each scroll frame is AppKit rebuilding the
whole visible content layer from the grid's recorded drawing, on every
scroll step, though only a strip of it is new. 1.6a had already ruled out
`prepareContent(in:)` overdraw (the content layer stays the size of the
visible rect), `layerContentsRedrawPolicy`, `drawsAsynchronously` on the
grid view, and 128 pt tile *subviews* (partly visible subviews redraw as
their visible part changes).

What was tried here is the well-understood alternative: **cached tiles in
layers that scrolling moves**, as `CATiledLayer` or a game's tile map
does, but positioned relative to the visible rect (a 40M-row grid is 880M
points tall, past where Core Animation's single-precision positions are
exact).

- A layer-hosting view over the clip view, under the scrollers, holds
  512 × 256 pt `CALayer` tiles, each with its own backing store, drawn by
  the grid's own drawing code (`GridView.drawContent`, the body of
  `draw(_:)`). `GridView` itself switched to `wantsUpdateLayer` with an
  empty `updateLayer`, so AppKit no longer records or replays it; it still
  draws for `cacheDisplay` (snapshots, tests).
- A scroll moves the tiles; a tile is drawn when it comes into view or when
  something in it changes (`setNeedsDisplay(_:)` and `needsDisplay` are
  passed on to the tiles under the rectangle).
- `-LealTiles NO` switched back to the 1.6 drawing in the same build, so
  each A/B pair ran the same binary back to back.

Variants, full `ScrollBench` fast profile, reference file, this Mac
(locked, 120 Hz built-in display), each against a `-LealTiles NO` run
straight before it:

| Variant | Late frames | Main-thread CPU p50 / p99 | Instructions a frame, mean / p99 |
|---|---:|---:|---:|
| No tiles (1.6 drawing), 7 runs | 2–33, median 3 | 3.3–3.6 / 7.0–7.6 ms | 12.9–13.2 M / 33–34 M |
| 512 × 256, drawn on the main thread | 156 | 2.2 / 10.0 ms | 14.8 M / 53 M |
| 256 × 128, main thread | 88 | 3.4 / 10.4 ms | 16.6 M / 66 M |
| 512 × 256, `drawsAsynchronously` | 38 | 2.4 / 7.9 ms | 10.0 M / 35 M |
| 512 × 256, async, a margin of one tile drawn ahead, 2 a frame | 13, 33, 28, 33 | 2.2–2.7 / 7.1–7.8 ms | 10.2 M / 36 M |
| … same, 4 a frame | 31 | 2.4 / 7.6 ms | 10.5 M / 37 M |
| … same, main thread, 2 a frame | 110 | 3.0 / 9.6 ms | 15.5 M / 61 M |

The best variant (async, margin drawn ahead two tiles a frame), three
rounds on the reference file and two on the 200-column file:

| | Reference: late frames | Reference: CPU p50 | 200 columns: late frames | Footprint peak |
|---|---|---|---|---|
| No tiles | 3, 2, 3 | 3.5 ms | 106, 50 | 232 MB |
| Tiles | 33, 28, 33 | 2.6 ms | 76, 61 | 415 MB |

**Not kept.** The tiles do what was hoped for the median: AppKit's replay is
gone, and a typical frame costs about a quarter fewer instructions and a
third less CPU. But the budget is dropped frames, and those got worse, ten
times worse on the reference file: a frame in which a row of new tiles
comes into view draws all of them at once, where the 1.6 drawing draws
only the strip that scrolled in. Drawing ahead spreads some of that but
not enough, and drawing more ahead costs more frames. The tiles also add
about 180 MB of graphics memory (footprint, not heap), and on a locked
screen WindowServer composites nothing, so the cost of compositing thirty
layers isn't even in these numbers.

The code is kept as [`1.10-tiles.patch`](1.10-tiles.patch) (against
`04a860d`; the bench options it reads, `-LealTiles`, `-LealTilesAsync`,
`-LealTileWidth`, `-LealTileHeight` and `-LealTilePrefetch`, are in it).
What would make it pay is spreading tile drawing evenly over frames,
which means predicting the scroll, or tiles small enough that one row of
them costs no more than a strip, which the 256 × 128 run shows costs more
in per-tile overhead than it saves. That is a design question for ADR-0001
(fallback C has the same replay), not a 1.10 fix.

## Decisions and deviations

- **"Launch to empty window"**: Leal opens no empty window
  (`applicationShouldOpenUntitledFile` is false, 1.6), so the budget is
  measured to the end of `applicationDidFinishLaunching`, when the app can
  take File ▸ Open. Launch with a file to its first rows is reported
  beside it.
- **"Open to first rows"** is measured two ways: the app launched with the
  file (the process's first window, AppKit's first text layout and the
  window's SwiftUI title bar included) and opening it again in a running
  app. The first is the one the table judges.
- **"Idle < 30 MB resident"** is judged on the physical footprint (Activity
  Monitor's Memory). The resident size (RSS) is reported too, but counts
  pages of shared system libraries every app maps, so it is over 30 MB for
  any AppKit app: 66–68 MB here.
- **Heap**: `heap -s`'s total for all malloc zones. That includes what
  AppKit and Core Animation allocate for Leal's window, about 19 MB with a
  two-row file, against 2.5 MB with no window. See "Results".
- **Scrolling while background work runs** is measured two ways: as real
  scrolling has it (P2 work pauses, the search stays in flight and its
  highlights are drawn), and the stress case with nothing pausing. The
  reference file's index finishes 20–35 ms after the first rows, too soon
  to scroll during it; the 1 GB variant gives about 140 frames of that.
- **Signposts in the shipped app** are new product code (DESIGN §3.10 asks
  for them). They cost a flag check unless something records them.
- **New dependencies:** none. `leal-perf` uses `serde_json`, already a
  dependency of `leal-bench`, and only tools that ship with macOS (`open`,
  `log`, `heap`, `ps`, `pgrep`, `caffeinate`, `pmset`, `ioreg`,
  `system_profiler`, `sysctl`).

## Open questions

- **Is the scrolling budget met on Rob's Mac, unlocked, and on an M1
  Air?** Nothing measured here can say: the screen was locked and the
  main thread ran at under 2 GHz. If it still drops frames unlocked, the
  next step is ADR-0001's: the 1.6a replay is half of every frame, and
  moving tiles (below) traded it for lumpier frames.
- **What does the heap budget count?** All malloc zones (as measured here:
  28 MB settled, peaks to 42 MB, 50 MB with a search), or Leal's own
  allocations (the core's index and diagnostics, about 5 MB, plus the
  app's caches)? With every zone counted, about 21 MB goes to any window
  AppKit draws.
- **A search's memory scales with its matching rows** (12 bytes each). On
  the 1 GB file a search for something in every row holds 120 MB. Should
  find store matches more compactly (a bitmap of rows, `u32` counts), or
  is that fine outside the reference file's budget? Not changed here: it
  is 1.8's design.
- **Which open counts for "open to first rows"**: the cold open (95 ms
  here, with the process's first window, of which AppKit's window and its
  SwiftUI title bar are most) or opening in a running app (36 ms)? On an
  Air the cold open is likely over 150 ms.
- **Idle "resident"**: judged here on the footprint (10.9 MB). RSS is
  65–68 MB, mostly shared system libraries; no AppKit app is under 30 MB
  by RSS.

## Rust notes

- **A binary that drives other programs** (`leal-perf.rs`).
  `std::process::Command` runs `open`, `heap`, `ps` and the rest and reads
  their output; `Command::spawn` starts `log stream` without waiting, and
  its `stdout` is a pipe read on a thread. Nothing here needs `unsafe`: the
  process ids and clocks come from those tools, not from system calls.
- **Sharing between threads** (`LogStream`). The reader thread pushes each
  signpost into an `Arc<Mutex<Vec<Signpost>>>`: `Arc` lets both threads
  own the vector, and the `Mutex` lets only one touch it at a time.
  `unwrap_or_else(PoisonError::into_inner)` carries on if the other thread
  panicked while holding the lock, instead of panicking too. A `mpsc`
  channel tells the main thread the stream has started.
- **`Drop`** (`impl Drop for LogStream`). When the `LogStream` goes out of
  scope, `drop` kills the `log stream` child, so it can't be left running
  whatever path the function returns by.
- **Closures that return `Result`** (`launch_run`). `(|| { …; Ok(m) })()`
  runs a block in which `?` works, so the app is always quitted afterwards,
  whether the block succeeded or not.
- **`f64::total_cmp`** (`Spread::of`). Floats have no total order (`NaN`),
  so `sort` needs a comparison that gives one; `total_cmp` is the standard
  library's.
- **`is_multiple_of`**, **`div_euclid`** (`thousands`,
  `days_from_civil`): `div_euclid` rounds towards negative infinity, which
  the calendar arithmetic needs for dates before 1970.
