# 0.4 Grid spike

Throwaway spike that decides the grid technology (ADR-0001). The code is in
`spikes/grid-spike/`. It is kept until task 1.6 lands, so the comparison can
be rerun, and 1.6 then deletes it. It stays available at the `phase-0` tag.
Raw numbers are in `docs/tasks/0.4-results.md`, moved out of the spike folder
so they outlive it.

## What was built

A standalone macOS app (`GridSpike.app`, XcodeGen, Swift 5 mode, no Rust)
with one synthetic data source and four grid variants that render the same
ADR-0002 mockup spec. They are selected with
`--impl table|table-lite|table-rowdraw|custom`: A, A-lite, C and B.

- **Data** (`Sources/Model.swift`): 1,000,000 rows × 12, 50 or 200 columns.
  Cell text is generated on demand from a hash of (row, column), with no big
  arrays: order IDs, dates, customer names, emails, country codes, SKUs,
  product names, right-aligned quantities, prices and totals, currencies, and
  notes that are mostly empty, sometimes short, and occasionally about 200
  characters. Columns beyond 12 repeat the 12 kinds with fresh values
  (`order_id_2`, …).
- **Per-cell styling, on in every measured run** (ADR-0002): active-cell
  2 px ring with its row number highlighted in the gutter, alternate row
  shading, right-aligned numbers, an edited-cell corner triangle on about 1
  cell in 150, hatched empty cells for ragged rows (1 row in 40 is missing
  1–6 trailing fields) with an orange diagnostic dot in the gutter,
  find-match highlights for "marlow" (a real substring search of every drawn
  cell, with the current match drawn stronger), and one in-cell editor open on
  row 9 "customer" (as in mockup 05b).
- **A: view-based `NSTableView`** (`Sources/TableGrid.swift`): one
  `NSTableColumn` per CSV column, cell views reused with
  `makeView(withIdentifier:)`, a native sticky header, native alternating
  rows and vertical grid lines. Cells are `NSTableCellView` + `NSTextField`,
  the standard pattern, which gives VoiceOver its text for free. Ring,
  triangle and hatching are drawn by an overlay view that exists only on
  decorated cells. Find matches use an attributed string.
- **A-lite** (`--impl table-lite`): the same table, but each cell is one
  `NSTableCellView` that draws its own text with the same Core Text code as B
  (no `NSTextField`). Each row view (`ShadeRowView`) draws the shading and
  grid lines and flattens its cells into one layer with
  `canDrawSubviewsIntoLayer`: 166 layers at 12 columns instead of 1,772. The
  cells must not set `wantsLayer` themselves, or they opt out of flattening.
  The first version of the spike made that mistake, so its A-lite was
  unflattened; see *Review corrections*. The editing cell still uses the
  `NSTextField` cell.
- **C** (`--impl table-rowdraw`): an `NSTableView` with no cell views. Each
  row view (`RowDrawView`) draws the row's visible cells itself, with the
  same code as B's grid. NSTableView still virtualises rows and provides the
  header, the columns and the row machinery. `viewFor` returns nil except
  for the cell being edited, which gets a real `NSTextField` cell view. The
  reviewer wrote this variant, and it was brought into the spike unchanged
  apart from naming.
- **B: custom grid** (`Sources/CustomGrid.swift`): an `NSScrollView` whose
  document view is sized to the whole table (1M × 22 pt tall) and whose
  `draw(_:)` draws only the cells inside the dirty rect with Core Text.
  AppKit scrolls the existing pixels and asks only for the newly exposed
  strip. There is a separate header view and gutter that follow the scroll
  offset. The **in-cell editor** is an `NSTextField` added as a subview of the
  document view at the cell's rect, so it scrolls with the content and gets
  the standard field editor (undo, input methods, spelling). Return commits
  through `control(_:textView:doCommandBy:)`, and Esc cancels.
- **Shared** (`Sources/Draw.swift`): Core Text drawing with tail truncation,
  decorations, and the row-number gutter, which both A and B use unchanged.
  Column widths are auto-sized from the first 1,000 rows with a 260 pt
  maximum (ADR-0002 q2), the same for all variants.
- **Measurement harness** (`Sources/Bench.swift`, `bench.sh`,
  `aggregate.py`, `memprobe.sh`, `tracesummary.py`).

Snapshots of the first screen for A, A-lite, C and B at 12 columns
(`runs/snap-*.png`, not committed; regenerate with `./bench.sh snap`)
match mockups 01a/03a/04a/05b: gutter, sticky header, auto-sized columns,
right-aligned numbers, shading, ring, triangle, hatching, find highlight and
the open editor.

## How the measurement works

- **Scripted scrolling, driven from inside the app.** A display link
  (`NSView.displayLink(target:selector:)`, macOS 14+, preferred rate 120 Hz)
  advances the clip view each frame (`NSClipView.scroll(to:)` +
  `reflectScrolledClipView`). There is no synthetic system input. The
  sequence is:
  1. **Vertical flings**, half the fling rows at x = 0. Each fling starts at
     the chosen speed and decays exponentially (τ = 0.5 s), like trackpad
     momentum. A new fling starts when the speed falls below 1/30 of the
     start speed.
  2. **Horizontal flings** to the right-hand end (a quarter of the speed).
  3. **Vertical flings** for the other half, while scrolled fully right.
  4. **Horizontal flings** back to x = 0.
  5. **A jump to the end**, then back to the top.
  6. **An edit**: open the in-cell editor, set the text, and press Return
     through the field editor's `doCommand(by: insertNewline:)`, which is the
     same path a key press takes. The run then checks that the edit landed
     and measures commit plus redraw.
- **Two speed profiles:** *fast* = 60,000 pt/s flings over 50,000 rows (at
  its peak about 23 rows, most of a screen, change per frame); *moderate* =
  15,000 pt/s over 10,000 rows (about 6 rows per frame at the peak).
- **Frame timing:** the interval between display-link callbacks (vsync
  timestamps, so exact multiples of 8.33 ms at 120 Hz). If the main thread
  takes longer than one refresh, callbacks are skipped and the interval
  grows. The results report p50/p95/p99, frames that missed at least one
  refresh ("> 8.3 ms", i.e. an interval of at least 16.7 ms) and frames that
  missed two or more ("> 16.7 ms").
- **Main-thread busy time per frame** (frame wall time minus run-loop sleep,
  measured with run-loop observers). It covers layout, drawing and the Core
  Animation commit, and shows headroom, which matters for extrapolating to
  slower Macs.
- **Memory:** `phys_footprint` from `task_info` in-app (the number
  `footprint(1)` prints; cross-checked with `footprint` and `vmmap --summary`
  in `memprobe.sh`), plus malloc bytes in use (`malloc_zone_statistics`),
  which is the "Leal's own heap" of the DESIGN §1 budget without graphics
  surfaces. Sampled 1 s after first paint, every 15 frames during the scroll
  (peak), and 1 s after scrolling.
- **Time to first display:** process start (from `kinfo_proc`) to the first
  display-link callback after the grid has drawn, with the column auto-size
  time reported separately.
- **Runs:** 3 of each (variant × width × profile), interleaved so drift
  affects every variant equally. Tables report medians.

## Review corrections

An adversarial review of the first version found real mistakes. Its
recommendation (custom-drawn cells) survived, but its central argument didn't.

- **The flattening test was broken.** The old `--flatten` set `wantsLayer` on
  each cell view, and `LiteCell` always did. Either one opts a view out of its
  row's `canDrawSubviewsIntoLayer`. So "flattening made no difference" and
  "this isn't a tuning problem" were wrong.
  - NSTextField cells do keep their own layers.
  - Self-drawing cells flatten fine: 960 layers drop to 166 at 12 columns.
  - Flattened A-lite meets the budget at 12 columns and fails as columns
    grow.
  - `--flatten` is removed, and `--impl table-lite` is now the correctly
    flattened version.
- **Variant C (row-drawing NSTableView) was missing.** It is the strongest
  NSTableView design, and the fallback in ADR-0001. The reviewer wrote it,
  and it is now `--impl table-rowdraw`.
- **The display link can stall on a locked Mac.** The display turns off after
  about a minute even with `caffeinate -d`. The first attempt at the re-run
  stalled on its second run (1.5 s of CPU in 76 s). `bench.sh` now keeps
  refreshing `caffeinate -u` for the whole run (a power assertion, not
  input). The app counts display-link gaps over 0.5 s (`displayLinkStalls`),
  and `aggregate.py` leaves any stalled run out of the medians.
- **The numbers move between sessions.** For example, A at 12 columns was 77%
  late in the first session and 34% in a single run of the second. The
  comparison is fair within a session, because variants are interleaved. But
  absolute numbers from different sessions should not be mixed, so every
  table in ADR-0001 now comes from the second session only.

## Rerunning

Once task 1.6 has deleted the spike, check it out from the `phase-0` tag
first (`git worktree add /tmp/grid-spike phase-0`) and work in
`/tmp/grid-spike/spikes/grid-spike`. `bench.sh` needs `timeout`, which
macOS doesn't ship (`brew install coreutils`). A new `./bench.sh run` writes
`results.md` in the spike folder; copy it over `docs/tasks/0.4-results.md`
only if ADR-0001's numbers are being replaced.

```sh
cd spikes/grid-spike
./build.sh                 # xcodegen + xcodebuild Release -> build/GridSpike.app
./bench.sh compare         # headline check: A, C and B at 200 columns, about 3 minutes
./bench.sh snap            # first-screen and last-rows snapshots into runs/
./bench.sh run 3           # full matrix, about 2 hours; writes results.md
./bench.sh one custom 200 --fling-rows 10000        # one run, JSON to stdout
./memprobe.sh table 200 --fling-rows 10000          # footprint + vmmap cross-check
xctrace record --template 'Time Profiler' --output traces/x.trace --launch -- \
  build/GridSpike.app/Contents/MacOS/GridSpike --impl table --cols 200 --bench --fling-rows 3000
python3 tracesummary.py traces/x.trace 30            # main-thread hot spots
```

Useful flags: `--impl table|table-lite|table-rowdraw|custom`,
`--clamp-prepare` (table variants: clamp NSTableView's overdraw to the visible
rect), `--no-overdraw` (B: the same for the grid), `--cols N`, `--speed PT_PER_S`,
`--fling-rows N`, `--no-styling`, `--no-editor`, `--dark`, `--screen N`,
`--rows N`, `--snapshot PATH`, `--snapshot-end PATH`, and `--hold` (stay
open after the bench, for `footprint`).

## Environment

- MacBook Pro `Mac17,8`, Apple M5 Pro (20-core GPU), 48 GB, macOS 27.0
  (26A428), Xcode 27.0 (27A266a), XcodeGen 2.46.0.
- The window was on the built-in Liquid Retina XDR display (ProMotion,
  `NSScreen.maximumFramesPerSecond` = 120; the measured display-link frame
  duration was 8.33 ms). The external DELL U2515H runs at 60 Hz and was not
  used. `system_profiler` doesn't print the built-in panel's refresh rate,
  so the rate comes from `NSScreen` and the display link.
- Window 1200 × 780 pt at 2×, light appearance forced to match mockup 01a.
  The system is in dark mode; appearance doesn't change the cost.

## Results (headline; the full tables are in ADR-0001 and `0.4-results.md`)

Second session (after review), fast profile, medians of 3 runs. 72 runs in
total, none stalled. Each cell shows late frames / main-thread p50–p99 /
heap after scrolling:

| | 12 cols | 50 cols | 200 cols |
|---|---|---|---|
| **A** | 35% / 9.8–24.9 ms / 28 MB | 99% / 30–68 ms / 60 MB | 100% / 174–295 ms / 181 MB |
| **A-lite** (flattened) | 0.05% / 5.2–8.2 ms / 17 MB | 15% / 6.5–22 ms / 22 MB | 74% / 16–75 ms / 39 MB |
| **C** (row-drawing) | 0.04% / 4.9–6.7 ms / 16 MB | 0.05% / 4.6–6.7 ms / 16 MB | 1.9% / 5.4–12.0 ms / 17 MB |
| **B** (custom) | 0.03% / 2.5–4.5 ms / 15 MB | 0.03% / 2.4–4.4 ms / 15 MB | 0.02% / 2.5–4.5 ms / 15 MB |

In the moderate profile, C at 200 columns is 12% late (main-thread p99
14.8 ms), and B is 0.04% (6.4 ms). C's misses are in horizontal scrolling:
each row view redraws its own strip, with horizontal p99 of 13–16 ms at 200
columns. They agree with the reviewer's independent runs: C 1.2% late at 5.1–11
ms, and B 0.0% at 2.5–5.6 ms.

## Other findings

- **NSTableView builds views for all columns of each visible row.** At 200
  columns it created 7,601 cell views. This still happens with its overdraw
  clamped to the visible rect (`--clamp-prepare`; the reviewer's check). It
  is the root cause of the wide-file problem that DESIGN §2 flagged: the cost
  is per cell view, and grows with the column count. NSTableView's
  `preparedContentRect` spans the whole table width (23,560 pt at 200
  columns), against B's empty one (0 × 0: B has no overdraw).
- **Precision at large offsets is fine.** `--snapshot-end` at 1M rows
  (22M pt) and 40M rows (880M pt, about the 4 GiB limit): rows, gutter, ring
  and editor line up in B and A, and in A-lite and C at 1M.
- **A's translucent header.** Since macOS 11, NSTableView content scrolls
  under a translucent header, so a row shows faintly through it. The mockups
  draw an opaque header, so A would need that turned off.
- **Harness bug found and fixed after the matrix.** A's gutter followed
  `table.visibleRect`, which includes the area under the translucent header.
  So away from the top of the file its row numbers were drawn about 28 pt
  (one header height) out of line. It now maps the gutter's top edge into the
  table. The gutter draws the same number of rows either way, so the timings
  are unaffected. B was never affected.
- **Memory probes, second session** (`memprobe.sh`, 10,000-row fast scroll,
  footprint a few seconds after scrolling):

  | | Settled footprint | Dirty IOSurface | Malloc Small (dirty) |
  |---|---:|---:|---:|
  | B 12 | 86 MB | 27 MB | 29 MB |
  | B 200 | 88 MB | 27 MB | 29 MB |
  | C 12 | 84 MB | 2.5 MB | 22 MB |
  | C 200 | 80 MB | 2.2 MB | 24 MB |
  | A 12 | 69 MB | 2.5 MB | 36 MB |

  First session, for A at 200 columns: 257 MB settled, 218 MB of it malloc.

  **Why B's footprint is higher than A's at 12 columns.** B draws into one
  window-sized layer, whose pixels live in shared graphics buffers
  (IOSurfaces): 27 MB, against about 2.5 MB for A and C. One full-window
  bitmap of the grid area at 2× is 1117 × 728 pt × 4 px × 4 bytes ≈ 13 MB.
  So 27 MB is consistent with two of them (one on screen, one being drawn).
  A and C hold their pixels in many small per-view or per-row buffers
  instead. The higher figure just after scrolling (B 208 MB, A 157 MB, C
  159 MB) is Core Animation's pool of recycled buffers, mostly reclaimable
  once idle. It is larger for B because B recycles larger buffers. This
  explanation fits the `vmmap` numbers, but I didn't prove it further.
- **Time Profiler**, first session (summarised by `tracesummary.py`; traces
  not committed):
  - **A, 12 columns:** 85% of main-thread time is in the CA commit (per-view
    backing stores: `CABackingStoreUpdate_`, `CA::Render::Shmem::new_bitmap`).
    NSTextField layout and `updateLayer` take about 7%. Our `viewFor` and
    `configure` take 2.1%.
  - **B, 200 columns:** 86% is in the CA commit, of which our drawing is
    `GridView.draw` 22%, `GutterView.draw` 8% and `HeaderView.draw` 2.5%.
    `CTLineCreateWithAttributedString` is 20%, the first thing to cache
    in 1.6.
- **Column auto-size from 1,000 rows** is 35 / 135 / 540 ms at 12 / 50 / 200
  columns, the same for every option. At 200 columns it alone breaks the
  first-paint budget, so 1.6 must size from the first screen at P0.

## Caveats

- **Faster Mac than the reference.** This is an M5 Pro, not a base M1 Air
  (DESIGN §1). Per-core speed is roughly double (an estimate). That is what
  separates B from C: C's 12–15 ms p99 at 200 columns is already over
  budget here. B's 4.5–6.4 ms would be about 9–13 ms on an M1 Air, near or
  over the limit in the fastest flings, so PLAN 1.6 must re-measure there
  and cut per-frame work (cached text lines, a cheaper gutter).
- **Background load:** median load average 4.2 (2.5–24.8; the peak was
  Spotlight indexing the fresh build). The top processes are logged before
  each run.
- **The screen was locked for every run.** `CGSessionCopyCurrentDictionary`
  reported `CGSSessionScreenIsLocked = 1`, with loginwindow shield windows
  on top, and `occlusionState` never reported the window visible. AppKit
  still laid out, drew and committed every frame, and the display link ran
  at 120 Hz while the display was kept on (`caffeinate -u`): about 7,500
  callbacks in 63 s, and one draw call per frame in B. So the main-thread
  cost is real, but WindowServer was not compositing the window:
  - GPU and compositor hitches are not measured. An *Animation Hitches*
    trace would be meaningless, so none was taken; *Time Profiler* traces
    were taken instead.
  - The surface-pool memory may be inflated.
  - `screencapture -l` failed ("could not create image from window", no
    screen-recording permission). Snapshots are rendered from the window's
    own layer tree (`CALayer.render(in:)`). These show the drawn content but
    not the compositor's view, and the window background shows as black
    around the status bar.
- **Programmatic scrolling.** Scrolling goes through `NSClipView.scroll(to:)`
  on the main thread, per the no-synthetic-input rule. Real trackpad
  scrolling uses AppKit's responsive scrolling with pre-drawn overdraw, which
  can mask some of A's late frames as briefly stale rows. It doesn't remove
  the work.
- **The fling integrator caps a frame's time step at 50 ms**, so when A's
  frames take 100–300 ms it scrolls less per frame than real momentum
  would. This flatters A.
- **Synthetic data in Swift.** FFI calls to the Rust core will add the same
  per-row cost to every option.
- **The busy-time metric** was redefined partway through development, to
  wall time minus run-loop sleep, after the first version double-counted.
  Every run in `0.4-results.md` uses the final definition.

## Deviations

- **Added A-lite** (self-drawing, flattened NSTableView cells) and **C**
  (row-drawing NSTableView), so the NSTableView route was judged on its
  strongest forms, not only on the heaviest one.
- **ADR-0001 is accepted.** Rob accepted B with C as the fallback, and the
  re-measured numbers still support it.
- **No Animation Hitches trace**, because the screen was locked (above).
- **The spike's `.gitignore`** excludes `build/`, the generated
  `*.xcodeproj`, `runs/` (JSON and snapshots) and `traces/`.
- **Only `spikes/grid-spike/`, ADR-0001, these notes and the 0.4 line of
  PLAN were touched.** No Rust changed, and `just check` passes.
