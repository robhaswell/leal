# 1.2b Reference file and CI benchmarks

## What was built

A new crate, **`crates/leal-bench`**, holds everything benchmark-related. It
is never shipped and nothing depends on it. Keeping it out of `leal-core`
means 1.1 (`source`) and 1.2 (detection), running in parallel, touch none
of the same files. Their only shared files are `Cargo.lock` and `docs/PLAN.md`.

| Path | What it is |
|---|---|
| `src/reference.rs` | The reference file generator, its constants (`ROWS`, `SEED`, `VERSION`, `HEADER`) and `ensure()`, which benchmarks call to get the file. |
| `src/bin/leal-refgen.rs` | The command-line tool that writes the file. `just reference-file` runs it. |
| `reference.sha256` | The SHA-256 of the default file, which `just reference-file` checks. |
| `benches/baseline.rs` | The speed-of-light baseline benchmarks. |
| `benches/common/mod.rs` | Shared set-up for the benchmark files: `reference_file()`, `whole_file()` (sampling settings for large inputs) and `canary()` (a group's noise canary; see "Group canaries and a third attempt"). |
| `src/budgets.rs` | The DESIGN §1 budgets that CI enforces. Empty until 1.3. |
| `src/report.rs`, `src/bin/bench-report.rs` | Read criterion's JSON results and print the report: pass, fail (budgets, regressions on every attempt), rerun (a noisy run or a regression; then, for a regression both attempts showed with one noisy for it, a third attempt of its group), or inconclusive (warns, passes). |
| `tests/reference.rs`, `tests/report.rs` | Tests for the generator and the report. |

Outside the crate:

- `justfile`: `bench` now runs only `leal-bench` and passes arguments to
  criterion. There are new `reference-file` and `bench-compare` recipes.
- `.github/workflows/bench.yml`: the CI benchmark job.
- DESIGN §7 lists the new crate.

### Adding a benchmark (1.3, 1.3a and later)

1. Add `crates/leal-bench/benches/<name>.rs`, and a `[[bench]]` entry with
   `harness = false` in `crates/leal-bench/Cargo.toml`. Add the crate being
   measured (for example `leal-core.workspace = true`) to its
   `[dev-dependencies]`. Benchmarks use only that crate's public API.
2. Start the file with `mod common;`, get the file with
   `common::reference_file()`, and call `common::whole_file(&mut group, len)`
   on any group that processes the whole file. Call
   `common::canary(c, "<group>", Side::Before)` just before each group and
   `common::canary(c, "<group>", Side::After)` just after its `finish()`
   (`tests/report.rs` checks that every group has both).
3. If the benchmark measures a DESIGN §1 budget, add a `Budget` to
   `src/budgets.rs` with its criterion id (`group/name`). CI then fails if
   the median goes over the budget, or if the benchmark stops running.
4. Put the result in your task notes, next to the baseline below.

## The reference file

`just reference-file` writes `target/bench-data/reference-v1.csv` (in
`target/`, which git ignores) in about 0.2 s and checks it against
`reference.sha256`. Benchmarks generate it themselves if it is missing, so
`just bench` also works from a clean checkout. Nothing is cached anywhere
else, and the file is never committed.

- **Shape (DESIGN §1):** a header and 1,000,000 rows × 12 columns, UTF-8,
  **99,954,047 bytes** (100.0 MB). 1,044,952 LF bytes and 2,534,598 quote
  bytes in all.
- **Contents:** an order export (`id,order_date,customer,city,country,sku,
  quantity,unit_price,currency,discount,status,notes`). The column table
  is in `src/reference.rs`. Names and cities are often non-ASCII (`Nguyễn`,
  `東京`, `Αθήνα`), and 74% of rows have some non-ASCII text. `customer` is
  always quoted (`"Surname, Given"`). 29,898 rows (3%) have a `notes` field
  with one or two newlines inside quotes, 5% have escaped quotes (`""`),
  and 8% have a comma in `notes`. Python's `csv` module, in strict mode,
  reads the file as 1,000,000 records of 12 fields, which independently
  checks the generator's quoting.
- **Regular on purpose:** LF line endings, no BOM, no CR, every row has 12
  fields, and fields are quoted exactly when they need it. The reference
  file measures the common path. Messy input is the corpus's job.
- **Reproducible:** the output depends only on the row count and the seed.
  The random numbers come from SplitMix64, written out in about 10 lines,
  not from a library whose output could change between versions. There is
  no floating point: prices are formatted from integer cents. Fewer rows
  give a prefix of the same file.
- **Pinned three ways:** a test pins the FNV-1a hash of the first 10,000
  rows, so `just check` catches any change to the output. `reference.sha256`
  pins the full file, and CI checks it on GitHub's runner, so the output is
  the same on a different machine. And `reference::VERSION` is part of the
  file name. If the output changes on purpose, bump `VERSION`, update both
  hashes, and say so in the task notes: earlier numbers then measured a
  different file.
- **Variants:** PLAN asks for none. `leal-refgen --rows N --seed S` writes
  others, for example `--rows 10000000` gives about 1 GB, for the "usable
  up to 1 GB" goal.

## Baseline (speed of light)

Machine: **`Mac17,8`** (`sysctl hw.model`), Apple M5 Pro, 18 cores (6
performance and 12 efficiency), 48 GB, macOS 27.0. This is the development
Mac, **not** the reference machine (a base M1 Air), which is slower. Expect
higher numbers there.

| Benchmark | Median | Throughput |
|---|---|---|
| Generate the file (`leal-refgen`, release) | 0.21–0.24 s | — |
| `baseline/sequential_read`: `File::read` into a 1 MiB buffer, page cache warm | 4.16 ms | 22.4 GiB/s |
| `baseline/memchr3_scan`: count `"`, CR and LF with `memchr3_iter`, file in memory | 30.1 ms | 3.09 GiB/s |

Three runs on the same day were within 8% of each other (sequential read
4.16–4.49 ms, scan 30.1–31.2 ms).

What these mean for later tasks:

- **No reader or indexer can beat these numbers.** The 1.3 row index
  (budget: 500 ms) has to look at every quote and line ending, so 30 ms is
  its floor on this Mac. That leaves about 16× headroom here, and less on
  an M1 Air.
- **The scan is limited by how often it finds a byte, not by memory
  bandwidth.** There are 3.6M matches, one every 28 bytes. `memchr3_iter`
  costs about 8 ns per match, which is why it runs at 3 GiB/s while reading
  runs at 22 GiB/s. An indexer that classifies 16 or 64 bytes at a time
  into bitmasks (the simdjson approach) could go faster than this "floor".
  So the floor is a practical one, for "find each special byte" designs.
- **Reads are from the page cache.** Criterion's warm-up reads the file
  first. That is the case for a file the user has just opened or saved. A
  cold read from disk needs `sudo purge` between iterations, so it isn't
  measured.
- The medians come from `target/criterion/baseline/*/new/estimates.json`.
  Criterion's own console line shows the mean, which can be slightly
  different.

### Rerunning

```sh
just reference-file          # generate and check the file (optional; benches do it)
just bench                   # every benchmark, results in target/criterion/
just bench baseline/         # only these; the argument is a criterion filter
just bench-compare main      # this checkout against main, as CI does it
```

Close other heavy apps first. The Mac doesn't need to be unlocked: these
benchmarks don't draw anything.

## CI: what runs, what gates, what only reports

**Decision: CI runs the benchmarks on each push to `main` that changes
code (`.github/workflows/bench.yml`). The job fails on three things:**

- **a DESIGN §1 budget,** whatever the noise;
- **a regression against the previous commit, measured on the same
  runner, on every attempt:** the whole 95% interval of the median's change
  is above +20% on the first attempt and on the rerun, and, if either was
  noisy for that benchmark, on a third attempt of its group too (see "A
  regression must repeat" and "Group canaries and a third attempt" below).
  With no rerun, the one attempt must be quiet: no noise canary moved by
  more than 10%;
- **broken comparisons:** the base commit's benchmarks fail, or a manual
  run names a base that isn't a commit.

**A run that is noisy twice (a canary moved by more than 10%, and again
on the one automatic rerun) doesn't fail: it is *inconclusive*.** The job
prints a `::warning::`, heads the job summary "Benchmarks: inconclusive",
and passes. Budgets were still checked. (Until the fix after 79fa5af,
being noisy twice failed the job; see "Noise canaries" below.)

**Everything else is only reported: a table in the job summary, plus
criterion's JSON as an artifact kept for 90 days.**

The problem is that a GitHub-hosted macOS runner is a shared VM: an
M1-class guest with 3 cores. It isn't the reference machine, and two jobs
can land on hosts that differ by 10–30%. So the job never compares numbers
from different runs. It only uses comparisons that survive that noise:

1. **Budgets are absolute, with no allowance.** A budget is a requirement
   (DESIGN §1: "these budgets are checked by benchmarks in CI (core)"), and
   DESIGN §3.10 asks for a CI benchmark that asserts first paint stays
   under 150 ms. The runner is roughly as fast as a base M1 Air, so a
   result near its budget on CI is near it on the reference machine too.
   That is worth hearing about even if noise put it over. A result well
   under budget never flakes. A budgeted benchmark with no result fails
   as well, so a renamed or deleted benchmark can't silently drop its
   gate. A noisy run doesn't excuse a budget failure. `budgets.rs` is
   empty until 1.3 adds the index (500 ms) and 1.3a adds first paint
   (150 ms).
2. **Regressions are A/B on one runner, judged by the confidence
   interval.** `just bench-compare <base>` extracts the base commit with
   `git archive`, then builds and benchmarks it and this checkout on the
   same VM, one after the other: base first on attempt 1, this checkout
   (head) first on the rerun (see "The rerun swaps the order" below). The
   side that runs first saves its results as a criterion baseline
   (`--save-baseline base`), and criterion compares the second side with
   it (`--baseline-lenient base`). It writes the median's change with a
   95% confidence interval
   (`change/estimates.json`). A benchmark has regressed when the interval's
   **lower bound** is above **+20%**: criterion is 95% sure it got more than
   20% slower. A single noisy median can't fail the job this way, but a
   real, large slowdown always does. CI's base is `github.event.before`,
   the tip of `main` before the push, so a task that lands as several
   commits is compared as a whole. A failure gets an `::error::`
   annotation, and GitHub emails the pusher.
3. **`memchr3_scan` is the noise canary, with a tighter 10% threshold.**
   Its code is the same on both sides of every comparison, so any change
   in it comes from the machine, not Leal. Each side runs the baseline
   twice: as `baseline/…` with the other benchmarks, then again as
   `baseline-late/…` after all of them, so noise that starts part-way
   through a run is caught too. The canaries are
   `baseline/memchr3_scan` and `baseline-late/memchr3_scan`
   (`report::CANARIES`). If either's median moves by more than 10% either
   way, the run is noisy, and `bench-compare` reruns both sides once. A
   regression on the first attempt is rerun too, noisy or not. If the
   rerun's run is noisy, the run is inconclusive: a warning, not a
   failure (above), unless a regression fails on every attempt. Since
   run 37069372104, each bench group also has canaries of its own, which
   judge whether an attempt was noisy for that group's benchmarks; a
   regression on an attempt noisy for it shows as "regression? (noisy for
   it)" (see "Group canaries and a third attempt" below). Noise is caught
   at 10%, regressions at 20%, so noise big enough to fake a regression is
   flagged first.
   `sequential_read` is still run and reported, as "info (not gated)": it
   is no canary, has no budget, and can't regress.

### Noise canaries: why `sequential_read` isn't one

At first both baseline benchmarks were canaries, and a run that was noisy
twice failed the job. On main at 79fa5af, the job failed though nothing
had regressed: `index/build` and `index/run` moved by ±4%, far inside
their 500 ms budget. It failed because `baseline/sequential_read` moved
+10.2% on the first attempt and `baseline-late/sequential_read` +15.7% on
the rerun. Meanwhile `memchr3_scan` stayed within about 6% on both.

- **`sequential_read` is a poor canary on a shared runner.** It takes
  only about 7 ms there, and it measures the page cache and the VM's I/O
  path, which other tenants on the host share. A short benchmark that
  depends on shared I/O moves by more than 10% with no code change.
- **`memchr3_scan` is a good one.** It is CPU-bound, works on a buffer
  already in memory, and takes about 47 ms on the runner. That is the
  same kind of work as the benchmarks it protects (the index), so if it
  holds still, they would have too.
- **Noisy twice is inconclusive, not a failure.** Two noisy attempts say
  the runner was bad, not that Leal got slower. Failing on that turns CI
  red for no reason, and a gate that is often red for no reason gets
  ignored. Budgets still fail on a noisy run, and a regression still fails
  when every attempt shows it, so nothing that matters goes through
  unflagged. A regression that an inconclusive run couldn't judge shows
  as one of the "regression? (…)" rows with a `::warning::`, and the next
  push compares again.

`bench-report --last-attempt` tells the report that it can't rerun:
`Report::outcome` then turns a noisy verdict into `Outcome::Inconclusive`
(exit 0) instead of `Outcome::Rerun` (exit 3). `bench-compare` passes it
on a base with no benchmarks, which never reruns.

### A regression must repeat (added after 1.10)

**A benchmark fails as a regression only if its whole 95% interval is
above +20% on every attempt that ran: the first attempt, even if it was
noisy, and the rerun.** `bench-compare` keeps the first attempt's results
(`target/bench-compare/criterion-attempt-1`) and gives them to the rerun's
`bench-report` (`--first-attempt`). Without `--plan`, that makes the
rerun the last attempt; with it (as `bench-compare` runs it since run
37069372104), the rerun may ask for a third attempt.
`Report::after` judges the rerun with them, and `Report::outcome` decides:

| First attempt | Rerun | Result |
|---|---|---|
| over budget (or missing) | none (no rerun) | **fail** |
| any | over budget (or missing) | **fail** |
| regression (noisy or quiet) | the same regression (noisy or quiet) | **fail** (since run 37069372104: only if both were quiet for it; otherwise a third attempt decides, see below) |
| no regression | a regression | inconclusive: "regression? (not on attempt 1)" |
| regression | no regression, and no sign its base side slowed | pass, with a warning naming it (inconclusive if the rerun's run was noisy) |
| regression | no regression, but its nearest canaries say its base side slowed | inconclusive: "regression? (not shown again, base side slowed)" (since run 37069372104; it used to depend on the run-wide canaries only) |
| noisy, no regression | quiet, no regression | pass |
| noisy, no regression | noisy | inconclusive |
| quiet, no regression | none (no rerun) | pass |

So a regression on the first attempt is now rerun, noisy or quiet; it
used to fail at once on a quiet run. Inconclusive warns and passes (exit
0), as before. Budgets fail on any attempt.

**Why: main at `ed09773` (task 1.10, run 36932316543).** Attempt 1 was
noisy (`baseline/memchr3_scan` −15.3%) and showed no regression on the
same binaries: `marks/next_wide` −8.1%, `navigate/*` −14% to +3%.
Attempt 2 judged itself alone. Noise started part-way through its head
side, 11 s into the `marks` group: `marks/previous_narrow` matched the
base, then `marks/next_wide`, in the same process, was +35%. That
slowdown lasted through `rows/*`. `baseline-late/memchr3_scan` was
+10.0%, at the limit and not over it, so the run counted as quiet and 13
benchmarks failed at +25–40%. Eleven of them were `navigate` and `rows`
benchmarks, whose machine code was identical on both sides apart
from one constant (`docs/tasks/1.10.md`). Under this rule that run is
inconclusive. A real slowdown shows on both attempts, so it still fails.

### The rerun swaps the order (added after `2cc71bb`)

**Attempt 1 benchmarks the base commit first, then this checkout (head).
The rerun benchmarks head first, then base.** The rules above are
unchanged: budgets fail on any attempt, a canary that moves makes the run
noisy, and a regression fails only if every attempt shows it. So a
regression now has to show in both orders to fail.

**Why: main at `2cc71bb`, compared with `33e4bef` (run 36958964776).** Both
attempts ran base first, and both showed the same two slowdowns:

| Benchmark | Attempt 1 (base first) | Attempt 2 (base first) | Dev Mac (`just bench-compare 33e4bef`) |
|---|---|---|---|
| `rows/parse` | +26.4% (+25.7% to +26.8%) | +26.4% (+20.1% to +33.8%) | −3.6% |
| `navigate/next_nul_wide` | +40.0% (+34.6% to +47.7%) | +26.4% (+21.2% to +31.4%) | +1.9% |

Both attempts were noisy (`baseline/memchr3_scan` −13.3% on the first,
`baseline-late/memchr3_scan` +16.5% on the second), but noise doesn't
excuse a regression that repeats, so the job failed. On the dev Mac the
same comparison showed nothing. The likely cause is drift: something that
changes steadily over the job, such as the VM's host warming up or a
neighbour's load building, makes whichever side runs second slower. With
the same order on both attempts, that drift counted against head twice,
which looks just like a real regression.

**How swapping cancels it.** If drift adds *d* to whichever side runs
second, attempt 1 measures head's true change *r* as about *r + d*, and the
rerun as about *r − d*. A drift alone can't push both above +20%. A real
regression still shows in both orders and fails, as long as it is bigger
than the drift. At `2cc71bb`, the rerun would have run head first, the
drift would have counted against base, and the job would have passed
with a warning that `rows/parse` regressed on attempt 1 only (as
inconclusive, if the rerun was noisy again). That case is now a
test (`a_drift_regression_does_not_repeat_in_the_other_order` in
`tests/report.rs`). This needs both attempts: one attempt on its own is
still biased against whichever side ran second. That is one reason a
regression on attempt 1 always reruns.

**How it works.** Criterion compares the side that runs second with the
one that ran first. On attempt 1 (base first) that is as before: base
saves its results as the `base` baseline, and head's run compares with it
(`--baseline-lenient base`). On the rerun (head first), head saves
`head`, and base's run compares with that (`--baseline-lenient head`).
`bench-compare` then deletes base's results and moves head's saved ones
into `new/`, where `bench-report` reads them. So budgets are always
checked on head's numbers, and a benchmark that only base has isn't
reported.

That rerun's `change/` is base's change relative to head, the wrong way
round. `bench-compare` writes each attempt's order (`base-first` or
`head-first`) to `bench-compare-order` in its criterion directory, which
is uploaded with the results. `report::collect` reads it, and on a
head-first attempt it inverts each change (`Change::inverted`): a median
ratio of 1 + *c* becomes 1 / (1 + *c*), so base at +25% means head at
−20%. The interval's ends swap. Inverting only ever reverses the order of
two changes, so the inverted ends are still the 95% interval: criterion takes them as percentiles of
its bootstrap distribution, and inverting every resample keeps their
order. The statistics stay criterion's own. Criterion's console lines on
the rerun show the change the other way round; the report's table is
always head's change.

The job summary says which order each attempt ran in, and so do the
annotations, for example "regressed on attempt 1 (base first) but not on
the rerun (head first), so it passed". If both attempts ran in the same
order, `bench-report` warns: that means `bench-compare` is broken, and
drift counted against the same side twice.

**First tried: criterion's `--load-baseline`.** Each side saved its own
baseline, then head's benchmark programs ran once more with
`--load-baseline head --baseline-lenient base`, so criterion compared
head with base in either order. It failed `just bench-compare` locally:
with `--load-baseline`, criterion never calls the benchmark closure, and
`find` checks a value the closure sets (`find.rs`: "rare: 0 matches").
Every benchmark would have to allow for a closure that never runs, and it
also cost a set-up pass per attempt. Inverting the change needs neither.

**Considered: base, head, base on each attempt,** with head compared with
the mean of the two bases. That cancels linear drift within a single
attempt, but it is too slow and needs code of our own:

- **Time.** One side's benchmarks take about 7 minutes on the runner. At
  `2cc71bb`, attempt 1's sides took 6 min 42 s (base) and 7 min 0 s
  (head), plus about 20 s each for `baseline-late` and 1–1.5 min each to
  build. The whole job took 32 min. A third side adds about 7 minutes per
  attempt, so about 14 minutes when there is a rerun. That is about
  46 minutes, over the job's 45-minute timeout.
- **Statistics.** Criterion compares with one baseline, not the mean of
  two. `bench-report` would need its own bootstrap over three sets of
  samples, in place of criterion's tested one.
- **It does no better on a step.** A runner that slows down suddenly
  part-way through (the `ed09773` case) isn't linear drift. Neither
  scheme cancels it within one attempt, and both rely on the rerun.

**The swap costs no time.** Each attempt still runs each side once, in
the same steps as before, only in the other order on the rerun.
Inverting the changes takes microseconds in `bench-report`. Over the
ten runs before this change, the job took 15–34 minutes (32 at
`2cc71bb`, which reran). That stays the same.

**Checked end to end** with `just bench-compare HEAD 0.20 0.0` on the dev
Mac. A noise threshold of 0 makes every attempt noisy, so attempt 1 (base
first) always reruns head first. Both attempts ran, and the rerun was
inconclusive and passed, as it should with identical code. Its table
showed head's change: criterion's raw `worst/blank_lines` change, base relative to
head, was −4.5% (−5.4% to −3.7%), and the table showed +4.7% (+3.8% to
+5.7%). The two attempts took 25 min 54 s in all.

### Group canaries and a third attempt (added after run 37069372104)

**Each bench group now has a short canary just before and just after it,
on both sides, and a regression on both attempts that either attempt was
noisy for goes to a third attempt of its group alone.** The thresholds
don't change: a regression is a 95% interval wholly above +20%, a canary
that moved by more than 10% means noise, a regression fails only if it
regressed on every attempt, and the rerun swaps the order.

**Why: run 37069372104** failed on `marks/next_wide` at +32.4% (+24.6% to
+39.3%) on attempt 1 and +31.3% (+21.3% to +36.1%) on the rerun. The code
it measures was identical instruction for instruction on both sides, and
a local A/B put it within 0.4%. CI's history shows `marks/next_wide`
swinging from −20% to +28% on unrelated commits. Both attempts were noisy
by the run-wide canaries (`baseline/memchr3_scan` −20.3%, then +10.2%), but
noise didn't excuse a regression that repeated, so the job failed. The
noise is VM contention that lasts minutes and starts part way through a
run. The run-wide canaries run at the start and end of each side, minutes
from the `marks` group, so they can't say whether it was hit.

**Group canaries.** `common::canary(c, group, side)` runs
`canary/<bench>.<group>.before` just before a group and `….after` just
after it: `memchr3` over the first 32 MiB of the reference file (the
run-wide canary's work, sized to more than the caches), with 10 samples,
0.3 s of warm-up and 1 s of measurement. They are a benchmark's **nearest
canaries**. If either moved by more than 10%, the attempt is **noisy for
that benchmark** (`Row::noisy`), whatever the run-wide canaries did; the
table shows them in a "Nearest canaries" column. A group whose canaries
didn't run on both sides (the first run after this change, against a
base without them) falls back to the run-wide canaries, as before. The
run-wide canaries still decide whether **the run** is noisy, which reruns
attempt 1 and makes a noisy rerun inconclusive, as before. A group canary
that moved is never a failure or a run-wide warning on its own.

**The third attempt.** A benchmark that regressed on both attempts:

| Attempts 1 and 2 | Attempt 3 (its groups only, base first) | Result |
|---|---|---|
| both quiet for it | none | **fail** |
| at least one noisy for it | the same regression, quiet or noisy | **fail** |
| at least one noisy for it | no regression, and no sign its base side slowed | pass, with a warning naming it |
| at least one noisy for it | no regression, but its nearest canaries say its base side slowed | inconclusive (warns, passes) |
| at least one noisy for it | no result for it | **fail** |

The rerun's `bench-report` gets `--plan`: when it finds such a benchmark
(`Status::Recheck`) and nothing else fails, it writes
`target/bench-compare/third-attempt-plan` (the bench targets on one line,
read from the canaries' ids, and a criterion filter for the groups and
their canaries on the next) and exits 3. `bench-compare` then runs, on
each side, base first: `baseline/memchr3_scan`, the planned groups with
their canaries, and `baseline-late/memchr3_scan`. Attempt 3's
`bench-report` gets both earlier attempts (`--first-attempt`,
`--second-attempt`) and settles each benchmark to recheck
(`Report::settle`). It checks the budgets of what it ran; the others were
checked on the attempts before. Without `--plan`, the rerun is the last
attempt and such a benchmark fails, as it always did.

**Why it keeps the guarantees.** A real regression shows on every
attempt, so it still fails: on the rerun if both attempts were quiet for
it, and on attempt 3 otherwise, noisy or not. Budgets fail on any
attempt, attempt 3 included.

**Which way the noise went.** A change is head's relative to base, so
noise fakes a regression only by slowing head, and hides one only by
slowing base. A canary that got faster on head relative to base by more
than 10% says base slowed (`Row::could_hide`). So when a later attempt
doesn't show a regression, it counts as evidence against it unless that
attempt's nearest canaries say base slowed; then the benchmark is
`Status::Unsettled`, inconclusive, never a silent pass. That rule is the
same after the rerun (a regression only attempt 1 showed) and after
attempt 3. A canary that moved the other way (head slowed) can't hide a
regression, so it doesn't stop one being cleared.

**What noise can still fail.** Noise between one group's two canaries
isn't seen by either, so that attempt looks quiet for the group. If such
a burst slows head in the same group on both attempts, in both orders,
the benchmark fails at attempt 2, with no third attempt. The group
canaries narrow the window from a whole run to one group (about a minute
at most); they don't close it. Noise the canaries do see needs to hit the
same group on three attempts to fail a benchmark. Run 37069372104
under these rules would have rerun `marks` (about a minute per side) and
most likely passed with a warning. That case, and the others, are tests
in `tests/report.rs` (`a_regression_on_two_noisy_attempts_and_a_quiet_third_without_it_passes_with_a_warning`,
`a_consistent_regression_on_quiet_runs_fails`,
`a_regression_on_all_three_attempts_fails`,
`a_noisy_third_attempt_without_the_regression_is_inconclusive`,
`a_regression_a_later_attempt_may_have_hidden_is_unsettled_on_the_rerun_too`,
`a_third_attempt_against_a_base_without_group_canaries_uses_the_run_wide_ones`,
`budgets_are_unaffected_by_the_third_attempt` and
`bench_report_runs_a_third_attempt_for_a_regression_on_noisy_attempts`).

**What it costs.** There are 8 bench groups, so 16 canaries a side. On
the dev Mac one canary takes about 1.2 s (10.6 ms an iteration, 0.3 s
warm-up, 1 s measuring, then criterion's analysis), so about 20 s a side
and 40 s an attempt. On the runner, where `memchr3` is about 25% slower,
expect about 25 s a side: **about 50 s an attempt, so about 1.7 minutes
on a job that reruns** (the job took about 35 minutes at
run 37069372104). A third attempt runs only when a benchmark regressed on
both attempts with one of them noisy for it. It then reruns only that
group's bench target, filtered: for `marks`, about 1 minute a side plus
the 20 s of run-wide canaries, so about 3 minutes. If every group needed
it, it would cost another full attempt (about 17 minutes with its
canaries). So the worst case is about 37 + 17 = 54 minutes, and the job's
timeout went from 45 to 75 minutes, to leave room for a slow runner.

**Checked end to end** on the dev Mac with `just bench-compare HEAD 0.20
0.0`, against a commit with this change, after doubling the work in
`marks/next_wide` in the working tree. A noise threshold of 0 makes every
attempt noisy for every benchmark. Attempt 1 (base first) showed
`marks/next_wide` at +102.4% and reran; the rerun (head first) showed
+91.1% and asked for a third attempt of `marks` alone (bench target
`index`); the third, base first, showed +97.5% and the job failed with
"regressed on all three attempts". The third attempt took about 2
minutes; the whole run 34 min 28 s, with the base's build. The 16 group
canaries moved by −2.6% to +2.8% on every attempt there.

**Considered: a third attempt whenever a regression repeats,** noisy or
not. It would cost the same in the rare case it runs, but it would retry
a consistent regression on two quiet attempts, which is the strongest
evidence the job gets. With the group canaries, two quiet attempts both
showing the regression is what a real one looks like, so it fails at
once.

**Not done: canaries inside a group, between benchmarks.** The noise at
`ed09773` started 11 s into the `marks` group, so even a group's canaries
can be tens of seconds from a benchmark. Contention that starts or ends
inside a group shows on one of its canaries, since they bound it. What
still fails is contention that starts and ends inside one group, between
its canaries, on both attempts: two bursts shorter than the group (about
a minute), in the same group, in both orders. A canary between every
pair of benchmarks would close that gap at about 1.2 s per benchmark
(about 50 of them) a side, roughly 2 minutes an attempt.

Both thresholds are `bench-compare` arguments (`regression="0.20"
noise="0.10"`). **They are starting values.** Same-runner noise for these
benchmarks was under 8% on this Mac. On GitHub, the one measurement so far
(79fa5af) had `memchr3_scan` within about 6%.
**Once a few weeks of CI runs show the real canary noise (it's in the
job summaries and artifacts), tighten both:** the noise threshold to just
above the canaries' usual movement, and the regression threshold to about
twice that.

The job also refuses to pass without having compared anything:

- If the base commit has benchmarks but they fail to build or run, the job
  fails, because otherwise it would pass without comparing.
- If the base has no benchmarks (the first run after this task lands), it
  prints a `::warning::` and checks only the budgets.
- A manual run (`workflow_dispatch`) whose `base` input isn't a commit
  fails with that message, rather than quietly comparing with something
  else. With no input, the base is the parent commit. On a push whose
  previous tip is gone (a force push), it warns and uses the parent.

What doesn't gate, and why:

- **Absolute numbers compared across runs** (for example "the index took
  320 ms last week and 350 ms today"). Host-to-host variance is as big as
  the changes we'd want to catch. Those numbers are recorded in the
  artifacts and in task notes, not compared automatically.
- **Slowdowns whose interval reaches below +20%.** They show in the table
  with their interval, and a reviewer can act on them.
- **Pull requests.** The job doesn't run on them. Branches aren't pushed,
  and outside contributions are rare.
- **Instruction counts** (`iai-callgrind`) would be noise-free and could
  gate tightly, but Valgrind doesn't run on macOS on Apple silicon. If
  wall-clock alerts turn out to be too noisy, the option is a Linux job
  for the portable core.

**When the Benchmarks run is red:** read the job summary.

- *Over budget* or *missing*: a real failure. Fix it or write an ADR.
- *Regression*: it showed on both attempts, in both orders, either with
  its group's canaries quiet on both or on a third attempt as well, so it
  is very likely real. (If the summary says both attempts ran in the same order,
  `bench-compare` is broken: fix that first.) Fix it. If the slowdown is deliberate (say, correctness bought with speed),
  say so in the task notes, and the next push compares against the new
  numbers.
- *Base benchmarks failed*: the base commit's benchmarks don't build or
  run any more (a toolchain change, say). Fix them or rerun with a
  different `base` input.

**When the run is green with an "inconclusive" warning:** a run-wide
canary moved on the rerun, the rerun showed a regression that the first
attempt didn't, or a later attempt that didn't show a regression may
have hidden it (its nearest canaries say its base side slowed), so not
every regression was judged (budgets were). Check the "regression?
(noisy for it)", "regression? (not on attempt 1)" and "regression? (not
shown again, base side slowed)" rows; if there are any, rerun the job. A
"regression? (not on attempt 3)" row with a warning passed: attempts 1
and 2 showed it, one of them noisy for it, and a third with no sign that
its base side slowed didn't. If runs
are often inconclusive, the noise threshold is too tight for GitHub's
runners: record the canary numbers and loosen it.

`just check` doesn't run benchmarks, but clippy compiles them
(`--all-targets`), and the generator and report tests run on small inputs
(about 0.1 s). The full 100 MB file is only ever written by `just
reference-file`, `just bench` and `just bench-compare`.

## Deviations and notes

- **"100 MB" is decimal:** 99,954,047 bytes (95.3 MiB), with a header plus
  1M data rows.
- **"Generating the file, then timing…" (PLAN):** generating the file isn't
  a criterion benchmark. It is set-up, and its time (0.2 s) is printed by
  `leal-refgen` and recorded above.
- **`just bench` used to be `cargo bench --workspace`.** It is now
  `cargo bench --package leal-bench -- <args>`. All benchmarks live in
  `leal-bench`. Running every crate's libtest harness in bench mode only
  printed "0 tests" lines, and it rejected criterion flags like
  `--save-baseline`. For the same reason, `leal-bench`'s library and
  binaries are `bench = false`.
- **No `mmap` benchmark.** Mapping needs `unsafe`, which belongs only in
  leal-core's `source` module (1.1). Once 1.1 lands, a benchmark for
  mapping and touching every page would add to this baseline.

  to be common, the noise threshold should be loosened instead.

## Rust notes

- **Benchmarks are their own build targets.** Each file in `benches/` is
  compiled as a separate program by `cargo bench`, in the `bench` profile.
  That profile inherits `[profile.release]` (`lto = "thin"`,
  `codegen-units = 1`), so benchmarks measure optimised code, the same as
  what ships. `harness = false` in `Cargo.toml` means "don't use the
  built-in test runner, the file has its own `main`". Criterion's
  `criterion_group!` and `criterion_main!` macros write that `main`
  (`benches/baseline.rs`, last two lines).
- **Criterion** runs a function many times, measures it, and works out the
  statistics: median, confidence intervals, outliers, and the change from
  the previous run. A *group* (`c.benchmark_group("baseline")`) shares
  settings, and the full id is `group/function`. `Throughput::Bytes` makes
  it report GiB/s as well as time. `SamplingMode::Flat` suits benchmarks
  that take milliseconds per iteration (`benches/common/mod.rs`).
- **`black_box`** (`std::hint::black_box`) tells the optimiser "assume this
  value is used, and assume you don't know what it is". Without it, the
  compiler could see that a result is never used and delete the work being
  measured. Or it could see a constant input and compute the answer at
  compile time. In `baseline.rs` it wraps the inputs (`black_box(&bytes)`)
  and the bytes read.
- **`mod common;` in a bench file** compiles `benches/common/mod.rs` into
  that benchmark program. Each bench file is a separate program, so this
  is how they share code without making it part of the library.
- **`env!("CARGO_MANIFEST_DIR")`** is filled in at compile time with the
  crate's directory. `reference::data_dir` uses it to find `target/` from
  any working directory. `env!("CARGO_TARGET_TMPDIR")`, used in the tests,
  is a scratch directory Cargo provides for integration tests.
- **Generic writers:** `reference::write<W: Write + ?Sized>(out: &mut W, …)`
  accepts anything that implements the `Write` trait. That can be a
  `Vec<u8>` (the tests), a `BufWriter<File>` (`generate`) or a socket. The
  compiler makes a specialised copy for each type, so this costs nothing at
  run time. `?Sized` also allows trait objects like `&mut dyn Write`.
- **`wrapping_add` and `wrapping_mul`** (the `Rng` in `reference.rs`):
  ordinary `+` and `*` on integers panic on overflow in debug builds. The
  random number generator relies on overflow wrapping around, so it says
  so explicitly.
- **Range patterns** like `0..530 => …` in a `match` (`write_notes`) match
  a number in that half-open range. The compiler checks that the arms
  cover every value.
- **Match guards** like `Status::Regression if outcome == Outcome::Rerun
  => …` in `bench-report` (`src/bin/bench-report.rs`) match only when the
  condition after `if` is also true; otherwise the next arm is tried. Here
  the next arm, `Status::Regression => …`, handles the last attempt.
- **`impl FromStr for Order`** (`src/report.rs`) teaches Rust how to turn
  a string into an `Order`. After that, `"head-first".parse::<Order>()`
  works, as it does for numbers. `parse` returns a `Result`: `Ok(order)`,
  or `Err(message)` for a name that isn't an order. `read_order` uses it
  on the contents of `bench-compare-order`.
- **A method as a function** (`report::collect`):
  `measurement.change.map(Change::inverted)` applies `inverted` to the
  change if there is one (`Some`), and leaves `None` alone. Naming the
  method, `Change::inverted`, is shorthand for the closure
  `|change| change.inverted()`.
- **`matches!` with a guard** (`Report::same_order`):
  `matches!((a, b), (Some(x), Some(y)) if x == y)` is true only when both
  are `Some` and their contents are equal. It is a one-line `match` that
  returns `true` or `false`.
- **Taking `self` by value** (`Report::after(mut self, first: &Report)`):
  the method consumes the rerun's report, changes its rows in place, and
  returns it, so the caller writes `report = report.after(&first)` and no
  copy is made. `first` is only borrowed (`&`), since it is only read.
- **`env!("CARGO_BIN_EXE_bench-report")`**, in `tests/report.rs`, is the
  path of the `bench-report` binary that Cargo builds before running the
  integration tests. The `bench_report_*` tests run it as CI does, with
  `GITHUB_ACTIONS` and `GITHUB_STEP_SUMMARY` set, and check its exit
  status, annotations and job summary.

Added with the group canaries and the third attempt:

- **`env!("CARGO_CRATE_NAME")` in a shared module** (`common::canary`):
  `benches/common/mod.rs` is compiled into each bench program separately
  (`mod common;`), so this compile-time constant is that program's name,
  `index` in `benches/index.rs`. That is how a canary's id records which
  bench target it ran in, without each file passing its own name.
- **A value made on first use** (`common::canary`): `let mut bytes:
  Option<Vec<u8>> = None;` then `bytes.get_or_insert_with(canary_bytes)`
  inside the closure reads the file the first time criterion calls the
  closure and reuses it on every later call. Criterion calls it once per
  sample, and not at all if a filter leaves the canary out.
- **`Box<Report>` inside `Report`** (`Report::third`): a struct can't hold
  a value of its own type directly, because its size would be infinite.
  A `Box` is a pointer to a value on the heap, with a fixed size, so the
  report after a third attempt can keep that attempt's own report.
- **`let … else`** (`evaluate`): `let (Some(canary), Some(change)) = (…)
  else { continue; };` binds both values if both are `Some`, and
  otherwise runs the `else` block, which must leave the loop iteration
  (`continue`), the function (`return`) or similar.
- **`Option::is_none_or`** (`evaluate`, `bench-report`): true for `None`,
  and for `Some(x)` whatever the closure says about `x`. It reads "keep
  this one if there is none yet, or it is bigger".
- **A borrowed struct** (`GroupCanary<'a>`): its `bench` and `group`
  fields are `&'a str` slices of the id it was parsed from, not copies.
  The lifetime `'a` says a `GroupCanary` can't outlive that id string.

## Budget-only benchmarks (added after 1.5)

`open/first_paint_removable_under_load` is gated on its 150 ms budget only,
never on change between commits (`report::BUDGET_ONLY`). On shared runners

reason. Its budget is still enforced on every run. Add a benchmark to
