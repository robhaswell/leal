# 1.2b Reference file and CI benchmarks

## What was built

A new crate, **`crates/leal-bench`**, holds everything benchmark-related. It
is never shipped and nothing depends on it. Keeping it out of `leal-core`
means 1.1 (`source`) and 1.2 (detection), running in parallel, touch none
of the same files. Their only shared files are `Cargo.lock` and `docs/PLAN.md`.

| Path | What it is |
|---|---|
| `src/reference.rs` | The reference file generator, its constants (`ROWS`, `SEED`, `VERSION`, `HEADER`) and `ensure()`, which benchmarks call to get the file. |
| `src/bin/leal-refgen.rs` | The command-line tool that writes the file. `just reference-file` runs it. |
| `reference.sha256` | The SHA-256 of the default file, which `just reference-file` checks. |
| `benches/baseline.rs` | The speed-of-light baseline benchmarks. |
| `benches/common/mod.rs` | Shared set-up for the benchmark files: `reference_file()` and `whole_file()` (sampling settings for large inputs). |
| `src/budgets.rs` | The DESIGN §1 budgets that CI enforces. Empty until 1.3. |
| `src/report.rs`, `src/bin/bench-report.rs` | Read criterion's JSON results and print the report: pass, fail (budgets, regressions), or noisy (a canary moved), which reruns once and is then inconclusive. |
| `tests/reference.rs`, `tests/report.rs` | Tests for the generator and the report. |

Outside the crate:

- `justfile`: `bench` now runs only `leal-bench` and passes arguments to
  criterion. There are new `reference-file` and `bench-compare` recipes.
- `.github/workflows/bench.yml`: the CI benchmark job.
- DESIGN §7 lists the new crate.

### Adding a benchmark (1.3, 1.3a and later)

1. Add `crates/leal-bench/benches/<name>.rs`, and a `[[bench]]` entry with
   `harness = false` in `crates/leal-bench/Cargo.toml`. Add the crate being
   measured (for example `leal-core.workspace = true`) to its
   `[dev-dependencies]`. Benchmarks use only that crate's public API.
2. Start the file with `mod common;`, get the file with
   `common::reference_file()`, and call `common::whole_file(&mut group, len)`
   on any group that processes the whole file.
3. If the benchmark measures a DESIGN §1 budget, add a `Budget` to
   `src/budgets.rs` with its criterion id (`group/name`). CI then fails if
   the median goes over the budget, or if the benchmark stops running.
4. Put the result in your task notes, next to the baseline below.

## The reference file

`just reference-file` writes `target/bench-data/reference-v1.csv` (in
`target/`, which git ignores) in about 0.2 s and checks it against
`reference.sha256`. Benchmarks generate it themselves if it is missing, so
`just bench` also works from a clean checkout. Nothing is cached anywhere
else, and the file is never committed.

- **Shape (DESIGN §1):** a header and 1,000,000 rows × 12 columns, UTF-8,
  **99,954,047 bytes** (100.0 MB). 1,044,952 LF bytes and 2,534,598 quote
  bytes in all.
- **Contents:** an order export (`id,order_date,customer,city,country,sku,
  quantity,unit_price,currency,discount,status,notes`). The column table
  is in `src/reference.rs`. Names and cities are often non-ASCII (`Nguyễn`,
  `東京`, `Αθήνα`), and 74% of rows have some non-ASCII text. `customer` is
  always quoted (`"Surname, Given"`). 29,898 rows (3%) have a `notes` field
  with one or two newlines inside quotes, 5% have escaped quotes (`""`),
  and 8% have a comma in `notes`. Python's `csv` module, in strict mode,
  reads the file as 1,000,000 records of 12 fields, which independently
  checks the generator's quoting.
- **Regular on purpose:** LF line endings, no BOM, no CR, every row has 12
  fields, and fields are quoted exactly when they need it. The reference
  file measures the common path. Messy input is the corpus's job.
- **Reproducible:** the output depends only on the row count and the seed.
  The random numbers come from SplitMix64, written out in about 10 lines,
  not from a library whose output could change between versions. There is
  no floating point: prices are formatted from integer cents. Fewer rows
  give a prefix of the same file.
- **Pinned three ways:** a test pins the FNV-1a hash of the first 10,000
  rows, so `just check` catches any change to the output. `reference.sha256`
  pins the full file, and CI checks it on GitHub's runner, so the output is
  the same on a different machine. And `reference::VERSION` is part of the
  file name. If the output changes on purpose, bump `VERSION`, update both
  hashes, and say so in the task notes: earlier numbers then measured a
  different file.
- **Variants:** PLAN asks for none. `leal-refgen --rows N --seed S` writes
  others, for example `--rows 10000000` gives about 1 GB, for the "usable
  up to 1 GB" goal.

## Baseline (speed of light)

Machine: **`Mac17,8`** (`sysctl hw.model`), Apple M5 Pro, 18 cores (6
performance and 12 efficiency), 48 GB, macOS 27.0. This is the development
Mac, **not** the reference machine (a base M1 Air), which is slower. Expect
higher numbers there.

| Benchmark | Median | Throughput |
|---|---|---|
| Generate the file (`leal-refgen`, release) | 0.21–0.24 s | — |
| `baseline/sequential_read`: `File::read` into a 1 MiB buffer, page cache warm | 4.16 ms | 22.4 GiB/s |
| `baseline/memchr3_scan`: count `"`, CR and LF with `memchr3_iter`, file in memory | 30.1 ms | 3.09 GiB/s |

Three runs on the same day were within 8% of each other (sequential read
4.16–4.49 ms, scan 30.1–31.2 ms).

What these mean for later tasks:

- **No reader or indexer can beat these numbers.** The 1.3 row index
  (budget: 500 ms) has to look at every quote and line ending, so 30 ms is
  its floor on this Mac. That leaves about 16× headroom here, and less on
  an M1 Air.
- **The scan is limited by how often it finds a byte, not by memory
  bandwidth.** There are 3.6M matches, one every 28 bytes. `memchr3_iter`
  costs about 8 ns per match, which is why it runs at 3 GiB/s while reading
  runs at 22 GiB/s. An indexer that classifies 16 or 64 bytes at a time
  into bitmasks (the simdjson approach) could go faster than this "floor".
  So the floor is a practical one, for "find each special byte" designs.
- **Reads are from the page cache.** Criterion's warm-up reads the file
  first. That is the case for a file the user has just opened or saved. A
  cold read from disk needs `sudo purge` between iterations, so it isn't
  measured.
- The medians come from `target/criterion/baseline/*/new/estimates.json`.
  Criterion's own console line shows the mean, which can be slightly
  different.

### Rerunning

```sh
just reference-file          # generate and check the file (optional; benches do it)
just bench                   # every benchmark, results in target/criterion/
just bench baseline/         # only these; the argument is a criterion filter
just bench-compare main      # this checkout against main, as CI does it
```

Close other heavy apps first. The Mac doesn't need to be unlocked: these
benchmarks don't draw anything.

## CI: what runs, what gates, what only reports

**Decision: CI runs the benchmarks on each push to `main` that changes
code (`.github/workflows/bench.yml`). The job fails on three things:**

- **a DESIGN §1 budget,** whatever the noise;
- **a regression against the previous commit, measured on the same
  runner, on a quiet run:** the whole 95% interval of the median's change
  is above +20%, and no noise canary moved by more than 10%;
- **broken comparisons:** the base commit's benchmarks fail, or a manual
  run names a base that isn't a commit.

**A run that is noisy twice (a canary moved by more than 10%, and again
on the one automatic rerun) doesn't fail: it is *inconclusive*.** The job
prints a `::warning::`, heads the job summary "Benchmarks: inconclusive",
and passes. Budgets were still checked. (Until the fix after 79fa5af,
being noisy twice failed the job; see "Noise canaries" below.)

**Everything else is only reported: a table in the job summary, plus
criterion's JSON as an artifact kept for 90 days.**

The problem is that a GitHub-hosted macOS runner is a shared VM: an
M1-class guest with 3 cores. It isn't the reference machine, and two jobs
can land on hosts that differ by 10–30%. So the job never compares numbers
from different runs. It only uses comparisons that survive that noise:

1. **Budgets are absolute, with no allowance.** A budget is a requirement
   (DESIGN §1: "these budgets are checked by benchmarks in CI (core)"), and
   DESIGN §3.10 asks for a CI benchmark that asserts first paint stays
   under 150 ms. The runner is roughly as fast as a base M1 Air, so a
   result near its budget on CI is near it on the reference machine too.
   That is worth hearing about even if noise put it over. A result well
   under budget never flakes. A budgeted benchmark with no result fails
   as well, so a renamed or deleted benchmark can't silently drop its
   gate. A noisy run doesn't excuse a budget failure. `budgets.rs` is
   empty until 1.3 adds the index (500 ms) and 1.3a adds first paint
   (150 ms).
2. **Regressions are A/B on one runner, judged by the confidence
   interval.** `just bench-compare <base>` extracts the base commit with
   `git archive`, then builds and benchmarks it. It then benchmarks this
   checkout on the same VM a minute later. Criterion compares the two
   (`--save-baseline base`, then `--baseline-lenient base`), and writes the
   median's change with a 95% confidence interval
   (`change/estimates.json`). A benchmark has regressed when the interval's
   **lower bound** is above **+20%**: criterion is 95% sure it got more than
   20% slower. A single noisy median can't fail the job this way, but a
   real, large slowdown always does. CI's base is `github.event.before`,
   the tip of `main` before the push, so a task that lands as several
   commits is compared as a whole. A failure gets an `::error::`
   annotation, and GitHub emails the pusher.
3. **`memchr3_scan` is the noise canary, with a tighter 10% threshold.**
   Its code is the same on both sides of every comparison, so any change
   in it comes from the machine, not Leal. Each side runs the baseline
   twice: as `baseline/…` with the other benchmarks, then again as
   `baseline-late/…` after all of them, so noise that starts part-way
   through a run is caught too. The canaries are
   `baseline/memchr3_scan` and `baseline-late/memchr3_scan`
   (`report::CANARIES`). If either's median moves by more than 10% either
   way, the run is too noisy to judge. Its regressions show as
   "regression? (noisy run)", and `bench-compare` reruns both sides once.
   If the rerun is noisy too, the run is inconclusive: a warning, not a
   failure (above). Noise is caught at 10%, regressions at 20%, so noise
   big enough to fake a regression is flagged first.
   `sequential_read` is still run and reported, as "info (not gated)": it
   is no canary, has no budget, and can't regress.

### Noise canaries: why `sequential_read` isn't one

At first both baseline benchmarks were canaries, and a run that was noisy
twice failed the job. On main at 79fa5af, the job failed though nothing
had regressed: `index/build` and `index/run` moved by ±4%, far inside
their 500 ms budget. It failed because `baseline/sequential_read` moved
+10.2% on the first attempt and `baseline-late/sequential_read` +15.7% on
the rerun. Meanwhile `memchr3_scan` stayed within about 6% on both.

- **`sequential_read` is a poor canary on a shared runner.** It takes
  only about 7 ms there, and it measures the page cache and the VM's I/O
  path, which other tenants on the host share. A short benchmark that
  depends on shared I/O moves by more than 10% with no code change.
- **`memchr3_scan` is a good one.** It is CPU-bound, works on a buffer
  already in memory, and takes about 47 ms on the runner. That is the
  same kind of work as the benchmarks it protects (the index), so if it
  holds still, they would have too.
- **Noisy twice is inconclusive, not a failure.** Two noisy attempts say
  the runner was bad, not that Leal got slower. Failing on that turns CI
  red for no reason, and a gate that is often red for no reason gets
  ignored. Budgets still fail on a noisy run, and a regression still fails
  on a quiet one, so nothing that matters goes through unflagged. A
  regression hidden by an inconclusive run shows as "regression? (noisy
  run)" with a `::warning::`, and the next push compares again.

`bench-report --last-attempt` tells the report that it can't rerun:
`Report::outcome` then turns a noisy verdict into `Outcome::Inconclusive`
(exit 0) instead of `Outcome::Rerun` (exit 3). `bench-compare` passes it
on the second attempt, and on a base with no benchmarks, which never
reruns.

Both thresholds are `bench-compare` arguments (`regression="0.20"
noise="0.10"`). **They are starting values.** Same-runner noise for these
benchmarks was under 8% on this Mac. On GitHub, the one measurement so far
(79fa5af) had `memchr3_scan` within about 6%.
**Once a few weeks of CI runs show the real canary noise (it's in the
job summaries and artifacts), tighten both:** the noise threshold to just
above the canaries' usual movement, and the regression threshold to about
twice that.

The job also refuses to pass without having compared anything:

- If the base commit has benchmarks but they fail to build or run, the job
  fails, because otherwise it would pass without comparing.
- If the base has no benchmarks (the first run after this task lands), it
  prints a `::warning::` and checks only the budgets.
- A manual run (`workflow_dispatch`) whose `base` input isn't a commit
  fails with that message, rather than quietly comparing with something
  else. With no input, the base is the parent commit. On a push whose
  previous tip is gone (a force push), it warns and uses the parent.

What doesn't gate, and why:

- **Absolute numbers compared across runs** (for example "the index took
  320 ms last week and 350 ms today"). Host-to-host variance is as big as
  the changes we'd want to catch. Those numbers are recorded in the
  artifacts and in task notes, not compared automatically.
- **Slowdowns whose interval reaches below +20%.** They show in the table
  with their interval, and a reviewer can act on them.
- **Pull requests.** The job doesn't run on them. Branches aren't pushed,
  and outside contributions are rare.
- **Instruction counts** (`iai-callgrind`) would be noise-free and could
  gate tightly, but Valgrind doesn't run on macOS on Apple silicon. If
  wall-clock alerts turn out to be too noisy, the option is a Linux job
  for the portable core.

**When the Benchmarks run is red:** read the job summary.

- *Over budget* or *missing*: a real failure. Fix it or write an ADR.
- *Regression*: the canaries held still, so it is very likely real. Fix
  it. If the slowdown is deliberate (say, correctness bought with speed),
  say so in the task notes, and the next push compares against the new
  numbers.
- *Base benchmarks failed*: the base commit's benchmarks don't build or
  run any more (a toolchain change, say). Fix them or rerun with a
  different `base` input.

**When the run is green with an "inconclusive" warning:** the canary moved
on both attempts, so regressions weren't judged (budgets were). Check the
"regression? (noisy run)" rows; if there are any, rerun the job. If runs
are often inconclusive, the noise threshold is too tight for GitHub's
runners: record the canary numbers and loosen it.

`just check` doesn't run benchmarks, but clippy compiles them
(`--all-targets`), and the generator and report tests run on small inputs
(about 0.1 s). The full 100 MB file is only ever written by `just
reference-file`, `just bench` and `just bench-compare`.

## New dependencies

All in `leal-bench`, which never ships:

- **`criterion` 0.8.2** (dev-dependency): the benchmark framework CLAUDE.md
  names. It runs with default features minus `plotters`: charts aren't
  needed, CI reads the JSON, and the build is smaller.
- **`memchr` 2.8.3** (dev-dependency): the scan in the baseline. It is
  already in the lock file, and CLAUDE.md names it.
- **`serde_json` 1.0.151**: `bench-report` reads criterion's JSON with it.
  Criterion already depends on it, so it adds nothing to the build.

## Deviations and notes

- **"100 MB" is decimal:** 99,954,047 bytes (95.3 MiB), with a header plus
  1M data rows.
- **"Generating the file, then timing…" (PLAN):** generating the file isn't
  a criterion benchmark. It is set-up, and its time (0.2 s) is printed by
  `leal-refgen` and recorded above.
- **`just bench` used to be `cargo bench --workspace`.** It is now
  `cargo bench --package leal-bench -- <args>`. All benchmarks live in
  `leal-bench`. Running every crate's libtest harness in bench mode only
  printed "0 tests" lines, and it rejected criterion flags like
  `--save-baseline`. For the same reason, `leal-bench`'s library and
  binaries are `bench = false`.
- **No `mmap` benchmark.** Mapping needs `unsafe`, which belongs only in
  leal-core's `source` module (1.1). Once 1.1 lands, a benchmark for
  mapping and touching every page would add to this baseline.

## Open questions

- Are the 20% regression and 10% noise thresholds right for GitHub's
  runners? They are starting values until CI has a few weeks of history,
  and should then be tightened (see above). If inconclusive runs turn out
  to be common, the noise threshold should be loosened instead.
- Should the benchmarks be re-measured on a base M1 Air, the reference
  machine, before the phase 1 gate? This Mac is much faster.

## Rust notes

- **Benchmarks are their own build targets.** Each file in `benches/` is
  compiled as a separate program by `cargo bench`, in the `bench` profile.
  That profile inherits `[profile.release]` (`lto = "thin"`,
  `codegen-units = 1`), so benchmarks measure optimised code, the same as
  what ships. `harness = false` in `Cargo.toml` means "don't use the
  built-in test runner, the file has its own `main`". Criterion's
  `criterion_group!` and `criterion_main!` macros write that `main`
  (`benches/baseline.rs`, last two lines).
- **Criterion** runs a function many times, measures it, and works out the
  statistics: median, confidence intervals, outliers, and the change from
  the previous run. A *group* (`c.benchmark_group("baseline")`) shares
  settings, and the full id is `group/function`. `Throughput::Bytes` makes
  it report GiB/s as well as time. `SamplingMode::Flat` suits benchmarks
  that take milliseconds per iteration (`benches/common/mod.rs`).
- **`black_box`** (`std::hint::black_box`) tells the optimiser "assume this
  value is used, and assume you don't know what it is". Without it, the
  compiler could see that a result is never used and delete the work being
  measured. Or it could see a constant input and compute the answer at
  compile time. In `baseline.rs` it wraps the inputs (`black_box(&bytes)`)
  and the bytes read.
- **`mod common;` in a bench file** compiles `benches/common/mod.rs` into
  that benchmark program. Each bench file is a separate program, so this
  is how they share code without making it part of the library.
- **`env!("CARGO_MANIFEST_DIR")`** is filled in at compile time with the
  crate's directory. `reference::data_dir` uses it to find `target/` from
  any working directory. `env!("CARGO_TARGET_TMPDIR")`, used in the tests,
  is a scratch directory Cargo provides for integration tests.
- **Generic writers:** `reference::write<W: Write + ?Sized>(out: &mut W, …)`
  accepts anything that implements the `Write` trait. That can be a
  `Vec<u8>` (the tests), a `BufWriter<File>` (`generate`) or a socket. The
  compiler makes a specialised copy for each type, so this costs nothing at
  run time. `?Sized` also allows trait objects like `&mut dyn Write`.
- **`wrapping_add` and `wrapping_mul`** (the `Rng` in `reference.rs`):
  ordinary `+` and `*` on integers panic on overflow in debug builds. The
  random number generator relies on overflow wrapping around, so it says
  so explicitly.
- **Range patterns** like `0..530 => …` in a `match` (`write_notes`) match
  a number in that half-open range. The compiler checks that the arms
  cover every value.
- **Match guards** like `Verdict::Noisy if last_attempt => …` in
  `Report::outcome` (`src/report.rs`) match only when the condition after
  `if` is also true; otherwise the next arm is tried. Here the next arm,
  `Verdict::Noisy => Outcome::Rerun`, handles the other case.
- **`env!("CARGO_BIN_EXE_bench-report")`**, in `tests/report.rs`, is the
  path of the `bench-report` binary that Cargo builds before running the
  integration tests. The `bench_report_*` tests run it as CI does, with
  `GITHUB_ACTIONS` and `GITHUB_STEP_SUMMARY` set, and check its exit
  status, annotations and job summary.

## Budget-only benchmarks (added after 1.5)

`open/first_paint_removable_under_load` is gated on its 150 ms budget only,
never on change between commits (`report::BUDGET_ONLY`). On shared runners
its 95% interval spanned −30% to +60% between near-identical commits, and
+29% to +157% on another, so a change gate on it would fail CI for no real
reason. Its budget is still enforced on every run. Add a benchmark to
`BUDGET_ONLY` only with evidence like this, and say why here.
