# 1.2 Dialect and encoding detection

Detection decides how to read a file (DESIGN §3.2): encoding and where it
came from, BOM, delimiter, quote character, line endings, header row and
trailing newline. It follows ADR-0003 decisions 1, 6 and 7, ADR-0004
decision 11 and ADR-0005 decisions 1, 4 and 5.

## What was built

Three new public modules in `leal-core`:

| Module | What it holds |
|---|---|
| `dialect` | The vocabulary: `Delimiter`, `LineEnding`, `Bom`, `Encoding` (the 16 encodings of ADR-0005 decision 5, with their `CFStringEncoding` numbers and IANA names), `QUOTE`. |
| `attributes` | Parsing and writing the two attribute *values*: `parse_text_encoding` / `text_encoding_value` for `com.apple.TextEncoding`, and `Interpretation` (with `Fingerprint`) for `io.github.robhaswell.leal.interpretation`. The formats are documented at the top of `attributes.rs`. |
| `detect` | `detect` (first paint, P0), `review` (whole file, P2), and their inputs and outputs: `Hints`, `Choices`, `Detection`, `Review`, `EncodingSource`, `DialectSource`, `Note`, `ChoiceError`, `FIRST_PAINT_BYTES`. |

### The API

```rust
pub fn detect(file: &[u8], hints: Hints<'_>, choices: Choices) -> Result<Detection, ChoiceError>;
pub fn review(file: &[u8], detection: &Detection) -> Review;
```

Both are pure functions over bytes. Neither reads a file or an attribute;
`source` (1.1) passes the mapped file and the raw attribute values in
`Hints { text_encoding, interpretation }` (both `Option<&[u8]>`), so this
task doesn't depend on 1.1's types. Neither changes a byte.

- **`detect`** reads only the first `FIRST_PAINT_BYTES` (64 KB) of `file`,
  even when given the whole mapped file, so it touches only the first
  pages. If the file is longer, the last row of that window may be cut, and
  is dropped (so is a row ending in a CR at the very end, which could be
  half of a CR LF), a UTF-8 sequence cut by the limit is not counted as
  invalid, and `trailing_newline` is `None`.
- **`review`** reads the whole file once for the encoding rule and once for
  the rows (P2 work). It returns `encoding_suggestion`,
  `delimiter_suggestion`, and the whole file's `line_ending`,
  `mixed_line_endings` and `trailing_newline`. It never changes the
  `Detection`: the app shows the suggestion banners (ADR-0005 decisions 4
  and 8). It only second-guesses a *guess*: an encoding from the BOM, the
  user or a UTF-8/Windows-1252 attribute, and a delimiter from the user or
  the attribute, are left alone. The one exception is ADR-0004's "decodes
  under it" rule for the other single-byte encodings: first paint checks it
  on 64 KB, and the review checks the rest of the file.
- **`Choices`** is how the core accepts the user's delimiter, header or
  encoding (DESIGN §3.2, **Treat as**, the header toggle, **Reopen with
  encoding…**). Re-running `detect` with a choice re-reads line endings,
  trailing newline and header under it (`a;"b\n` has a trailing newline
  under `,` and none under `;`). A chosen encoding must agree with the BOM:
  a file with a BOM can only be read in the BOM's encoding, and UTF-16 only
  with its BOM (`ChoiceError::EncodingDoesNotMatchBom`).
- **`Detection`** carries `encoding_source` (`Bom`, `Attribute`, `Guess` or
  `User`) for the status bar (1.6), `delimiter_source` and `header_source`
  (`Attribute`, `Guess` or `User`), and `notes`: an unreadable, unsupported
  or UTF-16-without-BOM `com.apple.TextEncoding`, one whose single-byte
  encoding doesn't decode the bytes, and an unreadable or no-longer-fitting
  interpretation attribute. Each is ignored with its note.

### Encoding (ADR-0003 decision 1, ADR-0004 decision 11, ADR-0005 decisions 4 and 5)

In order: the user's choice; the BOM; the attribute; the guess on the first
64 KB. The attribute is matched by its `CFStringEncoding` number only (the
name before the `;` is ignored). A UTF-8 or Windows-1252 attribute is always
honoured, even over invalid bytes (which get 1.5's usual warning). Another
supported encoding is honoured only if every byte decodes under it
(`encoding_rs`'s tables; Windows-1253 has unassigned 0xAA, for example). A
UTF-16 number (256, or the LE/BE ones) without a UTF-16 BOM is ignored. With
a BOM, the attribute isn't consulted at all.

The CFStringEncoding numbers were checked against CoreFoundation on this Mac
with a small Swift program (`CFStringBuiltInEncodings`, `CFStringEncodings`,
`CFStringConvertEncodingToIANACharSetName`); the unit test
`cf_string_encoding_numbers_and_names_match_core_foundation` records them.

### Delimiter

Each of `,` `;` `\t` `|` splits the sample's non-blank whole rows with a
quote-aware scanner (`detect/rows.rs`, the §3.4 rules: a quote opens a field
only at its start, text after a closing quote is literal). A delimiter is a
candidate only if its most common field count is at least 2. The best is the
most consistent (share of rows with the most common count), then the one
whose quotes are well formed in more rows (no mid-field quotes, no text after
a closing quote, no quote left open), then the one with more fields, then
the order `, ; \t |`. With no candidate (one column, or empty), `,`.

The well-formed-quotes tie-break was added because a pipe file whose quoted
values hold commas (`a|"x,y"`) splits just as evenly under `,`; a property
(`the_delimiter_guess_finds_a_tidy_file_delimiter`) generates such files for
all four delimiters, and fails without it.

The review's delimiter check reads two more 64 KB samples, from the middle
and the end, each starting after its first line ending. It suggests a
delimiter if, on those samples, it is the best and the one in use doesn't
split them as consistently (or doesn't split them at all). A sample can
start inside a quoted field; quotes open only at a field's start, so this
rarely misreads more than a row or two, which is acceptable for a
suggestion.

### Header row

`detect/header.rs`. Each cell is a number (signs, currency, `%`, grouping,
decimal commas, exponents), a date or time, a boolean, empty, or text with a
*shape* (letter case, and whether it has digits, spaces or symbols). Each
column votes on the first row: **+1** if the column is mostly typed and the
first cell is text, or the column is text and no cell below has the first
cell's shape; **−1** if the column is text and the first cell is typed; 0
otherwise. A header needs a positive total, a non-blank first row and at
least one non-blank row under it (up to 200 are looked at).

The shape rule exists for `dialect/quoted-delimiters.csv`, whose columns are
all text (`name,address` over `Ada,"12 High St, London"`). A types-only rule
(like Python's `csv.Sniffer`) says no header there; the sidecar says yes,
and a person would too. Shapes only ever vote *for* a header, since text over
text is weak evidence, so `Ada,London` over `Bob,Paris` stays headerless.

### Leal's interpretation attribute (ADR-0005 decision 1)

Format (defined here, documented in `attributes.rs`):
`v=1;delimiter=semicolon;header=yes;file=1532-9f3c0e1d2b4a5867`. `v=1` comes
first; `delimiter` is `comma|semicolon|tab|pipe`, `header` is `yes|no`, and
`file` is the saved file's fingerprint: its length, `-`, and the FNV-1a 64
hash of its first 64 KB in 16 lowercase hex digits. Any key may be left
out; unknown keys are ignored; a repeated key or a bad value makes the whole
value unreadable.

"Honours it if the file still parses sensibly with it" is made precise as:

- while the file matches the fingerprint, it is the file Leal saved, so the
  attribute is used as is;
- otherwise (another program changed it, or there is no fingerprint), the
  remembered delimiter must split the rows at least as consistently as the
  best guess does, counting one field per row as consistent. If not, the
  whole attribute (header too) is ignored with a note: the file has
  probably been rewritten by something else.

**Why the fingerprint.** Without it, the reopen property (below) found a
file Leal had legitimately saved whose remembered delimiter would be
rejected: a two-row comma file ending in an unterminated quote, which under
`;` reads as one perfectly consistent row. The attribute is only ever
written when a reopen would guess differently, so a "does the guess agree"
test rejects it in exactly the cases it exists for. Bytes alone can't tell
"a one-column file whose values hold semicolons" from "a semicolon file", so
the fingerprint records which file the choice was made for. Checking it
costs one pass over the 64 KB first paint already reads. 2.5 writes
`Fingerprint::of(&saved_bytes)`.

## Tests

96 tests in `leal-core` (88 unit and integration tests, 8 doctests), under a second
in `just check`; `just test-deep` passes (20,000 cases per property; the
200 KB-file property runs 2,500).

- **Corpus** (`tests/detect_corpus.rs`): every one of the 43 sidecars, for
  delimiter, line ending, mixed line endings, BOM, encoding, trailing
  newline, header, encoding source and no notes, and `review` agrees with
  first paint on each. All match; no sidecar was changed.
- **Against the testkit oracle** (`tests/detect_properties.rs`): the encoding
  equals `expected_encoding` on arbitrary bytes, and `reopen_encoding` with
  a UTF-8, Windows-1252 or UTF-16 attribute; under the file's own delimiter,
  BOM, encoding, line endings, mixed and trailing newline equal the
  generator's layout (clean, messy and UTF-16 files) in `detect` and
  `review`; the guess finds the delimiter when no other delimiter byte
  appears; tidy files with other delimiters inside quoted values; and files
  repeated past 64 KB (first paint from 64 KB agrees with the whole, no
  suggestions).
- **Attributes and choices** (`tests/detect_hints.rs`): the three real-read
  cases the 0.2 notes ask for — an attribute that contradicts the guess (both
  ways), a UTF-16 attribute without a BOM (all three numbers), and a UTF-8
  attribute over invalid bytes — plus BOM-beats-attribute, the other
  single-byte encodings decoding or not, unsupported and unreadable values,
  every interpretation path, and user choices.
- **ADR-0005 decision 4** (also `detect_hints.rs`): generated files over
  64 KB whose later bytes change the guess, both ways (ASCII then a
  Windows-1252 byte; one Windows-1252 byte then lots of UTF-8). First paint
  guesses from 64 KB; the review suggests the other encoding. Also: a
  character cut by the limit, rows and CR LFs cut by the limit, first paint
  ignoring everything past 64 KB, and a delimiter suggestion from the middle
  and end.
- **Reopen property** (`tests/detect_reopen.rs`): the 0.2 obligation. It
  replays the testkit's edit cases and save oracle, models
  `com.apple.TextEncoding` from `SavedFile::encoding_hint` and the
  interpretation attribute the way 2.5 will write it (when a reopen would
  guess differently, or the choice came from the user, with the saved file's
  fingerprint), reopens with the real detector, and requires the same
  delimiter, header, encoding and BOM, with no notes.

## Benchmarks

PLAN 1.2 doesn't ask for a benchmark, so none was added to 1.2b's suite. A
one-off timing on a synthetic 100 MB file (about 1.2M rows × 12 columns with a
quoted multi-line field, release build, Apple M5 Pro): `detect` 0.66 ms,
`review` 143 ms. First paint's share of the 150 ms budget is negligible;
the review is P2 work. `review` streams the rows and keeps none of them.

## Decisions and deviations

- **The reopen check lives in `leal-core/tests/detect_reopen.rs`**, not in
  the testkit's reopen property as the 0.2 notes put it: the testkit must
  never call product code, and checking the *detector* needs it. It uses
  the testkit's edit cases and save oracle unchanged.
- **The interpretation attribute has a `file` fingerprint** (see above).
  This is a format detail this task was asked to define, and a reading of
  ADR-0005's "still parses sensibly", not a change to it. If Rob would
  rather have it in an ADR, the reasoning above is ready to move.
- **ISO-8859-1** is decoded by hand (byte = code point): the WHATWG
  standard, and so `encoding_rs`, treats the label `iso-8859-1` as
  Windows-1252. 1.4 must keep the two apart for display.
- **ASCII** (`us-ascii;1536`) is not in ADR-0005's list, so an ASCII
  attribute is "unsupported" and noted. It never changes the outcome (an
  ASCII file guesses UTF-8), but the note may be noise; see open questions.
- The 0.3 skeleton's `inspect` module is untouched (1.1 replaces it).

### Testkit conventions (0.2 notes, "Open when written")

Confirmed for the product, without an ADR:

- **`,` for a file with no delimiter** (one column, or empty). It is also
  what ADR-0004 decision 3 does for line endings (LF when there is none),
  and the delimiter only matters once a column is inserted.
- **`header = false` for a single-row file.** With nothing under it there's
  no evidence, and showing the only row as data hides nothing. The user can
  turn the header on.
- **A final odd byte in a UTF-16 file is `invalid_encoding`** at its own
  offset and displays as U+FFFD. It is an incomplete code unit, the same
  kind of invalid text as ADR-0003 decision 7's unpaired surrogate. Detection
  ignores the byte (it is no whole unit); 1.4 and 1.5 implement the
  diagnostic and the display.

## Open questions

- Should an ASCII `com.apple.TextEncoding` (`us-ascii;1536`, which TextEdit
  can write) be read as UTF-8 rather than noted as unsupported? ASCII is a
  subset of every supported encoding, so it would be safe; it would need a
  line in ADR-0005 decision 5's list.
- Wiring with 1.1: `source` should pass the raw `com.apple.TextEncoding`
  and `io.github.robhaswell.leal.interpretation` values into
  `Hints`. An end-to-end test with a real attribute on a real file belongs
  with whichever of 1.1 and 1.2 lands second (or 1.6).

## Rust notes

- **Enums with data** (`detect/mod.rs`, `Note`; `attributes.rs`,
  `TextEncodingError`). Some variants carry values:
  `Note::TextEncodingUnsupported { cf_string_encoding: u32 }` says *which*
  encoding wasn't supported. A `match` on it must handle every variant, so
  the compiler points at every place to update when a new note is added.
- **Pattern matching on slices** (`dialect.rs`, `Bom::detect`):
  `[0xEF, 0xBB, 0xBF, ..]` matches a slice that *starts* with those three
  bytes, whatever follows (`..`). It replaces several `starts_with` calls
  and can't index out of bounds.
- **Patterns in `match` with `@` and `|`** (`choose_encoding`):
  `Ok(e @ (Encoding::Utf8 | Encoding::Windows1252))` matches either variant
  and binds it to `e`. A guard (`Ok(e) if decodes(body, e)`) adds a
  condition to an arm.
- **`let ... else` and `if let ... && ...`** (`remembered`): `let Some(value)
  = value else { return ... };` unwraps or leaves the function early, and
  `if let Some(d) = interpretation.delimiter && !unchanged && ...` chains a
  pattern with conditions (new in the 2024 edition).
- **Slices and borrowing** (`detect/units.rs`). `Units<'a>` holds a `&'a
  [u8]`: a view into the file's bytes, not a copy, so scanning a 100 MB
  mapped file allocates nothing. `'a` ties the view to the bytes, so the
  compiler won't let a `Units` outlive the file. `Hints<'a>` does the same
  for the attribute values.
- **Writing an iterator** (`detect/rows.rs`, `impl Iterator for Rows`). A
  type becomes an iterator by implementing one method, `next`, which returns
  `Some(row)` or `None` at the end. Everything else (`map`, `filter`,
  `take`, `collect`, `last`) then comes for free. `review` uses this to
  stream every row of a large file without keeping them.
- **Iterator chains** (`detect/delimiter.rs`, `splits`):
  `whole_rows(..).into_iter().filter(|r| !r.is_blank()).map(|r| ...).collect()`
  reads as "keep the non-blank rows, turn each into a `Split`, gather them
  into a `Vec`". The closures (`|r| ...`) are small anonymous functions.
  `fold` (`attributes.rs`, `Fingerprint::of`) carries a running value through
  the bytes: there, the hash.
- **Closures as arguments** (`delimiter::scores(rows: impl Fn(Delimiter) ->
  Vec<Split>)`). The caller passes the *how*: first paint passes
  `|d| splits(units, d, cut)`, the review passes a closure that reads the
  middle and end samples. `impl Fn(...)` means "any function or closure with
  this signature".
- **`Option` helpers** in place of `if`/`else`: `(!cut).then(|| ...)` is
  `Some(...)` only if not cut; `.then_some(x)`; `.filter(...)`;
  `.is_some_and(...)`; `.is_none_or(...)`; `.map_or(default, f)`.
- **`Ordering` and `then_with`** (`Score::rank_cmp`): comparisons return
  `Less`, `Equal` or `Greater`, and `a.then_with(|| b)` uses `b` only when
  `a` is `Equal`. That is a sort key with tie-breaks, in one expression.
- **Copy types passed by value** (`detect(file, hints, choices)`). `Hints`
  and `Choices` are small and `Copy`, so they are passed by value rather than
  by reference; clippy's `trivially_copy_pass_by_ref` insists for `Choices`
  (3 bytes).
- **`std::mem::take`** (`rows.rs`): returns a variable's value and leaves the
  default (`false`) in its place, in one step.
- **`encoding_rs`**: each encoding is a `&'static Encoding`.
  `decode_without_bom_handling(bytes)` returns the text (with U+FFFD for
  bytes that don't decode) and whether any didn't; the
  `..._without_replacement` form returns `None` instead, which is how
  `decodes` builds its 256-entry table of assigned bytes.
- **`str::utf8_chunks`** (`detect/encoding.rs`): splits bytes into runs of
  valid UTF-8 and the invalid bytes between them, which is exactly what the
  ADR-0003 count needs. `.peekable()` lets the loop ask "is this the last
  chunk?" without consuming the next one.
- **`pub(crate)`** marks items (the scanner, the scores) visible inside
  `leal-core` but not to the app or other crates; only `detect`, `review`
  and their types are the public API.
- **Integration tests sharing code** (`tests/common/mod.rs`): each file in
  `tests/` is its own crate; shared helpers go in a subdirectory module that
  each test includes with `mod common;`. Here they convert between the
  testkit's types and leal-core's, which are deliberately separate copies.
- **A hand-built proptest runner** (`a_large_file_is_detected_from_its_first_64_kb`):
  the `proptest!` macro always lets `PROPTEST_CASES` override the case
  count, so a test that needs fewer, larger cases builds a `TestRunner`
  itself.
