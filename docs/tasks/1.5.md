# 1.5 Diagnostics

## What was built

### `leal_core::diagnostics` (`crates/leal-core/src/diagnostics/`)

Every diagnostic kind in DESIGN §3.5, collected during the row index's
single pass (DESIGN §3.3), exactly as ADR-0003 decisions 4, 5 and 7 and the
corpus sidecars define them. The module only describes: it reads the bytes
and never changes them.

| File | What it holds |
|---|---|
| `mod.rs` | The public API: `DiagnosticKind`, `Severity`, `Location`, `Diagnostic`, `Report`, `Diagnostics`, `MAX_LOCATIONS`. The module docs give the rules and how reports behave while indexing. |
| `collect.rs` | The `Collector`, the index scanner's observer: bounded tallies, the ragged-row candidates, and the `Finder`s that look for NULs and invalid text. |
| `marks.rs` | `RowMarks`: one byte per row, for "does this row have a warning?" on every row (added after review; see "Row marks"). |
| `tests.rs` | 39 tests (12 of them property tests), plus 2 doctests in `mod.rs`. |

The scanner (`index/scan.rs`) gained the hook points 1.3 marked
`HOOK(1.5)`: its `RowObserver` trait now hears about each chunk, each
stretch of units it passes, text after a closing quote, the unterminated
quote, each row end and each publish. `index/mod.rs` gained the two
constructors below.

**Public API:**

```rust
// On the calling thread (tests, the CLI's `leal check` in 4.3):
let (index, report) = RowIndex::build_with_diagnostics(bytes, dialect, encoding)?;

// Progressively, as the app will (1.3a puts the indexer on its own thread):
let (index, diagnostics, indexer) = RowIndex::start_with_diagnostics(dialect, encoding)?;
indexer.run(bytes, &cancel, |progress| { … })?;   // unchanged from 1.3
let report: Arc<Report> = diagnostics.report();   // any time, from any thread

// Gutter markers and Next/Previous over every row (1.7):
diagnostics.row_has_diagnostic(row)            // bool: any warning or error in the row
diagnostics.next_row_with_diagnostic(from)     // Option<usize>: first marked row >= from
diagnostics.previous_row_with_diagnostic(to)   // Option<usize>: last marked row < to

report.diagnostics()        // &[Diagnostic], in DiagnosticKind::ALL order, only kinds found
report.get(kind)            // Option<&Diagnostic>
report.rows()               // the rows this report covers
report.is_complete()        // true once the whole file is indexed
report.shows_banner()       // any warning or error (DESIGN §3.5)
report.kinds_at_least(Severity::Warning)   // "This file has N kinds of irregularity"

diagnostic.kind() / severity() / count()   // count covers every occurrence
diagnostic.first()          // &[Location { row, offset }], at most MAX_LOCATIONS (1,000)

DiagnosticKind::ALL / kind.severity()
```

`encoding` is `dialect::Encoding`, the same type the row parser takes (see
"Seam with 1.3a"). A new error, `IndexError::EncodingMismatch`, refuses an
encoding whose code unit doesn't match the dialect's (UTF-16 with byte code
units, or the other way round). `RowIndex::build` and `RowIndex::start` are
unchanged and collect nothing.

### What each kind is

These are the testkit's `DiagnosticKind` definitions and the README's kinds
table, unchanged:

| Kind | Severity | One per | Location |
|---|---|---|---|
| `UnterminatedQuote` | Error | file | the opening quote |
| `RaggedRows` | Warning | non-blank row whose field count isn't the mode (ties: first seen) | row start |
| `TextAfterClosingQuote` | Warning | field | first unit after the closing quote |
| `InvalidEncoding` | Warning | field | first invalid byte (UTF-16: the unit's first byte) |
| `NulBytes` | Warning | field | first NUL (UTF-16: a U+0000 unit) |
| `MixedLineEndings` | Info | row whose line ending isn't the most common (ties: first seen) | start of that line ending |
| `BlankLines` | Info | row with no bytes before its line ending, anywhere | row start |
| `BomPresent` | Info | file | row 0, offset 0 |

### How field-level kinds are found (the 1.4 open question)

Text after a closing quote, invalid encoding and NUL are per field, but the
index's scan never splits rows into fields; it only counts delimiters. 1.4
asked whether 1.5 should run the row parser over every row (about 100 ms
more for the reference file) or add field boundaries to the scan. I did
neither, because both pay for every field of every row, and these
diagnostics are rare:

- **Text after a closing quote** needs no search. The scanner already
  stops at every closing quote, so it checks the one unit after it (a
  delimiter, CR, LF or the end of the file means no text). That's one or
  two comparisons per quoted field.
- **NUL and invalid text** are found by searching each chunk's bytes with
  fast whole-slice searches, *not* by looking at fields: `memchr` for 0x00,
  and `simdutf8` (SIMD UTF-8 validation) for invalid UTF-8. In a clean file
  they find nothing, and the scanner's hook costs one comparison per
  stretch of units it passes ("is the next hit before the end of this
  stretch?").
- **Only a hit is placed in its field.** The scanner reports each stretch
  with its row, the field it starts in, and whether it is inside quotes.
  For a hit in a stretch outside quotes, the collector counts the
  delimiters between the stretch's start and the hit; inside quotes, the
  hit is in the stretch's field. A hit in the same `(row, field)` as the
  last one isn't counted again.
- **A field full of NULs costs no more than one with a single NUL.** After
  a hit, the search jumps to the next delimiter, CR or LF (every field
  boundary is one of those), so it doesn't stop at every NUL in the field.
- **When nearly every field has a hit** (see "Worst cases"), the next
  boundary and the next hit are a few bytes away, and starting `memchr3` or
  the SIMD validator once per field costs more than the search itself. So
  both searches look at the first 64 bytes one unit at a time (UTF-8 with
  the standard library's validator, which is quick on short slices) and
  start the fast search only past that. That made the worst files 1.3 to 3
  times faster.

Chunk boundaries need care, because a sequence can straddle one. Each
search window runs a little past the chunk's end: 3 bytes for UTF-8 (the
rest of a 4-byte sequence) and 2 for UTF-16 (the low surrogate after a high
one). A sequence the window still cuts off can only start at or after the
chunk's end, so the next window decides it before the scanner gets there.
A search that has to resume in the middle of a character (only after a hit
whose field runs past the window) can make a false hit at that point, but
there is no field boundary between it and the real hit, so it is never
counted. The tests put chunk boundaries at every byte.

**Why not a separate P2 pass?** DESIGN §3.10 lists "diagnostics details"
as P2 work. With this approach the whole job costs about 13 ms on the
reference file (see "Benchmark"), and with smaller chunks even the worst
files keep each chunk under 2 ms here, so a second pass over the file, with its
own scheduling, cancellation and a second read of 100 MB, would cost more
than it saves. The index is already P1 work, so first paint isn't affected
either way.

### Ragged rows without keeping every row

Which rows are ragged depends on the most common field count, which isn't
final until the end. Keeping every row's count would be 1M entries for the
reference file. Instead the collector keeps only rows that could be among
the first 1,000 ragged rows, *whatever* count ends up most common:

- row `p` with `c` fields can be one of the first 1,000 ragged rows for a
  final mode `m` only if `c ≠ m` and fewer than 1,000 earlier rows don't
  have `m` fields;
- after 2,000 rows, at most one count can satisfy that (a count with more
  than `rows − 1,000` rows is a strict majority), and it must be the
  current mode.

So a row is kept if it is among the first 2,000 non-blank rows, or if its
count isn't the current mode's and at most 1,000 rows so far differ from
the mode. That is at most 3,000 rows (72 KB), and the first 1,000 ragged
rows are among them both for the final mode and for every earlier one. The
count is exact: non-blank rows minus the rows with the mode's count (the
index's field-count tally, which the collector reads, so the index and the
diagnostics never disagree about the mode). Tests flip the mode after 1,500
rows, after 2,300 rows, and start the ragged rows only after 2,500 rows.

Mixed line endings have the same problem with only three line endings, so
the collector keeps a tally (count and first 1,000) for each, and merges
the two that aren't dominant.

### Row marks (added after review): every affected row, not only 1,000

The report's lists stop at 1,000 locations per kind, but the gutter marks
every row with a warning or an error (ADR-0002 question 7), so 1.7 needs
that for every row. The coordinator decided the core keeps a compact
per-row set, built in the same pass: `row_has_diagnostic(row)`,
`next_row_with_diagnostic(from)` and `previous_row_with_diagnostic(to)`.
Info-level kinds (blank lines, mixed line endings, the BOM) mark nothing.

**It is one byte per row, not one bit** (`marks.rs`), because of ragged
rows. Whether a row is ragged depends on the most common field count,
which can change until the last row. A bit set against the mode so far
would be wrong for every earlier row once it changes, and fixing that
needs each row's field count, which the pass doesn't keep. So each row
keeps:

- bit 7: a field-level warning (text after a closing quote, invalid
  encoding, NUL) or the unterminated quote, known when the row ends;
- bits 0–6: the field count (0 for a blank line, which is never ragged),
  or 127 for "127 or more", whose exact count goes in a side list of
  `(row, delimiters)` pairs. A row with 127 fields has at least 126 bytes,
  so that list holds at most one 8-byte entry per 126 bytes of the file,
  and in practice only rows of very wide files.

"Ragged" is decided when asked, against the current mode, so the marks are
right while indexing (against the mode so far, like the report) and at the
end. That is 1 MB per million rows, a quarter of the row index's 4 MB; a
bitset would be 125 KB but could not be both exact and one pass. The marks
are published with each report, under the same lock.

`next_…` and `previous_…` read one byte per row and skip 64 rows at a time
with a vectorised check, so a search is about a millisecond per few
million rows. When the mode is 127 fields or more, wide rows need a lookup
in the side list (a binary search), which only very wide files pay.

### Memory

Every diagnostic keeps its count and at most `MAX_LOCATIONS` (1,000)
locations of 16 bytes: 16 KB per kind, 128 KB if all eight are full. With
the ragged candidates (72 KB) the collector is under 250 KB however large
or messy the file. On top of that, the row marks take a byte per row (1 MB
for the reference file). A published report is a copy of those lists, made
once per chunk and shared as an `Arc`, so readers copy nothing.

### While indexing (PLAN 1.5: ragged rows and hatched cells)

`diagnostics.report()` while the indexer runs describes **exactly the rows
indexed so far** (`report.rows()`, the same count `index.row_count()` gave
at that publish). It equals what a complete index of just those rows would
report: occurrences found in the row being scanned are held back until it
ends (each field-level tally knows how many of its occurrences are in the
last row it saw). The row marks likewise cover finished rows only. A
property test checks both after
every chunk, with chunks from 1 byte up, on generated UTF-8, Windows-1252
and UTF-16 files and on arbitrary bytes.

So, before the index finishes:

- **Ragged rows** are relative to the most common field count *so far*,
  `index.field_count_mode()`, which is the same tally. If later rows change
  the mode, rows that were ragged stop being ragged and others start, and
  the count can go down as well as up. The **hatched cells** of short rows
  and the extra "Column N" of long rows (ADR-0002 question 5) follow the
  same provisional mode: the grid should draw them from
  `index.field_count_mode()` at draw time and redraw on the progress
  callback, so hatching, gutter markers and the banner always agree. In
  practice the mode is settled by the first chunk: it only moves if the
  start of the file is unlike the rest.
- **Mixed line endings** are relative to the most common line ending so
  far, in the same way.
- An **unterminated quote** is known only at the end of the file. Until
  then its rows look like one growing row, and nothing is reported.
- **Every other kind only gains occurrences**: a location, once reported,
  stays.
- The final report has `is_complete()`. A cancelled or failed run leaves
  its last report incomplete, describing the rows indexed before it
  stopped.

Both the rows and the report are published after a chunk and before the
progress callback, so 1.3a can treat the callback as the moment both are
up to date.

### Clarifications and decisions beyond the ADRs

- **Clarification of ADR-0003: unmapped bytes in single-byte encodings
  are `invalid_encoding`** (decided by the coordinator after review). ADR-0003
  covers UTF-8, Windows-1252 and UTF-16, but ADR-0005 decision 5 added
  other code pages, some of which leave bytes unmapped (Windows-1253 0xAA,
  0xD2 and 0xFF, for example). 1.4 displays those as U+FFFD, and the intent
  of ADR-0003 is that nothing is silently lossy, so each field with one is
  `invalid_encoding` once, located at its first such byte, exactly as for
  invalid UTF-8. The collector builds each code page's unmapped bytes from
  `encoding_rs`'s own tables, the ones display uses. Tests: every byte of
  every encoding is reported if and only if it displays as U+FFFD
  (Windows-1252, ISO-8859-1 and Mac Roman map every byte, so never), and a
  Windows-1253 file with unmapped bytes in plain, quoted and Greek-text
  fields (`windows_1253_unmapped_bytes_are_invalid_once_per_field`). It
  only affects encodings that come from the attribute or **Reopen with
  encoding…**, never detection's three.
- **A NUL delimiter or quote turns NUL diagnostics off.** `RowIndex`
  accepts 0x00 as a delimiter or quote, and then 0x00 is structure, not
  text. The testkit counts such a byte "on its own" (its own fallback, for
  a case it says can't happen). Detection never picks one (DESIGN §3.2),
  so the collector just doesn't report NULs then.
- **The banner's count.** `kinds_at_least(Severity::Warning)` is offered
  for "This file has N kinds of irregularity", since info-level kinds don't
  show the banner. 1.7 decides the wording.

## Tests

All in `crates/leal-core/src/diagnostics/tests.rs`, written before the
collector did anything. Against a stub that reported nothing, 25 of the 32
tests failed (the 7 that passed check errors, empty files and type
properties). Expected answers come from the testkit: the corpus sidecars,
the generator's diagnostics, and `leal_testkit::diagnostics::derive` (the
testkit's definition of each kind). The testkit's reference parser is never
used, and no testkit code is in the product.

- **Every corpus sidecar** (43 files): exactly the kinds listed and no
  others, each count, the first locations (and that all of them are kept up
  to 1,000), and each severity against the testkit's. The same report must
  come from `build_with_diagnostics` and from the progressive path with
  chunks of 1, 2, 3, 5 and 16 bytes and 1 MiB. Every kind appears in the
  corpus. **No sidecar or oracle problems found.**
- **Generated files** (properties, 256 cases each, 20,000 in `test-deep`):
  clean and messy `csv_file` (UTF-8, and Windows-1252 when the ADR-0003
  rule says so), messy `csv_file_utf16` (LE and BE), and messy files with
  long values. The whole report must equal the generator's `diagnostics`,
  with random chunk sizes from 1 byte and with 1 MiB chunks.
- **Any bytes** (`csv_bytes`, any of the four delimiters, as UTF-8,
  Windows-1252, UTF-16 LE or UTF-16 BE): the report must equal `derive`
  over the layout the 1.4 row parser finds. This reaches what the generator
  doesn't: unpaired surrogates, final odd bytes, NULs and invalid sequences
  next to delimiters and quotes, BOMs mid-file.
- **Thousands of occurrences** (48 cases of up to 5,000 rows of mostly two
  or three fields, so the mode changes often, with blank lines, all three
  line endings, NULs, invalid bytes and text after quotes, in chunks up to
  4 KB): equal to `derive`, and a check that such files really do go over
  1,000 ragged rows, mixed line endings and blank lines.
- **While indexing:** the property above (every published report describes
  exactly the rows so far), three hand-built mode changes, a cancelled run,
  and the report before the indexer runs.
- **Hand-written cases:** an empty file; a BOM alone and with rows (info
  only, no banner); an unterminated quote with NULs past a quoted newline;
  NULs, invalid bytes and text after a quote counted once per field; 1,500
  NUL fields (count 1,500, 1,000 locations); UTF-8 split across every chunk
  boundary, and cut off at the end of the file; UTF-16 NUL units (not the
  0x00 bytes of ASCII), a surrogate pair across chunks and a lone low
  surrogate; text after a closing quote that is a final odd UTF-16 byte;
  every unmapped byte of every single-byte encoding; NULs in Windows-1250;
  a NUL delimiter and quote; UTF-16 without a BOM read as Windows-1252;
  line-ending ties; blank lines never ragged; mismatched encodings; the
  kinds and severities against the testkit's table.
- **Row marks** (after review): every property and corpus-style check
  above that compares a whole report also checks every row's mark, and the
  next and previous marked rows from a spread of rows, against marks worked
  out independently: ragged rows, text after a closing quote and the
  unterminated quote from the row parser's layout, and NULs and invalid
  text from the testkit's *untruncated* offset lists
  (`invalid_utf8_offsets`, `utf16_nul_and_invalid_offsets`). That includes
  the 5,000-row files (more than 1,000 occurrences of a kind) and every
  report while indexing. Hand-written: rows of 127 fields and more in a
  wide file (mode 200) and in a narrow one (mode 3); a mark on every 500th
  and 501st row of 5,000 with info-level kinds marking nothing; 2,500 NUL
  rows, so marks past the 1,000th location.

## Benchmark

`crates/leal-bench/benches/index.rs`, on the 1.2b reference file (100 MB,
1,000,001 rows, in memory). Same machine as 1.2b–1.4: `Mac17,8`, Apple M5
Pro. This is **not** the reference machine (a base M1 Air, which is
slower). "Before" is `main` today, measured with `--save-baseline` before
any change; "after" is from a full `just bench` run at the end, which
`bench-report` lists as `ok` against every budget.

| Benchmark | Before | After | |
|---|---|---|---|
| `index/build` | 42.3 ms | 41.0 ms | unchanged: without diagnostics the hooks compile away |
| `index/run` | 40.9 ms | 41.0 ms | unchanged |
| `index/build_diagnostics` | — | **53.2 ms** | budgeted, 500 ms |
| `index/run_diagnostics` | — | **53.5 ms** (54.1 ms after review, with 256 KiB chunks) | budgeted, 500 ms; reads the report after every chunk, as the UI will |

- **Diagnostics cost about 12.5 ms (+30%)** on the reference file. Most of it
  is the two searches: SIMD UTF-8 validation (about 8.5 ms for 100 MB of
  mostly-ASCII text with many accented names) and `memchr` for NUL (about
  1.2 ms); the rest is the per-row bookkeeping. With `std::str::from_utf8`
  instead of `simdutf8` the validation alone took 18 ms (measured in a
  scratch program, 1 MiB chunks).
- **Budget: 500 ms. Result: 53.5 ms**, 9× headroom on this Mac. The 1.3 notes
  expect the M1 Air to be 2–3× slower, which still leaves plenty.
- Two new budgets in `src/budgets.rs`: `index/build_diagnostics` and
  `index/run_diagnostics`, both 500 ms (DESIGN §1). The app indexes with
  diagnostics, so these are the numbers the budget is really about.

Worst cases and UTF-16, not budgeted (DESIGN §1's budget is for the
reference file):

| Benchmark | File | Median |
|---|---|---|
| `index/run_diagnostics_nul_heavy` | the first half of the reference file as UTF-16 LE without a BOM (99 MB), read as Windows-1252: every one of its millions of fields holds NULs | 120 ms |
| `index/run_utf16` | the same text with a UTF-16 LE BOM, read as UTF-16, no diagnostics | 25.1 ms |
| `index/run_diagnostics_utf16` | the same with diagnostics | 39.5 ms |

UTF-16's searches look at code units, so they can't use `memchr` or
`simdutf8`. They first skip 64-byte blocks that can't hold a hit, with a
fixed-size check the compiler vectorises; that brought UTF-16 diagnostics
from 35 ms to 15 ms per 99 MB.

### Worst cases (after review)

`nul_heavy` isn't the worst case: files where *every* field or every row
is an occurrence are. The `worst` group (`benches/index.rs`) indexes four
100 MB files with diagnostics and without (`_plain`), and prints the
longest chunk of two warm runs (DESIGN §3.10 rule 3: chunks of at most
about 5 ms). Not budgeted, since they are pathological. Same Mac.

| File (100 MB) | Plain | First version | After review | Longest chunk, first version → after |
|---|---|---|---|---|
| `invalid_utf8`: `\xFF,` repeated (UTF-8) | 14 ms | 747 ms | **240 ms** | 8.5 → 0.7 ms |
| `invalid_and_nul`: `\xFF\0,` (UTF-8) | 14 ms | 509 ms | **339 ms** | 8.2 → 1.7 ms |
| `unmapped_1253`: `\xAA,` (Windows-1253) | 14 ms | 274 ms | **209 ms** | 3.8 → 1.2 ms |
| `blank_lines`: 100M `\n` (UTF-8) | 266 ms | 631 ms | **574 ms** | 6.9 → 1.7–2.7 ms |

- Every chunk stays under 3 ms here, so under ~5 ms on an M1 Air if it is
  2× slower, with 256 KiB chunks (`DIAGNOSTICS_CHUNK_BYTES`). At 1 MiB they
  reached 8.5 ms here.
- What's left is per occurrence: about 4–7 ns per field with a hit, or per
  row. The plain index pays none of that, which is why it is 15–40 times
  faster on these files. Doing better would mean finding hits and
  boundaries with bitmasks over 64-byte blocks, which isn't worth it for
  files like these.
- The smaller chunks cost the reference file about 1 ms
  (`index/run_diagnostics` 53.5 → 54.1 ms).
- The blank-lines numbers are the noisiest (2.7 ms was measured as the
  machine got busy; 1.7 ms on a quiet run).

**After joining 1.3a** (final `just bench`, same Mac, Time Machine
running): the reference file `index/run_diagnostics` 54.8 ms against
`index/run` 42.3 ms; `invalid_utf8` 243 ms, `invalid_and_nul` 340 ms,
`unmapped_1253` 190 ms, longest chunks 0.6–1.1 ms. `blank_lines` is
slower than before the rebase, 684 ms (plain 308 ms, was 266), with a
longest chunk of 2.5–2.9 ms: 1.3a's `View` costs the scanner a little per
row, and the collector's row hook a little more. Still inside the chunk
rule here. **First paint under load** (1.3a's `open` group, budget
150 ms): 1.97 ms, and 2.2 ms on the simulated removable drive; the extra
`Diagnostics` made at first paint costs nothing measurable (1.3a's notes
give the earlier numbers).

## New dependencies

- **`simdutf8` 0.1.5** (MIT/Apache-2.0) in `leal-core`, for finding invalid
  UTF-8 during the index's pass. Its `compat` API gives exactly the error
  positions `std::str::from_utf8` gives (`valid_up_to`, `error_len`), which
  the testkit's sequences follow, and it is about twice as fast on the
  reference file (8.5 ms against 18 ms). It was already in the build:
  `encoding_rs` depends on it, so `Cargo.lock` gains only the edge, and
  `cargo tree -p leal-core -e normal` lists the same crates as before.

## Joined with 1.3a (the scheduler)

1.3a landed first, so 1.5 was rebased onto it and wired in at its
`SEAM(1.5)` comments (now removed).

- **The scanner reads through a `View`** (a slice and its offset in the
  file) since 1.3a. The observer hooks take the view instead of the whole
  file's bytes, and the finders search `view.slice(from, to)`; every
  location is still a file offset.
- **Chunk by chunk, on a removable drive.** `ChunkedIndexer` (fed by
  `Source::stream`) now carries a collector when its indexer has
  diagnostics, so its state, like the scanner's, survives from one chunk
  to the next. The finders read up to 3 bytes past the point a scan stops,
  but the chunked scan used to keep only one unit back. So the observer
  says how far it looks (`RowObserver::LOOKAHEAD`: 4 for the collector, 0
  by default), and the chunked scan holds that many bytes back for the
  next chunk. Without diagnostics nothing changes (1.3a's chunk tests,
  which check how far a tiny chunk gets, still pass). A UTF-8 sequence or
  surrogate pair cut by a chunk boundary is judged when the next chunk
  arrives. Tests: properties over generated and arbitrary files cut into
  chunks of 1 to 39 bytes (report and marks after every chunk, and equal
  to the whole-file answer at the end), and every pair of cuts of a short
  file full of straddling sequences. Setting the collector's `LOOKAHEAD`
  to 1 fails three of them.
- **The P1 job.** Each reading's indexer comes from
  `RowIndex::start_with_diagnostics(dialect, detection.encoding)`, so the
  index job collects diagnostics on both paths. On a removable drive the
  stream's 1 MiB chunks are pushed in `DIAGNOSTICS_CHUNK_BYTES` pieces, so
  a stretch of work between checkpoints is no longer than on a mapped
  file. No P2 job: the second `SEAM(1.5)` (in `start_checks`) now says so.
  Progress is reported per 256 KiB chunk instead of per 1 MiB (1.3a's
  progress test changed to match).
- **`Document`** (`leal-core`): `diagnostics()` (the current reading's
  `Arc<Report>`), `diagnostics_with_generation()`, `row_has_diagnostic`,
  `next_row_with_diagnostic` and `previous_row_with_diagnostic`.
  `reinterpret` starts them again with the new reading. Tests: a messy
  file of about 800 KB opened normally, and one of 700 KB through
  `Source::open_simulating_removable` with 4093-byte chunks. Both reports
  and every row's mark equal a whole-slice index of the same bytes, with
  more than 1,000 marked rows; after reinterpreting as Windows-1252 the
  invalid bytes are gone.
- **FFI** (`leal-ffi`): `Document.diagnostics()` returns a
  `DiagnosticsReport` record (generation, rows covered, complete,
  `showsBanner`, `bannerKinds`, and each `Diagnostic`'s kind, severity,
  count and first locations), and `rowHasDiagnostic(row:)`,
  `nextRowWithDiagnostic(from:)` and `previousRowWithDiagnostic(to:)`. New
  `DiagnosticKind` and `Severity` enums. Tested in Rust and by an XCTest
  through the generated Swift (`testDiagnosticsReachSwift`). One trap
  found: a doc comment with `**Previous**/**Next**` broke the generated
  Swift, which puts docs in `/* … */` comments.
- **Cancelling** works as in 1.3: a cancelled run's last report stays
  readable and incomplete.
- **`dialect::Encoding`.** Diagnostics take the same encoding type as the
  row parser, so that the encoding that decides what displays as U+FFFD
  and the encoding that decides what is reported as invalid are the same
  value. (Written against 1.4's provisional `rows::Encoding`; 1.3a replaced
  it with 1.2's `dialect::Encoding`, and the rebase followed.) The
  collector uses `Encoding::code_unit` and `Encoding::whatwg`, the decoder
  table display values use.
- **Re-indexing** with another delimiter or encoding (1.2, 1.7) means new
  diagnostics: call `start_with_diagnostics` again.
- **1.3 open question** ("should the index store line endings for mixed
  line endings?"): no. The collector hears each row's line ending in the
  pass and keeps what it needs.

The integration review approved the join with 1.3a. It ran 15,900
release cases comparing every chunking pattern (including the

## First-paint regression

**What CI saw.** The benchmark run for `982edcf` (this task, on `main`)
against `d10d535` flagged `open/first_paint` at 5.97 ms, +91.8% (+81.4% to
+113.2%), and `open/first_paint_under_load` at 6.55 ms, +81.6%. The
canaries didn't move. The raw samples (the run's criterion artifact) are
about twice the base's throughout the measurement, not a burst.

**It doesn't reproduce here.** On the development Mac (M5 Pro, 18 cores,
48 GB), base against `982edcf`, with the bench binaries of both:

| Setup | `first_paint` base → 1.5 | `under_load` base → 1.5 |
|---|---|---|
| Plain | 1.59 → 1.54 ms | 2.03 → 2.04 ms |
| 15 spinning processes | 2.13 → 2.13 ms | 2.37 → 2.49 ms |
| `taskpolicy -c background` | 5.23 → 5.31 ms | 11.6 → 12.2 ms |
| Pool of 2, bench at utility QoS, 15 default-QoS spinners | 4.61 → 4.51 ms | 4.79 → 4.73 ms |
| Pool of 2, 15 user-interactive spinning threads | 1.79–1.98 → 1.75–2.68 ms (4 runs, noise) | 1.85 → 1.84 ms |

(The pool size came from a scratch patch to the bench, not committed.)

**What 1.5 added to P0.** `read_first_paint` called
`RowIndex::start_with_diagnostics` instead of `RowIndex::start`, which made
an empty `Diagnostics` (a `RwLock` holding an `Arc<Report>` and empty
`RowMarks`): two small allocations and no preallocation sized from the file.
Nothing else on the first-paint path changed. Nothing allocates the marks
up front, `RowObserver` state is made on the index thread, P1 still starts
after the first screen is parsed, and the 256 KiB chunks only change what
the index threads do. Time Profiler (`xctrace`, `open/first_paint`, 8 s at
each commit) agrees: the main thread's samples under `Document::start` are
the same at both commits (92% in `detect`, then `RowIndex::build` and
parsing the first screen), and none has a diagnostics frame. The index
threads take about the same CPU at both commits (7,825 and 8,015 samples).
At `982edcf` about half of it is diagnostics, but they don't take more.

**The fix.** First paint now does no diagnostics work. `read_first_paint`
uses `RowIndex::start` again, and the index job calls the new
`Indexer::with_diagnostics` as its first step, on its own thread. It puts
the result in the reading's `OnceLock` slot. Until then the document's
readers get an empty, incomplete report (a shared `static`) and no marked
rows, as they did before the first chunk. The only diagnostics-related
thing left in `open` is the empty slot (one small `Arc`), made after the
first-paint interval ends. One behaviour changed: an encoding that doesn't
fit the dialect would now fail the index job instead of `open`. Detection
never gives one. Test: `first_paint_makes_no_diagnostics` holds the index
thread at its start (the `Gate` platform), checks that the reading has no
diagnostics and that readers see an empty report, then lets it go and
checks the full report. It checks a `reinterpret` reading the same way.

**Best hypothesis for CI: the benchmark run, not the code.** 1.5 added the
`worst` and `marks` groups to the `index` bench binary. Cargo runs that
binary just before `open` (targets run in name order), and only on the
1.5 side, since the base doesn't have them. `worst/blank_lines` (100M
rows) builds a 400 MB row index on every iteration. macOS's allocator
keeps large freed blocks counted against the process until the system
needs the memory: a loop that builds and drops that index adds about
380 MB of footprint per iteration (a plain `Vec<u32>` loop does the
same). The `index` binary peaks at **4.4 GB** resident in a full run here,
and at 9.2 GB footprint with longer measurement, against **0.1 GB** at
`d10d535`. CI's runner is a 3-core virtual Mac with 7 GB, so the 1.5 side
runs `open` right after the VM has been pushed into memory pressure. Every
`open` clones the file, and a fresh APFS clone has its own page cache (a
first read of a clone pages in all 100 MB here, 83 ms, against 3 ms for
the cached original). So first paint and the index threads read from the
virtual disk, which is where pressure hurts. Evidence from that CI run:
`worst/blank_lines`' longest chunk was 38.5 ms there against 2.3–2.8 ms
here (17 times, where the other worst cases were 4–11 times), and the
review's longest chunk in the `open` binary went from 2.7 to 3.6 ms,
though 1.5 didn't change the review. Whether the pressure lasts into
`open` can only be checked on CI. A cheap test is to dispatch the
Benchmarks workflow on this branch. If `open/` still regresses, move
`worst`/`marks` into their own bench target, or cut their memory, and run
again.

**After the fix** (`just bench-compare d10d535`, this Mac, attempt 1, no
noise): `open/first_paint` 1.53 ms, −0.9% (−3.1% to +1.7%);
`open/first_paint_under_load` 1.96 ms, −5.2%;
`open/first_paint_removable_under_load` 2.41 ms, +5.7% (+3.6% to +15.0%,
under the 20% gate, and noisy at both commits). Budget 150 ms. With a pool
of 2 and 15 user-interactive spinning threads: 1.97 ms against the base's
1.81 ms for `first_paint`, and 2.26 ms against 2.59 ms under load (noise).
`just check-all` (507 Rust tests, 16 app tests), `just test-deep` (20,000
cases) and the full benchmark suite (in `bench-compare`) pass.

## Rust notes

- **Enums with data** (`collect.rs`). `enum Search { Hit(usize),
  Clear(usize) }` is a search result that is *either* a hit at an offset
  *or* "nothing before this offset". Each variant carries its own value,
  and a `match` must handle both, so a caller can't forget the "nothing
  found" case. `enum Target` goes further: `InvalidUtf16 { big_endian:
  bool }` carries a named field, and `Unmapped(Box<[bool; 256]>)` carries a
  256-entry table on the heap (`Box`), so the other variants stay small.
  `Finder::search` is one `match` on the target, chosen once per search,
  not once per byte.
- **Bounded collections** (`Tally`). A `Vec` grows without limit, so the
  bound is in `push`: the count always goes up, but a location is stored
  only while `first.len() < MAX_LOCATIONS`. Elsewhere `.take(MAX_LOCATIONS)`
  on an iterator and `Vec::truncate` cut lists to size.
- **Traits with default methods, and generic methods** (`RowObserver` in
  `index/scan.rs`). A trait lists methods a type must provide; a method
  with a body `{}` is a default that a type may override. `NoObserver`
  writes only `row`, and the `Collector` overrides all six. Some methods
  are generic (`fn content<U: Units>(…)`), so the compiler makes a copy
  for bytes and one for UTF-16. That means the trait can't be used as a
  `dyn RowObserver` (a trait object needs one fixed function per method),
  which is fine: the scanner is generic over its observer (`scan<O:
  RowObserver>`), so every call is a direct, inlinable call, and with
  `NoObserver` the empty ones vanish. That is why `index/build` costs the
  same as before.
- **Closures as arguments** (`skip_clean_blocks(…, maybe: impl Fn([u8; 2])
  -> bool)`). The caller passes the test for "might this unit be a hit?"
  as a closure, `|unit| unit == [0, 0]` for NULs and one that checks the
  high byte for surrogates. `impl Fn` makes a specialised copy per closure,
  so the check is inlined into the loop and can be vectorised. The hooks
  use traits rather than closures because there are six related events
  and the observer keeps state between them; a struct implementing a trait
  says that more clearly than six closures sharing captured variables.
- **Borrowing versus sharing** (`Collector { diagnostics: Arc<Diagnostics>,
  … }`). The first version borrowed: `Collector<'a>` held a
  `&'a Diagnostics`, and the lifetime `'a` made sure it couldn't outlive
  them. That works while the collector lives only for one call
  (`Indexer::run`). But the chunked indexer (1.3a) keeps its collector
  between calls, inside a struct that also holds the `Arc` the reference
  would point into, and Rust doesn't allow a struct to borrow from itself.
  So the collector now holds its own `Arc` clone: it shares ownership
  instead of borrowing, and the lifetime is gone. In
  `build_with_diagnostics`, `Arc::try_unwrap` gets the `Diagnostics` back
  once the collector has been dropped.
- **`Option::take`** (`ChunkedIndexer::push`). `self.collector.take()`
  moves the collector out and leaves `None`, so it can be passed as
  `&mut` to `push_observed(&mut self, …)` without borrowing `self` twice;
  it is put back afterwards.
- **An associated constant on a trait** (`RowObserver::LOOKAHEAD`). A trait
  can give each type a constant, with a default (`= 0`) a type can
  override (the `Collector`'s 4). The chunked scan reads `O::LOOKAHEAD`
  for whichever observer it was given, at compile time, so the plain index
  holds back nothing extra.
- **Publishing snapshots with `Arc` behind a `RwLock`**
  (`Diagnostics::publish` and `report`). The lock holds an
  `Arc<Report>` (with the row marks). Publishing builds a new report and
  swaps the `Arc` in; reading clones the `Arc` (a counter bump) and
  releases the lock at once. A reader can keep its report as long as it
  likes, even while newer ones are published, and never sees a
  half-written one.
- **Moving a value out of an `Arc` and a lock** (`Diagnostics::into_report`,
  used by `build_with_diagnostics`). `Arc::unwrap_or_clone(arc)` gives the
  value without copying *only if this is the last `Arc` pointing at it*;
  otherwise it copies. The first version called it on `diagnostics.report()`,
  a second `Arc` cloned from the one inside the lock, so it always copied
  (found in review). `into_report(self)` takes the `Diagnostics` by value,
  so nothing else can hold it; `RwLock::into_inner` then gives up the lock
  and hands back what was inside, including the lock's own `Arc`, now the
  only one, so `unwrap_or_clone` moves the report out. Taking `self` by
  value is what lets the compiler prove nobody else is looking.
- **Iterating over optional fields** (`Collector::finders`).
  `self.nul.iter_mut().chain(self.invalid.iter_mut())`: an `Option` can be
  iterated (zero or one item), so this yields each finder that exists. It
  returns `impl Iterator<Item = &mut Finder>`, which borrows `self`
  mutably until the loop ends; that is why `take_hits` copies
  `self.delimiter` into a local first.
- **A sentinel instead of `Option`** (`NONE = usize::MAX` for "no next
  hit"). `Option<usize>` would be the usual choice, but the hot path asks
  "is the next hit before `to`?" once per stretch of the scan, and with a
  sentinel that is one integer comparison (`usize::MAX` is never `<` any
  offset). The constant is named and documented so it reads as clearly.
- **Hot and cold paths** (`#[inline]` on `content`, `#[inline(never)]` on
  `take_hits`). The common case (no hit) is tiny and should be inlined into
  the scanner's loop; the rare case is large and is kept out of it, so it
  doesn't bloat the loop the CPU runs millions of times.
- **Tie-breaks with `std::cmp::Reverse`** (`mixed_line_endings`).
  `max_by_key(|i| (count, Reverse(first_seen)))` compares tuples left to
  right: the higher count wins, and on equal counts `Reverse` makes the
  *earlier* first-seen order the larger key.
- **`#[cfg(test)]` on a method** (`Indexer::with_chunk_bytes`). The method
  exists only in test builds, so tests can force tiny chunks while the
  product API stays as it was.
- **Packing two things into a byte** (`marks::code`). `code & 0x80` keeps
  only bit 7 (the field-level flag), and `code & !0x80` (`!` flips every
  bit) keeps bits 0–6 (the field count). `count | 0x80` sets the flag.
  `u8::try_from(fields).map_or(WIDE, |n| n.min(WIDE))` turns a `usize` into
  a byte safely: a count that doesn't fit, or is 127 or more, becomes
  `WIDE`, with no silent truncation (which the workspace lints forbid).
- **Moving a buffer's contents without reallocating** (`RowMarks::extend`).
  `shared.append(&mut new)` moves every element of `new` onto the end of
  `shared` and leaves `new` empty *but with its capacity*, so the collector
  reuses the same buffer for every chunk instead of allocating a new one.
- **Searching from the end** (`RowMarks::previous`). `slice.rchunks(64)`
  yields 64-element pieces starting from the end (the last piece, the
  first one in the slice, can be shorter), and `rposition` finds the last
  matching element in a piece. `binary_search_by_key(&row, |&(r, _)| r)`
  (`wide_fields`) finds a row in the side list of wide rows, which is
  sorted because rows are added in order.
- **`#[inline]` on a trait method** (`Collector::row`). The scanner calls
  `row` once per row; in a file of 100 million blank lines, the call
  itself, and building its arguments, cost more than the work inside.
  `#[inline]` asks the compiler to copy the method's body into the
  scanner's loop instead, which made that file about 20% faster to index
  with diagnostics.
- **Walking two lists in step** (`RowMarks::next`, after the integration
  review). `slice.partition_point(|x| pred(x))` is a binary search that
  returns the first index where `pred` stops being true, so
  `wide.partition_point(|&(r, _)| r < from)` is where the wide rows at or
  after `from` begin. From there, each time the walk over the codes meets a
  wide row, the next entry of the side list is that row's, so a cursor
  (`w`) moves forward by one instead of searching again. `(from..).zip(tail)`
  pairs each code with its row number: `from..` is an endless range, and
  `zip` stops when the shorter side, the codes, runs out.
- **A value set once, later, by another thread** (`DiagnosticsSlot` in
  `document/mod.rs`, after the first-paint regression). `OnceLock<T>`
  starts empty. `set` fills it once, and later calls are refused.
  `get()` returns `Option<&T>`: `None` until it is set, then the value,
  with no lock to take. The reading and the index job each hold an `Arc`
  of the same `OnceLock`, so the job can fill it after the reading exists.
  `get()?` inside a function that returns `Option` means "return `None` if
  it's empty". `static NO_REPORT: LazyLock<Arc<Report>>` is a global made
  the first time it is used: here, the first time a reader asks for a
  report before the index job has made the diagnostics. After that it is
  shared, so asking again allocates nothing.
