# 1.1a Removable drives

ADR-0006 option C: a file on a removable drive is never mapped from the
drive. It is read with ordinary reads, copied to the internal disk in one
streaming pass, and mapped from there once the copy is complete. If the
drive vanishes first, the document keeps what was copied and refuses Save.

### The reader API

`Source::bytes() -> &[u8]` is gone, because a file on a removable drive has
no single slice until its copy is complete. In its place:

```rust
source.as_slice()            // Option<&[u8]>: the whole file, when it is mapped or in memory
source.read_range(range)     // Result<Cow<[u8]>, ReadError>: any range, in every state
source.stream(&cancel, |chunk: Chunk| …)   // Result<(), ReadError>: the whole file, in order, in chunks
source.storage()             // + Storage::Reading, Storage::Disconnected
source.available_len()       // u64: bytes that can still be read (less than len only when disconnected)
source.can_save()            // false when disconnected; Save As is always allowed
Source::open_on(path, &temp, VolumeInfo { folder, is_internal, is_ejectable })
```

`Source::open(path, temp, volume_folder)` is unchanged. It is `open_on`
with no facts from Foundation.

How each consumer uses it:

- **First paint** reads `read_range(0..64 * 1024)`. It is borrowed from the
  map on an internal volume, and read with `pread` otherwise. Ranges are
  clamped to the file, like `pread`, so a short file just gives fewer
  bytes.
- **The index** (sequential) runs on `stream`. `Chunk { offset, bytes }`
  arrives in order with no gaps, `STREAM_CHUNK_BYTES` (1 MiB, the same as
  `index::CHUNK_BYTES`) at a time. `cancel` is checked before each chunk,
  as in `Indexer::run`. On an internal volume the chunks are borrowed from
  the map and nothing else happens. On a removable drive each chunk is
  written to the internal copy *before* it is handed over, so whatever the
  index has seen is in the copy. This is the seam for 1.3a (below).
- **Rows** are read with `read_range(index.row_extent(r))` until there is a
  slice, and from `as_slice()` after that.

### A file on a removable drive

`open` clones the file on its own volume, as before (ADR-0005 decision 7).
It then decides whether that volume can vanish:

1. If the file is on the same volume as the scratch directory (the boot
   volume), it can't vanish and is mapped exactly as before. This costs one
   `stat`, with no detection at all. The scratch directory may not exist
   yet, so it asks the nearest folder that does.
2. Otherwise it applies the rule in `volume::can_vanish`. Either source of
   facts saying "it can vanish" is enough:
   - **Foundation** (`VolumeInfo`, from the app): the volume can vanish
     unless `volumeIsInternal` is `true` and `volumeIsEjectable` isn't
     `true`. These are the properties PLAN 1.1a names. On this Mac, a disk
     image gives `isInternal = nil` and `isEjectable = true`, and the boot
     volume gives `true` and `false`.
   - **The volume's mount flags** (`fstatfs`, read by the core): it can
     vanish if `MNT_REMOVABLE` is set or `MNT_LOCAL` isn't. A disk image
     has `MNT_REMOVABLE`. This gives the CLI and the Rust tests real
     detection without Foundation. If the flags can't be read, the volume
     is assumed able to vanish. The removable path is always correct, just
     slower to reach a map.

A file whose volume can vanish becomes `Storage::Reading`. `Removable`
holds:

- the clone on the drive, open for `pread`, in a `Mutex<Option<…>>` so it
  can be dropped while other threads use the source. Each reader takes an
  `Arc` of the `File` for the length of one read.
- Leal's copy in a new recorded folder in the scratch directory (the
  `Source`'s `temp`), open for reading and writing.
- `copied`, an `AtomicUsize`: how many bytes from the start the copy holds.
  Bytes below it are never written again.
- `disconnected`, an `AtomicBool`.
- `map`, a `OnceLock<Mmap>`: the copy's map, set once.

`read_range` takes the map if it is set. Otherwise it reads the copy if
`copied` covers the range, and the clone on the drive if not.

`stream` holds a lock for the whole pass, so only one pass runs at a time.
It reads each chunk from the copy if the copy already has it (an earlier,
cancelled pass), or reads it from the clone with `pread`, writes it to the
copy with `pwrite`, and advances `copied`. Then it hands the chunk over.
After the last chunk it makes the copy mode 0400, maps it, sets `map`, and
drops the clone, which deletes the clone, its folder and its record. From
then on `storage()` is `Copy`, and the source behaves like the large-file
copy fallback.

**Disconnection.** When a read of the clone fails, `drive_vanished` checks
two things. One is whether the kernel revoked the descriptor: after a
forced unmount, every `pread` gives `EIO`, even for cached pages, and
`fstat` gives `EBADF`. The other is whether the clone's path no longer
leads to the same `(dev, ino)`. If either is true, the source becomes
`Storage::Disconnected` and the error is `ReadErrorKind::Disconnected`.
Otherwise, for example a bad block on a drive that is still there, it is
`ReadErrorKind::Other` and nothing changes. When disconnected:

- `available_len()` is `copied`. Reads within it still work (from the
  internal copy), and reads past it fail with `Disconnected`.
- `can_save()` is `false`. Save As is allowed and writes the
  `available_len` bytes. 2.5 and 1.7 word it.
- `stream` delivers the copied chunks again, then returns `Disconnected`.
  So re-indexing with another delimiter still works on the rows that
  survived.

I checked these error codes with a probe before writing the
classification: `pread` gives `EIO` (5), `fstat` gives `EBADF` (9), and
`stat` of the path gives `ENOENT`.

## Tests

`source/tests/removable.rs`, 17 tests. Most force the removable path on a
file in an ordinary temporary directory (`VolumeCheck::Removable`, a
private open option). They are fast and run in parallel. Four use a disk
image and are in the `disk-images` nextest group.

- **Ordinary reads** before any copy: `Reading`, `as_slice` is `None`, and
  `read_range` returns owned bytes for first paint's 64 KB, a middle row,
  the whole file, clamped ranges and empty ranges. Both folders and both
  records exist.
- **Reads during the copy**, from every chunk's callback: the whole file,
  plus a range that straddles the copied part's end.
- **The switch**: the chunks' offsets and lengths, and their concatenation,
  are checked. After the switch the storage is `Copy`, `as_slice` is the
  file, `read_range` borrows, and the copy is mode 0400. The external
  clone, its folder and its record are gone. A second pass streams from
  the map. Dropping the source removes everything.
- **A snapshot**: rewriting the original during the copy changes nothing.
- Empty file. A mapped source streams without copying, and a set cancel
  flag stops it.
- **Property** (F1 for this path; 256 cases): for any bytes and chunk sizes
  from 1 to 63, two `read_range`s cut at a random point, the stream's
  chunks and the final map all equal the bytes.
- **Cancel**: set from the third chunk's callback, the pass stops with
  `Cancelled` and delivers no fourth chunk. Reads keep working, and a new
  pass starts from 0 and completes. A cancel before the first chunk
  delivers nothing.
- **Cleanup**: dropping mid-copy removes both folders and records. A crash
  mid-copy leaves both, and `remove_leftovers` removes both (2).
- **The rule**: a table of Foundation facts × mount flags.
- **Detection without overrides**: a file on the boot volume is mapped,
  even with facts saying "ejectable" and before the scratch directory
  exists.
- **Disk images** (real detection, no override):
  - `a_disk_image_is_detected_as_removable`: the image's mount flags have
    `MNT_REMOVABLE` and a temp directory's don't. `Source::open` with the
    folder on the image gives `Reading`, with the clone on the image.
  - `a_drive_disconnected_before_the_copy_fails_reads_without_crashing`:
    first paint is read, then `hdiutil detach -force`. Reads give
    `Disconnected`, the storage is `Disconnected`, `can_save` is false,
    `available_len` is 0, and the stream gives `Disconnected` with no
    chunks.
  - `a_drive_detached_mid_copy_keeps_what_was_copied`: 16 chunks of
    256 KiB, force-detached from the fourth chunk's callback. The pass
    delivers exactly 4 chunks and returns `Disconnected`. The 1 MiB that
    was copied reads back byte for byte, a range crossing its end gives
    `Disconnected`, Save is refused, and a new pass re-delivers the 4
    chunks before `Disconnected`.
  - `a_completed_copy_survives_the_drive_vanishing`: copy a 3 MB file,
    force-detach, then touch every byte through `as_slice` and
    `read_range`.
- Existing image tests:
  - `file_on_a_second_apfs_volume_is_cloned_on_that_volume` now uses
    `VolumeCheck::Internal`, standing in for a second internal disk, to
    keep testing the mapped clone on another volume.
  - `cleanup_removes_a_crashed_clone_on_another_volume` now covers a
    removable source and expects 2 folders.

## Performance

**Internal volumes: unchanged.**

- `as_slice` and `read_range` are one `match` on the storage, then a borrow.
- `open` adds one `stat` of the scratch directory and nothing else.
- The index and its benchmarks don't use `Source`.

`Source::open` on the boot volume, release build, median of 21, using a
throwaway example program that isn't committed. The same program was built
from `main` and from this branch, on the same machine (`Mac17,8`, M5 Pro):

| File | `main` open (two runs) | branch open (two runs) | Drop, both |
|---|---|---|---|
| 1 MB | 0.25, 0.23 ms | 0.25, 0.28 ms | ~0.1 ms |
| 100 MB | 0.22, 0.27 ms | 0.26, 0.23 ms | ~0.1 ms |

The two are within run-to-run noise.

**Removable path**, on a disk image. A disk image lives on the internal
SSD, so this measures the code, not a USB drive:

| 100 MB file, median of 11 | Time |
|---|---|
| `open` (clone, detect, create the internal copy's folder) | 0.35 ms |
| First 64 KB (`pread`) | 1.7 ms |
| `stream`: copy 100 chunks, map, delete the clone | 60 ms |
| Drop | 1.4 ms |

The file was in the page cache, so the stream figure is roughly the cost of
the copy itself (about 1.7 GB/s). On a real drive it is limited by the
drive's read speed.

Before the switch, first paint costs one 64 KB `pread`. On a real USB 3
drive that is a few milliseconds. The copy runs at the drive's read speed,
during the index pass. It uses internal disk space equal to the file's
size and no extra memory beyond one 1 MiB chunk buffer, as ADR-0006 says.

## Decisions and deviations

- **The reader API is an enum inside `Source`, not a trait.** Every caller
  keeps one `Source` type, and the state can change from `Reading` to
  `Copy` while it is shared. See the Rust notes.
- **`bytes()` was renamed to `as_slice()` and returns `Option`.**
  Returning an empty slice while reading would have been a silent bug. On
  `main`, only tests called `bytes()`. **Branches in flight:** `task/1.2`'s
  `tests/detect_source.rs` calls `source.bytes()` twice. After rebasing it
  needs `source.as_slice().unwrap()` (or `read_range(0..64 * 1024)`).
- **Detection uses Foundation's facts and the mount flags together**,
  rather than DiskArbitration in Rust. Foundation's two properties are
  what PLAN names. The app already passes the volume folder, and reading
  two resource values is a one-liner in Swift. DiskArbitration from Rust
  would have meant CoreFoundation FFI and linking another framework into
  the app. The mount flags give the CLI and the Rust tests a real answer.
  `MNT_REMOVABLE` is set for disk images. I couldn't check it on a
  physical external SSD; Foundation's `isInternal`/`isEjectable` covers
  that case in the app.
- **`open_source` in the FFI takes a `VolumeInfo` record** (folder,
  `isInternal`, `isEjectable`, each defaulting to `nil` in Swift) instead
  of `volumeFolder`. In the core, `Source::open` keeps its signature, and
  `open_on` takes the facts.
- **Every stream pass starts at offset 0**, even after a cancel, so 1.3a
  can always start a fresh index. The part already copied is re-read from
  the internal copy, which is fast, and isn't copied again.
- **After the switch the storage is `Copy`**, the same as the large-file
  fallback. Nothing needs to tell the two apart.
- **Every removable volume takes this path**, including ones that can't
  clone. This changed after review; see below.

## Seam with 1.3a (index from the same pass)

Call `source.stream(&cancel, |chunk| …)` on the index thread, for every
storage kind. The chunks are the file, in order, and on a removable drive
they are already safe in the internal copy when they arrive. What 1.3a
needs to add:

- **An index that takes chunks.** Today `Indexer::run(bytes, …)` wants the
  whole slice. For internal volumes 1.3a can keep calling it with
  `source.as_slice()`, which is as fast as today. For removable drives it
  needs a push API: feed chunk after chunk, carrying the scanner's state
  and the one-unit look-ahead past a CR or a quote at a chunk's end.
- **Rows before a slice exists.** `RowIndex::row(r, bytes)` and 1.4's
  `RowParser::parse(bytes, span)` both take the *whole file* plus absolute
  offsets. Until `as_slice()` is `Some`, a caller has
  `read_range(index.row_extent(r))`, which is a window starting at the
  extent's start. Either the parser gets a "window plus base offset"
  variant, or the line ending is read from the extent's last one or two
  units, and the fields are parsed relative to the window and offset back.
  That is a few lines in 1.4's parser. I didn't change it, because 1.4
  isn't on `main`.
- **Cancel** is the same `&AtomicBool` the indexer takes.

## Changes after review

The review found no crash path and no way to map a file on a removable
volume. It confirmed that the internal copy is mapped only once it is
complete and set to 0400, that a full internal disk fails safely, that the
switch to the map is race-free, that cleanup is correct, and that open
time on internal volumes is unchanged. The fixes:

- **Rebased onto `main`** (1.2 and 1.4). `tests/detect_source.rs` called
  `source.bytes()`. It now passes `&source.read_range(0..FIRST_PAINT_BYTES)`
  to `detect`. No other caller on `main` used `bytes()`: 1.4's rows,
  tests and benchmarks take plain slices, and `inspect.rs` and `leal-ffi`
  don't read the bytes.
- **Errno classification** (`removable::classify`, with unit tests).
  After a real unplug, reads can fail with `ENXIO`, `ENODEV`, `ENOTCONN`,
  `ESTALE`, `EBADF` or `ENOENT` while `fstat` and the path still look
  fine. Those now mean `Disconnected` straight away. Only `EIO`, which a
  bad block also gives, goes through the "has it vanished?" check, and
  that check runs a second time after 50 ms if the first says no. This
  closes the window in the old open question, where a read failed a
  moment before the kernel unmounted the volume. The 50 ms pause happens
  only for an `EIO` on a drive that still looks present.
- **Removable drives that can't clone** (exFAT, FAT, HFS+) now take the
  removable path too, as ADR-0006 option C says for every removable
  volume. They used to read the whole file into memory (up to 512 MiB),
  or copy it, inside `open`, before first paint and without a way to
  cancel. Now:
  - `open` keeps the user's file open read-only and reads it with `pread`,
    never mapped (`removable::Origin::Original`), and streams it to the
    internal copy as for a clone.
  - The memory and copy fallbacks remain only for volumes that can't
    clone *and* can't vanish, such as an internal HFS+ partition.
  - ~~A network share also streams.~~ Reverted in the re-review: see
    below.
  - Without a clone there is no snapshot, so another app could change the
    file during the copy. ~~The identity was checked when the copy
    completed, and the copy was still mapped.~~ That let Save write mixed
    bytes over the file. The re-review replaced it with a check after every
    read: see below.
  - Limit: a change that keeps the size *and* lands within the volume's
    modification-time granularity can't be seen. That is 10 ms on exFAT,
    but 2 s on FAT and 1 s on HFS+.
  - The vanish check reads only the descriptor for the user's own file,
    not its path, because the user may simply have renamed it.
- **Tests**, on exFAT disk images, all in the `disk-images` group:
  - `a_drive_that_cant_clone_is_streamed_not_read_at_open`: open plus the
    first 64 KB take under 150 ms, and nothing has been copied at open
    (the internal copy is empty). The file is read itself, the app's
    folder is removed, a cancel stops at the next chunk, a second pass
    completes and maps the copy, `changed_on_disk` is false, and
    everything is cleaned up.
  - `a_drive_that_cant_clone_detached_mid_copy_is_disconnected`: as for
    APFS.
  - A change during the copy is reported (replaced in the re-review by
    `changes_to_the_file_without_a_clone_are_reported_and_block_save`).
  - The HFS+ fallback tests now open "as internal" (`VolumeCheck::Internal`).
    `file_on_another_volume_without_a_folder_there_falls_back` covers both
    cases: memory if internal, reading the file itself if removable.
  - The disk images' volume names are now at most 11 characters, the
    exFAT limit.
- **PLAN**:
  - 1.9 gains the "drive returns" criterion (detect the remount,
    re-verify the identity, then resume or allow Save) and the
    `changed_on_disk` banner.
  - 1.3a gains the window variants of the index and row parser
    (`row_in(window, base)`, `parse(window, base, span)`), and the chunked
    index pass. The reviewer measured about 2 µs per screenful.

`just check-all` passes, and 10 runs of the 15 disk-image tests passed (see
the commit). `hdiutil info` showed nothing of Leal's attached afterwards.

## Changes after re-review

The re-review found no crash path, and confirmed that the user's file is
never mapped. The fixes:

- **Save after a change (must-fix).** `can_save()` used to stay `true`
  after `changed_on_disk`. The reviewer reproduced it on exFAT: first paint
  served "abcd", the file was rewritten in place, the copy held "ZZZZ", and
  Save would have written that mix over the file. Now:
  - `can_save()` is `false` once a change is detected.
  - A changed source never maps its copy, and stays `Storage::Reading`.
  - Bytes read from the file after the change are never returned:
    `read_range` gives `ChangedOnDisk` for anything not already in the
    copy, and every later `stream` pass fails straight away.
  - `Source::changed_on_disk`'s docs say that rows read *before* the
    detection must be discarded too. PLAN 1.9 now says to invalidate the
    row cache and offer Reload.
  - The old notes' "the index and the bytes agree" is struck through
    above.
- **Truncation mid-copy (must-fix).** A short read gave `UnexpectedEof`,
  classified as `Other`, so `changed_on_disk` stayed false and every retry
  failed the same way.
  - A short read now runs the identity check (`fstat`: inode, size,
    modification time), and a change gives `ChangedOnDisk`.
  - The check also runs after *every* read of the user's file: each
    stream chunk, before the chunk is copied or delivered, and each
    `read_range` from the drive. So a change shows up at the next chunk,
    not at the end.
  - An `fstat` costs about a microsecond, so the check is cheap enough
    for every chunk and every read.
- **No sleeping outside `stream` (should-fix).** The 50 ms `EIO` re-check
  slept on whatever thread called `read_range`, which DESIGN §3.9 allows
  to be the main thread (1 ms limit).
  - It now happens only in `stream` (`Wait::Allowed`), which runs in the
    background.
  - `read_range` classifies with one look and no wait (`Wait::Never`). If
    the drive is mid-unmount, the read is `Other`, and the next read or
    the stream catches the disconnection.
- **Network shares are back on the 1.1 fallbacks (should-fix).** Putting
  them on option C changes accepted ADR-0006, which needs Rob.
  - `volume::kind` now returns `Fixed`, `Removable` or `Network`.
    `Network` means `MNT_LOCAL` is missing, whatever Foundation says.
  - `can_vanish` in `mod.rs` routes only `Removable` to the streaming
    path. Moving shares over is one line there.
  - DESIGN §3.1 and ADR-0006 match this again: they say network volumes
    can't clone and use the memory/copy fallbacks.
  - The network errnos (`ETIMEDOUT`, `EHOSTDOWN`, `EHOSTUNREACH`,
    `ENETDOWN`, `ENETUNREACH`, `ECONNRESET`) are classified `Ambiguous`
    now, because a removable drive behind a bridge can return some of
    them. This has unit tests.
- **Stale docs (should-fix).**
  - `as_slice` and `read_range` no longer claim "exactly as on disk when
    opened" or "the clone" for the no-clone case.
  - `stream`'s error list includes `ChangedOnDisk`, and says to run it in
    the background.
  - The module docs say which volumes fall back.
- **Tests.** `changes_to_the_file_without_a_clone_are_reported_and_block_save`
  uses one exFAT image and four files:
  - **The reviewer's case.** First paint reads the old bytes, then the
    file is rewritten in place. The next uncopied read gives
    `ChangedOnDisk`, `can_save` is false, the stream fails with no
    chunks, and nothing is mapped.
  - **Changes during the copy**, made after the second chunk: an in-place
    rewrite (with a later modification time), a truncation (a short read)
    and an append. For each one:
    - exactly two chunks are delivered, and the third, read after the
      change, is not;
    - `changed_on_disk` is true, `can_save` is false, and nothing is
      mapped;
    - the copied part reads back as the old bytes, and nothing past it is
      served;
    - a new pass fails straight away.

  `the_removable_rule` now checks the `Network` kind.

### Proposal for Rob: network shares on option C

The reviewer's notes, for the phase 1 gate. Streaming a share instead of
reading it all at open would make first paint fast for large files on a
share, but it needs care:

- **Never `pread` an uncopied range on the main thread for a non-local
  volume.** A hard NFS mount, or an SMB share reconnecting, can block a
  read for seconds or forever, and that would hang the app. Rows past the
  copied part would have to wait for the stream (or a background read),
  not be read synchronously.
- **`ETIMEDOUT`, `EHOSTDOWN`, `EHOSTUNREACH`, `ENETDOWN`, `ENETUNREACH`
  and `ECONNRESET` are ambiguous.** A share can come back. (They are
  already classified that way.)
- **`ESTALE` or `ENOENT` on a share can mean another client deleted or
  replaced the file**, not a disconnection. A share would need its own
  classification ("changed elsewhere", not "drive disconnected").
- **Attribute caching makes `ChangedOnDisk` unreliable on shares.** SMB
  and NFS clients cache size and modification time for a while, so
  another client's write may not show up in `fstat` during the copy. The
  copy of a share is then not a dependable snapshot.

Until Rob decides, shares keep ADR-0006's behaviour: read into memory, or
copied, at open, with ordinary reads, which is safe but slow for large
files.

- **First paint's rows** are read before the copy starts. If the drive

  `available_len` is 0, though the UI's row cache still has those rows.

## Rust notes

- **Enum vs trait for "where the bytes come from"** (`Bytes` in
  `source/mod.rs`). A *trait* (`trait ByteSource { fn read_range(…) }`)
  lets each storage kind be its own type, and callers would hold a
  `Box<dyn ByteSource>`, which picks the method at run time. An *enum*
  (`enum Bytes { Mapped(Mmap), Owned(Vec<u8>), Removable(Box<Removable>) }`)
  lists every kind in one type, and each method is a `match`. I used the
  enum because:
  - the set of kinds is closed and small;
  - the compiler checks that every `match` handles every kind;
  - the hot case (a map) is one branch away with no indirection;
  - callers keep a single concrete `Source`.

  A trait is better when *other* code adds kinds, which isn't the case
  here. `Box<Removable>` keeps the enum small: an enum is as big as its
  biggest variant, and `Removable` is much bigger than an `Mmap`.
- **`Cow<'_, [u8]>`** (`read_range`). "Clone on write": either
  `Cow::Borrowed(&[u8])`, a view into memory someone else owns (the map),
  or `Cow::Owned(Vec<u8>)`, bytes this call just read and hands over. Both
  deref to `&[u8]`, so callers write `&*bytes` or `bytes.len()` and don't
  care which. The `'_` says a borrowed `Cow` can't outlive the `Source`.
- **`pread` without `unsafe`** (`removable.rs`). `pread(fd, buf, len,
  offset)` reads at an offset without moving the file's position, so
  several threads can read one `File` at once. The standard library has it
  as `std::os::unix::fs::FileExt::read_at`, and `read_exact_at` loops until
  the buffer is full. `write_all_at` is `pwrite`. Unlike a mapped page,
  these report a vanished drive as an `io::Error` instead of killing the
  process. That is the whole point of ADR-0006.
- **Error kinds for a vanished volume** (`drive_vanished`, `ReadErrorKind`).
  The OS doesn't have one errno for "the drive was unplugged". A read on a
  force-unmounted volume gives `EIO`, the same code as a bad block. So the
  code doesn't trust the errno alone. It asks two follow-up questions: did
  the kernel revoke our descriptor (`fstat` fails with `EBADF`), and does
  the path still lead to our clone? Only then is it `Disconnected`.
  `ReadError` keeps the original `io::Error`, so `raw_os_error()` still
  gives `EIO` for logs, and `kind()` gives the app the meaning. This is the
  same "errno plus kind" design as `OpenError`.
- **Interior mutability: `OnceLock`, atomics and `Mutex`** (`Removable`).
  `stream` takes `&self`, a shared reference, but it changes the source
  from "reading" to "mapped". Rust allows changes through `&` only via
  types built for it:
  - `OnceLock<Mmap>` can be set exactly once. After that, `get()` hands
    out `&Mmap` to any thread with no locking, which is why reads after
    the switch cost nothing.
  - `AtomicUsize` and `AtomicBool` (`copied`, `disconnected`) are numbers
    any thread can read and write without a lock.
  - `Mutex<Option<External>>` guards the clone on the drive, so the stream
    can `take()` it out and drop it while readers are about.
- **`Ordering::Release` and `Acquire`** (`copied`). The stream writes a
  chunk to the copy, *then* stores the new `copied` with `Release`. A
  reader loads `copied` with `Acquire` and only then reads the copy.
  Release/Acquire is the promise that a reader who sees the new number
  also sees everything the writer did before storing it, here the
  `pwrite`. (`Relaxed`, which the cancel flag uses, makes no such promise,
  and doesn't need to.)
- **`Arc<File>` for a read in flight** (`external_file`). A reader clones
  the `Arc` under the lock, releases the lock, and then reads. If the
  stream drops the clone meanwhile, the reader's `Arc` keeps the file open
  until its read finishes. Deleting an open file is fine on Unix: it
  disappears when the last descriptor closes.
- **Drop order, again** (`Removable`'s fields). `map` is declared first, so
  it is unmapped before the files close and before the `Source`'s `temp`
  deletes the copy. In `External`, `file` comes before `folder`, so the
  clone is closed before it is deleted.
- **`#[cfg(test)]` on enum variants** (`VolumeCheck::Internal`,
  `VolumeCheck::Removable`). These variants only exist in test builds, so
  product code can't take a shortcut past detection by accident. The
  `match` in `can_vanish` puts the same attribute on its arms.
- **`MaybeUninit` and `fstatfs`** (`sys::volume_flags`). C fills in a
  `struct statfs` we hand it. `MaybeUninit::<libc::statfs>::uninit()` is
  memory of the right size that Rust knows isn't valid yet. Reading it
  before it is filled would be undefined behaviour. After `fstatfs` returns
  0, `assume_init()` says "it's filled in now". Each of the two steps is
  its own `unsafe` block with its own `SAFETY` comment.
