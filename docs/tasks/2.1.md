# 2.1 Edit overlay and commands

The core can now edit cells (DESIGN §3.6). An edit never touches the file's
bytes. It goes into an **overlay**, and every reader of a row sees the row
through it: the grid, the inspector, the editor's starting value, Copy,
Find, the diagnostics marks and their Previous/Next, column widths and
number detection (ADR-0008 decision 2).

Each edit is a **command** in logical coordinates, with each cell's value
before and after. The app's `NSUndoManager` will hold the commands (task
2.5): undo applies a command's inverse, and redo applies it again. A
command applies only to the edits it was made in (its **lineage**) and only
if its cells still hold what it expects. The same commands, kept in a
journal of the app's own, can be replayed into a freshly opened document,
which reports any that no longer apply (ADR-0008 decision 5).

Also in this task:

- **Missing cells.** A short or blank row's hatched cells can be edited
  (ADR-0005 decision 2). Edits past an unterminated quote are refused
  (ADR-0004 decision 8). The save oracle and the edit strategy now do the
  same, and that landed first, as test code.
- **Batches.** Several cells set at once (a paste) are one command: all of
  them or none.
- **Re-reading.** While there are unsaved edits, the core refuses a new
  delimiter or encoding. The header row can still change, and a drive
  coming back keeps the edits (ADR-0008 decision 4).
- **The header row.** The core edits file row 0 whether or not it is the
  header row. Whether the app should let users do that is a question for
  2.5; my recommendation is below.
- **FFI.** What 2.5 needs: `setCell`, `setCells`, `canEdit`, `undo`,
  `redo`, `replay`, `lineage`, `hasUnsavedEdits`, `editedCellCount`,
  `editConflicts` and `fullValue`.

Saving (2.2), row and column inserts and deletes (2.4) and the editing UI
(2.5) are not part of this task. "What 2.4 needs" lists what they will
have to add.

The review's findings and what changed for each are under "Changes after
review", at the end. The sections before it describe the code as it is
now.

### The command model, and who owns undo

`Document::set_cell(row, column, value)` is the user committing an edit.
It returns a `Command`, or `None` if the cell already reads as `value`
(ADR-0008 decision 3: committing an unchanged value is no edit, so nothing
goes on the undo stack). `set_cells` does the same for several cells at
once.

```text
Command { lineage: Lineage, edit: Edit }
Edit::SetCell(CellChange) | Edit::SetCells(Vec<CellChange>)
CellChange { row, column, old: Option<String>, new: Option<String> }    None: a missing cell
```

- **`new` is what the cell reads as afterwards,** not what was asked for.
  Setting an edited hatched cell to `""` makes it missing again, so its
  `new` is `None`, and its undo restores it from missing.
- **`Document::apply(&command)`** applies a command only:
  - in its own lineage (otherwise `OtherLineage`);
  - if every cell holds its `old` value and ends up holding its `new` one
    (otherwise `ValueChanged`).

  Undo is `apply(&command.inverse())`, and redo is `apply(&command)`.
- **A batch** is checked whole before anything changes, then applied
  under one writer lock and one store write, rebuilding each row's edits
  once. Its inverse is each change's inverse, last first. A refusal
  anywhere applies nothing and names the first cell refused. The
  unterminated-quote rule is checked on each row as the batch leaves it,
  so a batch that closes the quote and fills a cell after it is allowed.

**The app's `NSUndoManager` owns undo; the core keeps no stack.** Why:

1. **Recovery needs the app to hold the commands anyway.** ADR-0008
   decision 5 says the app keeps its own record of the edit commands. A
   core stack would sit inside the failed document, behind a lock a panic
   may have poisoned. So a core stack would mean two copies kept in step.
2. **`NSUndoManager` gives 2.5 the rest for free.** It handles undo
   groups, the Edit menu's titles, per-document undo and `NSDocument`'s
   change count.
3. **The commands are values,** not byte positions, so they survive a save
   (ADR-0008 decision 1). After 2.2 rebases the document on the saved
   file, in the same lineage (`EditStore::with_lineage` keeps it), undo
   applies the old value as a new edit on the new base. One case needs a
   2.2 decision: undoing a hatched edit (`None` → `"x"`) after a save. The
   saved file has the cell as a real field, so making it missing again is
   refused with `ValueChanged`. 2.2 should choose between undoing it to
   `""` (keeping the delimiters) and a change that truncates the row back
   (which a cell edit can't express).
4. **The lineage and old-value checks make a stale command harmless.** A
   command is never applied to the wrong cell: one from before a new split
   is refused by lineage, and one into a changed file by value.

**But `NSUndoManager` can't be listed,** so it can't be the recovery
record. Task 2.5 also keeps an **append-only journal** of each command it
applies (edits, undos and redos, in order), together with the reading's
choices (delimiter, encoding, header). For recovery it opens the file with
those choices, waits for the index, and replays the journal. The FFI's
module docs say so too.

The **dirty state** comes from the core (`has_edits`, FFI
`hasUnsavedEdits`). It is true when some cell reads differently from the
file. An edit set back to its original value doesn't count, so an
edit-then-revert is clean, matching F3's byte-identical output. Task 2.5
can use it for the window's dirty dot as well as for disabling Treat As;
`NSDocument`'s change count would still say "edited" after an
edit-then-revert.

### The overlay

```text
EditStore (one per lineage; shared by readings that split the file the same way)
├─ lineage: Lineage
└─ RwLock
   ├─ overlay: Arc<Overlay>
   │  └─ BTreeMap<physical row, Arc<RowEdits>>
   │       RowEdits { fields:    the row's own field count when first edited,
   │                  cells:     Vec<(column, Arc<str>)>, sorted, never empty,
   │                  flagged:   Arc<[(column, Kinds)]>, its own fields' diagnostics,
   │                  kinds:     the row's diagnostics as it reads now,
   │                  head_hash: Option<u64>, if edited from the first 64 KB }
   ├─ log: Vec<row>     the row each edit touched, in order; its length is the version
   └─ cells: usize      how many cells are edited
```

- **Reading a row** takes one snapshot of the overlay per call (a
  read-lock and a reference count) and does one `BTreeMap` look-up per row:
  O(log n) in the edited rows. With no edits the map is empty, and the
  look-up returns at once. An unedited row then takes exactly the path it
  took before (`cells(…)` on its fields).
- **An edit's cost is its cells, not the row's**, apart from reading the
  row to check it. Its own fields' diagnostics (`flagged`) are worked out
  once, the first time the row is edited (none to look for if the row's
  marks say it has none), and shared with every later version of its
  edits. `kinds` is then `flagged` minus the edited fields, plus any NUL in
  an edited value. Values are `Arc<str>`, so a new version of a row's
  edits copies pointers, not text.
- **The store is changed in place** unless a reader holds the overlay (a
  copy in progress): `Arc::make_mut` copies it then, and the copy is of the
  edited rows' `Arc`s, not their values. Jobs that run long (Find) take
  only the rows they need (`rows_in`, `since`), never the whole map, so an
  edit during a search doesn't copy it.
- **Setting a cell back to its original display value removes its edit**
  (DESIGN §3.6). Its original bytes come back on save, quoting and invalid
  bytes included (ADR-0004 decision 9).
- **Edits are serialized** with each other and with `reinterpret` and
  `restart`, by the document's `writer` lock (formerly `reinterpreting`).
  So an edit can't be checked against one reading and land in the next.
- **The log grows** by 8 bytes per row each edit touches, for the
  document's life: 8 MB after a million cell edits. It is what lets a
  search catch up.

### One way to see a row: `RowView`

Every reader gets each row as a `RowView` (`document/view.rs`). Its cells
are, column by column, one of:

- an edited value;
- one of the row's own fields, unedited;
- **padding**: an empty cell between the row's own end and an edited cell
  past it.

The row is as long as its own fields as they are read now, or up to its
last edited cell, whichever is longer. (Not the field count stored with the
edits: a row edited from the first 64 KB may now be read from the trusted
copy.)

| Reader | What it does now |
|---|---|
| Grid (`rows`, `cells`) | Edited values; `field_count` is the row's length now, so the grid's hatching follows it. |
| First screen of a `reinterpret` | The same, so a header toggle shows the edits at once. The FFI's `firstScreen()` is that screen cached; it doesn't follow later edits. |
| Inspector (`cell_value`) | The edited value; `invalid` is false for one; `exists` follows the row's length now. |
| Editor (`full_value`) | The whole display value as it reads now: never the grid's shortened text (ADR-0008 decision 3). `""` for a hatched cell. |
| Copy (`copy_cells_now`, `copy_cells`) | Edited values, from a snapshot of the overlay taken when the copy is made. An edit made while a large copy runs isn't in it. |
| Copy's estimate (`estimated_copy_bytes`) | Adds the edited values in the selection. |
| Find | See "Find" below. |
| Marks and Previous/Next | See "Diagnostics" below. |
| Number detection (`numeric_columns`) | Edited values. |
| Column widths | The app measures the text `cells` returns, so these see edits too. Task 2.5 must ask again after an edit, as it does after a reinterpret. |

### Find

A match is a cell as it reads now. An edited cell matches on its new
value, and stops matching on the one it replaced.

- **Catching up.** The store logs the row each edit touched. A search
  catches up by recounting the rows logged since it last did, among the
  rows it has searched, without holding its counts' lock, then rebuilding
  its matching rows and running counts in one merge pass (`Found::merge`):
  O(M + K) for M matching rows and K recounted ones.
  - If a chunk was added meanwhile, it goes round again.
  - A chunk searched with older edits than the latest is caught up the
    same way: after adding it, `synced` drops back to the chunk's version,
    so the recount covers anything edited meanwhile.
- **Who catches up.** The search's job does, after each chunk. A query
  from the main thread (`progress`, `step`, `ordinal`, `matches_in`):
  - with no edits since, returns at once, taking only the counts' lock, so
    a search with no edits never says it is catching up;
  - otherwise does only a little itself: at most 64 rows, while the counts
    have at most 65,536 matching rows (the merge pass is about 0.1 ms
    then). It gives up before even listing the edited rows if there are
    more edits than that, or more matching rows.

  Beyond that it starts a catch-up job, and:
  - `progress` reports `catching_up: true`;
  - `step` answers `Pending`;
  - `ordinal` and `matches_in` answer from the counts as they are.

  So a finished search with a million matches, after a 10,000-cell paste,
  costs the main thread 35 µs, not a recount. One catch-up runs at a time.
- **The catch-up job** checkpoints every 256 rows (DESIGN §3.10 rule 3),
  so it pauses while the user interacts, and on cancel it returns without
  moving the counts on. Dropping or cancelling the search cancels it, so
  it never holds the reading after the search is gone. Its "started" flag
  is cleared by a drop guard even if it panics, and once it has caught up
  it looks again and starts another if edits came after its last look.
- **For 2.5:** while `progress().catchingUp` is true, keep asking for the
  progress, or await `Search.catchUpJob()` (a `Job`, `nil` when none runs)
  and then ask again; retry a `Pending` Next or Previous once it clears.
- **The raw-byte prefilter** skips rows whose bytes don't contain the
  query. It passes over edited rows, which are checked separately:
  - if the query is nowhere in the row's own bytes, only its edited values
    are checked;
  - otherwise every cell as it reads now.

  The hits are merged in row order.
- **No overlay held.** A chunk takes only its own rows' edits
  (`EditStore::rows_in`), and a catch-up only the touched rows' (`since`).
- The header row still isn't searched; an edit to it changes nothing.

### Diagnostics

An edited cell is checked on its new value (ADR-0008 decision 2). Only a
NUL can be in one (`value_has`):

- the value is text, so nothing in it is invalid;
- the save quotes it as needed (DESIGN §3.7), so it has no text after a
  closing quote and no unterminated quote.

A character the encoding can't hold isn't a diagnostic: saving names it
(F5, task 2.3).

- **The marks.** An edited row's marks come from its `RowEdits` (see "The
  overlay"). It is ragged if its length now differs from the most common
  field count. An edited row is never a blank line. `row_flags`,
  `row_has_diagnostic` and `next_`/`previous_row_with_diagnostic` use these
  for edited rows and the index's marks for the rest.
- **Each kind's Previous and Next** run the existing search over the
  file's own rows. Any edited row before the row it finds is checked as it
  reads now, and an edited row the search returns is passed over (it was
  just checked). `place` finds the column in the row as it reads now.

### Hatched cells and unterminated quotes

- **A cell past the end of a row can be edited** (ADR-0005 decision 2), up
  to column `COLUMN_LIMIT` (2²⁰), or further if the row itself is longer.
  The limit only guards against a mistaken edit that would pad a row with
  millions of cells; the oracle has the same limit. A blank line edited in
  column *c* reads as *c* + 1 cells.
- **A missing cell is `None`, an empty one `""`.** A hatched cell reads as
  missing; a padding cell (between the row's end and an edited cell past
  it) reads as `""`. Undoing a hatched edit gives the short row back byte
  for byte; the properties check this against the oracle.
- **An unterminated quote** is always its row's last field, and that row
  is the file's last. While its cell is unedited, so its quote is still
  open, no cell after it may be edited. Setting it back to its original
  value while a cell after it is edited is refused too. This is the
  oracle's rule 10, checked within the row (in 2.1 nothing can come after
  that row). `can_edit` says whether a cell can be edited before the
  editor opens.

### Re-reading a document with edits (ADR-0008 decision 4)

`edits_after(old, detection)` decides what a new reading starts with:

- **The same split** (the same delimiter, encoding and BOM): the same
  store, and so the same lineage, so the edits carry on. This covers the
  header toggle, and `restart` after a drive comes back (the file is
  confirmed unchanged, so first paint detects the same split).
- **Another split with no edits:** a new, empty store with a **new
  lineage**.
- **Another split with edits:** `DocumentError::UnsavedEdits`. The document
  is unchanged, and its generation isn't spent. The check is on what
  detection gives, not on what the user asked for, so no route around it
  exists.

The check is "no unsaved edits", not "an empty undo stack". After an edit
is undone, the delimiter can change. Its command is from the old lineage,
so `apply` refuses it with `OtherLineage`, even where the cell happens to
hold the same value under the new split. The reviewer's case is a test: in
`a,k,;k;`, cell 1 is `k` split by commas and by semicolons, and a redo of
`k`→`x` after Treat As semicolon is refused. Task 2.5 should clear its
undo stack when the split changes.

### Replay (ADR-0008 decision 5)

`Document::replay(&commands)` applies each command in order, checking
values but not lineage. It skips any that doesn't apply, and returns:

- the commands that applied, in the fresh document's lineage, for the
  app's new undo history;
- the ones that didn't, by position, with the reason:
  - `ValueChanged`: the file changed, or a command built on one that
    didn't apply;
  - `NoSuchRow`;
  - `AfterUnterminatedQuote`;
  - `NotReadYet`;
  - `Unreadable` (FFI) for a row that couldn't be read.

A command for a row the index hasn't reached yet is refused with
`NotReadYet`, so the app should replay once the fresh document's index job
has finished. On a 100 MB file that is about 0.3 s, and recovery is rare;
a replay that waited for rows by itself would have to be a job, which
wasn't worth it. `NotReadYet` is also what a row past an index that
stopped on a read error gets (the drive may come back); `NoSuchRow` only
once the index is complete.

### Edits on rows of the first 64 KB that turn out stale (task 1.9)

Rows of the first 64 KB can be edited before the index reaches them. If
the file then turns out to have changed while it was read
(`changed_on_disk`), those 64 KB aren't trusted, and rows come only from
the checked copy. An edit to such a row is **kept, never dropped**. It
records a hash of the row's bytes (`head_hash`), and
`Document::edit_conflicts` (FFI `editConflicts`) names the cells of those
rows the trusted copy doesn't have, or has with other bytes, for 2.5 and
for Save As from an incomplete document (ADR-0008 decision 6) to name.
Where the row can be read, the edits show on it.

In practice the conflict is almost always a row the copy never reached.
When first paint read the user's file itself (no clone), the copy refuses
any chunk that differs from the first 64 KB (`Removable::check_against_
head`). I tried a test that rewrote a row in place, with the same length
and its modification time put back, before the copy reached it, and the
copy stopped there with `ChangedOnDisk`.

That check isn't armed in one case: **a drive that reconnects after its
clone was lost** (`Removable::reconnect`, the branch that falls back to
the user's own file). First paint read the clone, so no head bytes were
kept, and the rest of the first 64 KB is then copied from the user's file
unchecked. A same-size change with its time put back would be read
unnoticed, and an edit made from the first 64 KB could then sit on a row
with other bytes in the copy. The hash comparison catches exactly that,
so `edit_conflicts` names it, but the grid would show the copy's row. The
fix is small (keep first paint's bytes whatever it read, and check every
copied chunk against them), but its test needs a way to lose the clone
before a reconnect, which the test hooks don't have. So it is left for a
ticket (a 1.9 follow-up).

### What 2.4 needs

In 2.1 a command's row is the physical row (the header row, if any, is
row 0), and its column is a field of the row, or a cell past its end.
Commands are applied, undone and redone in order, so each one always meets
the coordinates it was made in. That makes "logical coordinates" right in
2.4 too.

DESIGN §3.6's plan holds up, but 2.4 will change 2.1's code, not only the
overlay's key. In my first notes I wrote that it wouldn't; that was wrong.
What 2.4 needs:

1. **A logical-to-physical `RowMap` seam in every walk over rows.** Every
   reader that walks rows by number today assumes logical = physical, and
   each needs the map:
   - Find's chunks and `Found.rows` (matching rows are physical numbers);
   - the edit log (`EditStore::log`);
   - the marks and `row_flags`;
   - each kind's Previous/Next;
   - Copy's row ranges;
   - the number-detection sample;
   - the first screen.

   `RowView` covers one row's cells, not which rows there are.
2. **A stable row id for the edit log**, so a search can catch up across
   inserts and deletes. Logging logical rows would make every insert move
   every later entry.
3. **A base epoch for structural undo after a save.** After 2.2's rebase
   the piece list starts again from the saved file. An undo of a row
   delete made before the save must then work by value against the new
   base, not by the old piece.
4. **Each column operation records, per row, whether it applied.** A column
   insert or delete applies only to rows long enough (ADR-0004 decision 5),
   and a blank line never gains a column. Its undo must touch exactly those
   rows, so the operation keeps which they were, not only the rule.
5. **Find remaps or restarts on row shifts.** `Found.rows` are row
   numbers; an insert or delete either shifts them all (a pass over M) or
   restarts the search. Restarting is simpler and probably fine.
6. **Undo and redo name cells by identity.** A cell edit after a column
   insert must undo onto the same cell even if the coordinates moved, so
   `RowEdits`' key becomes something like
   `Field(k) | Inserted(column id) | Appended(n)`, and inserted rows get
   their own store, keyed by an id from the piece list.
7. **Undoing a row or column delete restores the original bytes** (F3),
   not re-inserted values, which would be written with new quoting. So a
   structural command keeps the piece it removed for undo within the
   session, and the values for replay and for undo after a save.

### The header row: recommendation for 2.5

**Recommendation: let users edit header cells, in place, the same way as
any other cell.**

- **The core already supports it, at no cost.** File row 0 is an ordinary
  row to the overlay, the save oracle and the serializer. The header
  toggle changes only how row 0 is shown, and the edits stay.
- **Renaming a column is a common edit,** such as fixing a typo or making
  a name match another system. Without it the user has to turn the header
  off, edit row 1, and turn it on again.
- **Excel and Numbers allow it.** A header that can't be edited would be
  surprising.
- **What 2.5 must take care of:**
  - the header cell's editor starts from `fullValue(row: 0, …)`, not the
    header's title text;
  - the column header view refreshes after an edit;
  - Find still doesn't search row 0;
  - editing a header cell past the end of a short header row (a hatched
    header cell) should be allowed too, for consistency.

If 2.5 finds the in-place header editor awkward (it is a different view,
not a grid cell), a fallback is "Rename Column…" in the header's context
menu, using the same `setCell(row: 0, …)`. None of this needs an ADR; it
doesn't change DESIGN.

## Decisions and interpretations

- **For Rob: a hatched cell set to `""` is no edit.** This narrows ADR-0005
  decision 2's literal text, which says a hatched cell "can be edited".
  Typing nothing into a missing cell leaves it missing, rather than adding
  a delimiter for an empty field.
  - That keeps F3 simple: undoing a hatched edit, or clearing it, gives
    the row back its original bytes.
  - It matches "committing an unchanged value is no edit" (ADR-0008
    decision 3), since the editor opens on `""`.
  - Explicitly padding a short row with empty fields would be a separate,
    future command ("Fill missing cells"), not an edit of one cell.
- **Undo is the app's** (see "The command model"). The core provides the
  commands, their inverses, lineage and the old-value check.
- **The dirty state is "some cell differs from the file"**, not "the undo
  stack isn't empty".
- **The diagnostics report (the banner's counts and the details' totals)
  still describes the file as it was read.** The marks and Previous/Next
  follow edits, as ADR-0008 decision 2 lists them. Recounting the report
  with edits would need merging its "first 1,000 locations" with the
  overlay. If 2.5 wants the banner to follow edits, it is a contained
  change.
- **The most common field count doesn't move with edits.** Ragged is
  judged against the file's own count, and `column_count` stays the
  file's. Otherwise, filling in a few hatched cells could change which
  other rows are ragged and the grid's column count.
- **Batches check the unterminated-quote rule on the rows as they end up**,
  not after each cell, so a paste that closes the quote and fills a cell
  after it applies. A batch the oracle would accept one cell at a time is
  always accepted.
- **`can_edit` answers for "some value"**: setting the quote's own cell back
  to its original value while a cell after it is edited is refused only on
  commit.
- **UTF-16 documents can be edited in the core.** Read-only is the app's
  policy (DESIGN §4.3), and 2.2 refuses to save them. Task 2.3's "edit
  those cells and try again" for Save As UTF-8 may need edits in a
  document whose save is refused.
- **An `EditError::Read` reaches Swift as the usual read error**
  (`DriveDisconnected` and so on) from an edit, and as `.unreadable` in a
  replay report.
- **The app's wording for `EditRefused` is generic** ("The change couldn’t
  be made."). Task 2.5 words each refusal where the edit is made.
- **T5 holds the copy with "the user is interacting", not a closed Gate.**
  The Gate holds only the index thread. Every row an edit can reach before
  the index runs is in the first 64 KB, and the copy job copies those
  without waiting for the index. Holding background work (P2) pauses the
  copy job before its first row, which is what the test needs.
- **F1's "copied with other bytes" case can't happen today** (see "Edits
  on rows of the first 64 KB that turn out stale").

## Rust notes

- **`Arc::make_mut`, copy-on-write** (`EditStore::set_rows`). The store
  holds the overlay in an `Arc` (a shared, reference-counted pointer).
  Readers clone the `Arc`, which only bumps a counter. When an edit needs
  to change the overlay, `Arc::make_mut` changes it in place if no one
  else holds it, or first makes a private copy if someone does (a copy job
  still using the old one). So the copy job keeps exactly what it started
  with, and nobody pays for a copy unless someone is looking. The edit
  itself must let go of its own snapshot first (`drop(overlay)`), or it
  would count as someone looking.
- **`Arc<str>`** (`RowEdits` cells). A shared, immutable string: cloning it
  copies a pointer and bumps a count, not the text. Each edit builds a new
  version of the row's edits from the old one, so its unchanged values are
  shared, not copied.
- **`Option<String>` for a cell's value.** `None` and `Some(String::new())`
  are different values, so the type itself says "missing" versus "empty",
  and the compiler makes every reader decide which it means.
- **`BTreeMap`** (`Overlay`). A sorted map. Looking a row up is O(log n),
  and `range(a..b)` walks the edited rows between two rows in order, which
  Find's chunks and the marks' Previous/Next need. A `HashMap` would find
  one row a little faster but can't do ranges.
- **The entry API** (`rows.entry(row)` in `change`). One look-up that
  either finds a row's work or gives a slot to fill, instead of
  `contains_key` then `insert` (two look-ups).
- **`Mutex::try_lock`** (`SearchState::catch_up`). It takes the lock if it
  is free, and otherwise returns at once with `WouldBlock`, rather than
  waiting. A main-thread query uses it so it never waits for a catch-up
  job; the job itself waits with `lock`.
- **`AtomicBool::swap`** (`start_catch_up`). It sets the flag and returns
  what it was, in one step no other thread can come between. So of two
  threads asking for a catch-up job at once, exactly one starts it.
- **Lifetimes in `RowView<'a>`.** A `RowView` borrows the row's bytes, its
  parsed fields and its edits; it owns nothing. The `'a` says all of them
  must outlive the view, and the compiler checks that no view outlives the
  read it came from. Its cells (`ViewCell::Edited(&'a str)`) borrow the
  same way, so reading an edited value copies nothing.
- **`Cow<'a, str>`** (`RowView::value`). "Clone on write": either a
  borrowed `&str` or an owned `String`. A value that needs no unescaping
  or decoding is borrowed straight from the file's bytes, or from the
  overlay; only one that does is allocated.
- **A closure that takes a struct** (`read_rows`'s `each:
  impl FnMut(RowView<'_>) -> T`). Before, it took four arguments (parser,
  bytes, offset, parsed row). Bundling them into `RowView` meant adding the
  edits changed every reader's signature once.
- **`let … else`** (`let Some(RowBytes { … }) = … else { return … }`). It
  binds the pattern if it matches, and otherwise runs the `else` block,
  which must leave the function. That keeps the "missing row" exits flat
  instead of nested `match`es.
- **A bit set in a `u8`** (`edit::Kinds`). Four flags, one per bit, with
  `insert` and `contains`. It is smaller and faster than a `Vec` of kinds
  for something checked on every mark query.
- **`pub` and `pub(crate)` modules** (`edit/command.rs` and
  `edit/overlay.rs`). The commands are the crate's public API; the overlay
  is visible only inside leal-core. `edit/mod.rs` re-exports each with the
  visibility it should have.
- **`#[expect(lint, reason = …)]`** (`append_rows`, FFI `set_cells`).
  Like `#[allow]`, it silences a lint, but it warns if the lint stops
  firing, so a stale exception doesn't linger, and it says why.
