# 2.1a Drive reconnect head check

A 1.9 follow-up, from the 2.1 notes ("Edits on rows of the first 64 KB
that turn out stale"). These notes supersede `docs/tasks/2.1.md`'s claim
that `edit_conflicts` named such a row: it compares hashes only once
`head_is_stale` (`changed_on_disk`) is set, which nothing set in this case.
That sentence in 2.1.md is corrected.

**The gap.** A drive can come back without the clone Leal made on it,
because the clone was deleted while the drive was away. `Removable::reconnect`
then falls back to the user's own file, if its inode, size and
modification time are unchanged. First paint had read the clone, so its
bytes weren't kept (`read` kept them only when it read the user's file).
The rest of the first 64 KB was then copied from the user's file with
only the `fstat` check. A same-size change with its modification time put
back got through that check. The grid then showed the copy's row while an
edit made from first paint's bytes sat against the old row.
`edit_conflicts` couldn't name it either, because `changed_on_disk` stayed
`false`.

## What changed

- **First paint's bytes are kept whatever they were read from**
  (`Removable::read`, `Reader::Head`): the `reads_the_original()`
  condition is gone. `check_against_head` already compares every copied
  chunk that overlaps them, so after a reconnect without the clone, a
  chunk of the first 64 KB that differs from first paint's bytes stops
  the copy with `ChangedOnDisk`. That is the same as when first paint
  read the user's file. Read from a clone, the chunks always agree, so for
  a clone that survives, the check costs one 64 KB comparison and changes
  nothing.
- **What the drive's file is, said explicitly** (2.1a review; the root
  cause predates this task, from 1.9). `External` used `folder.is_some()`
  to mean "this is the clone". But after a fallback, `folder` stays (so
  the clone is still cleaned up) while `path`, `id` and `file` are the
  user's file. `External::reads` (`Reads::Clone` or
  `Reads::Original(identity)`) now says which, and replaces the old
  `watched: Option<FileIdentity>`. Every place that asks "is this the
  clone?" uses it:
  - `drive_vanished` looks at the path only for a clone. Before, after a
    fallback, a renamed user's file plus an `EIO` counted as a vanished
    drive; now it is a read error, as for any user's file.
  - `reconnect` tries the clone only while it is what is read. After a
    fallback it stays with the user's file. Before, a second reconnect
    would have "reopened the clone" at the user's file's path.
  - `note_original_written`, `note_original_path`, `check`,
    `confirm_deletion` and the open-time length use `reads` too. Their
    behaviour is unchanged.
- **Test hook** `Source::simulate_clone_lost` (`Removable::simulate_clone_lost`),
  behind `cfg(any(test, feature = "test-hooks"))` and `#[doc(hidden)]`.
  It deletes Leal's clone by its folder's own path (never
  `External::path`, which is the user's file after a fallback), so
  `reconnect` falls back to the user's file. It returns whether there was
  a clone to delete. It is `pub` in leal-core (under the feature), so
  `check-no-test-exports`'s pattern now has `simulate_?(drive|share|clone)`.
  It is not exported through leal-ffi.
- Test-only (`cfg(test)`): `kept_head_len` (how many of first paint's
  bytes are kept) and `classify_eio_now` (what an `EIO` would be classed
  as now).
- Doc comments on `Removable::head`, `read_head`, `check_against_head`,
  `changed_on_disk`, `reconnect` and `Source::read_head` say what is kept,
  when, and why.

Nothing outside the source layer changed. The document already treats
`changed_on_disk` as "the first 64 KB aren't trusted" (`head_is_stale`),
so `edit_conflicts` names the edited row once the copy stops.

## Tests

In `source::tests::removable`:

- `a_drive_back_without_its_clone_checks_the_copy_against_first_paint`:
  open with a clone and read first paint. The drive goes, then the clone
  is lost and `XX` is written in place inside the first 64 KB with the
  modification time put back. Reconnect succeeds (the file looks
  unchanged), and the next pass stops with `ChangedOnDisk` at the changed
  chunk, without delivering it. Save is refused, nothing is mapped, and
  the kept bytes are let go. Three cases:
  - 4 KB chunks, the drive gone at 16 KB, the change at 40 KB;
  - 5,000-byte chunks, one of which (65,000–70,000) crosses the end of the
    64 KB, with the change at 65,100, in its part inside them;
  - the app's 1 MB chunks on a 2.5 MB file, the drive gone before the
    first chunk, so the one chunk holding all of the 64 KB is read from
    the user's file.
- `a_drive_back_with_its_clone_completes_the_copy`: the same, but the
  clone survives (and the user's file is changed without its time put
  back). The copy completes from the clone, with the bytes as opened.
- `first_paints_bytes_from_a_clone_are_let_go_once_copied`: the memory
  check (below).
- `losing_the_clone_again_leaves_the_users_file_alone`: after a fallback,
  the hook finds nothing more to delete (twice), the user's file is
  untouched, and the copy completes.
- `after_falling_back_a_renamed_file_and_an_eio_is_not_a_disconnection`:
  after a fallback, the user's file is renamed and an `EIO` is classed as
  `Other`, with the source still reading. While a clone is read, a clone
  gone from its path plus an `EIO` is still `Disconnected`.

In `document::tests::edits`:

- `a_drive_back_without_its_clone_catches_a_change_to_an_edited_head_row`:
  the drive goes at 16 KB. A row at about 40 KB is edited from first
  paint's bytes, and so is row 2, which the copy has. Then the clone is
  lost and that row's `café` becomes `CAFé` (same length, time put back).
  `check_original` reconnects (generation 1, edits kept). The index job
  ends with `ChangedOnDisk`, and `edit_conflicts` is exactly
  `[(row, 1)]`. Both edits are kept, and row 2 still shows its edit.

Without the head fix, the first four tests above and the document test
fail. The first and the document test fail because the pass completes
(`Ok(())`) and the index job ends `Ok`. The second and third fail on
`kept_head_len`, which is 0 for a clone. Without the review fix,
`losing_the_clone_again…` fails because the user's file is deleted, and
`after_falling_back…` fails because the `EIO` counts as a disconnection. I
checked both by putting the old code back for a run.

The document test doesn't start the file watcher. That matches a real
unplug, where the watcher's descriptor is revoked and, once the volume is
back, `look_again` compares only inode, size and modification time. A
watcher on the same volume would instead see the write (`NOTE_WRITE`),
mark the file diverged, and never reconnect.

No disk images were needed for the new tests: the simulated drive
(`open_simulating_fault`) clones on the scratch volume. The existing
disk-image tests in `just check` attach and detach their own images.

## Not covered

A same-size change, with its time put back, made while the drive is away
to bytes the copy **already has** (before the point where it stopped)
isn't caught. The copy keeps the old bytes there and reads the new ones
after, so it could mix two versions. That was so before this task, and
it is the same for a drive that can't clone. The first-paint check only
covers the first 64 KB that haven't been copied yet. Catching it would
mean reading the copied part of the user's file again on reconnect, so it
is left for the coordinator to ticket if wanted.

## Memory

The source now keeps first paint's bytes for a clone too. That is at most
`FIRST_PAINT_BYTES` (64 KB) per document, the same as a drive that can't
clone already kept. It is held only until the copy's chunks reach 64 KB
(the first chunk at the app's 1 MB, or the first 16 at 4 KB), or until a
mismatch. A drive that goes before the copy reaches 64 KB keeps the bytes
until it comes back, or until the document is closed.
`first_paints_bytes_from_a_clone_are_let_go_once_copied` checks this:
64 KB is kept while the copy is in the first 64 KB and nothing after,
and a 1,000-byte file keeps 1,000 bytes until its one chunk is copied.
The document's own `head` (also 64 KB) is unchanged. Nothing on a hot
path changed (one 64 KB `memcmp` per copy), so there is no benchmark.

## Deviations

None. No ADR: this arms the check DESIGN describes ("Changes during the
copy": the copy's first chunks are checked against first paint's bytes) in
the one branch where it wasn't armed. DESIGN and PLAN are unchanged.

## Rust notes

- **`Mutex<Option<Vec<u8>>>`** (`Removable::head`): the bytes can be there
  or not (`Option`), and the stream thread and first paint both reach
  them, so they sit behind a lock. `check_against_head` sets the `Option`
  to `None` to free the 64 KB. Dropping a `Vec` frees its memory at
  once, so there is no garbage collector to wait for.
- **An enum instead of a guess from another field** (`Reads`, in
  `removable.rs`). `enum Reads { Clone, Original(FileIdentity) }` holds
  the user's file's identity only in the variant that has one, so code
  can't read an identity for a clone. `#[derive(PartialEq)]` lets
  `reads_clone` compare with `==`. `match` must cover every variant, so
  adding a third kind of file later would make the compiler point at
  every place that has to decide about it.
- **`#[cfg(any(test, feature = "test-hooks"))]`** compiles the hook only
  into test builds and builds that turn on the `test-hooks` feature (the
  app's tests and the benchmarks). The shipped app never has it.
  `check-no-test-exports` looks for its name in the Release binary to
  prove that. `#[cfg(test)]` (`kept_head_len`, `classify_eio_now`) is
  narrower: only leal-core's own tests.
- **`let Some(External { folder: Some(folder), .. }) = … else { return
  false; }`** (`simulate_clone_lost`) is a `let … else`. It matches a
  pattern, here "there is an external file and it has a clone folder",
  and binds `folder`, or runs the `else` block, which must leave the
  function.
