# 1.3a Work scheduler

Opening a file now runs as DESIGN §3.10 asks: first paint (P0) on the
caller's thread, without waiting for anything, then the index (P1) on its
own thread and the review (P2) on a bounded background pool, which pause
while the user interacts. Every job has a handle with `cancel()`, and
every job, first paint and pause is an `os_signpost` interval.

### First paint (P0)

`Document::open(path, temp, volume, scheduler, options, progress)`:

1. `Source::open_on` (clone and map, or ordinary reads on a removable
   drive).
2. One `read_range(0..64 KB)`, kept in memory as the document's `head`.
3. `detect` on it, then `RowIndex::build` over those 64 KB alone. Every
   row but the last is whole (the last may be cut, or end in a CR whose LF
   is past 64 KB), unless the file fits.
4. Parse the first screen (`first_screen_rows`, each cell to `max_chars`).
5. End the "First paint" interval, then start P1 and P2, and return the
   `FirstScreen`: the detection, the rows, the rows known so far and an
   estimated row count (file size over the 64 KB's average row length).

Nothing in P0 waits for a job. The test
`first_paint_does_not_wait_for_the_index` holds the index thread at its
start through the platform hook, so if first paint waited, it would time
out.

### Background jobs

- **P1, the index**: a new thread per index job (`leal-index`), at
  user-initiated QoS. On a mapped file, `Indexer::run` over the slice. On a
  removable drive (`as_slice()` is `None`), `Source::stream` feeds a
  `ChunkedIndexer`: one pass both copies the file to the internal disk and
  indexes it (ADR-0006). Each chunk publishes rows and calls the progress
  callback. P1 never pauses.
- **P2, the review**: `review_with` on the background pool, with the job's
  checkpoint between its 128 KiB chunks. On a mapped file it runs
  alongside the index. On a removable drive it is queued behind the index
  (`spawn_after`), because it needs the whole file as a slice, which exists
  once the copy is mapped. If the drive vanished first, it ends with
  `JobError::Read(Disconnected)`.
- **P3**: no work yet. The scheduler has the priority, its queue and its
  rules; filter and sort acceleration (phase 3) spawn with `Priority::P3`.
- **Diagnostics (1.5)**: `SEAM(1.5)` comments mark both places: the
  index pass (`document::index_file`, which can hand an observer to
  `fill` or `ChunkedIndexer::push_observed`), and `start_checks`, for P2
  details. The index module's `RowObserver` hook is unchanged; the scanner
  still calls it once per row, with offsets in the file, from both the
  slice and the chunked path.

### The scheduler

- **Pools** (rule 4): P1 jobs get their own thread. P2 and P3 share a
  `rayon` pool of (performance cores − 1) threads (`leal-background-N`, at
  utility QoS). The app's platform reads `hw.perflevel0.physicalcpu`;
  without it (tests, CLI) the guess is half the cores, less one.
- **Order**: the scheduler keeps its own two queues. Each job queued asks
  the pool for a thread; whichever pool thread gets there first takes the
  first queued P2 job, or else a P3 job. P3 jobs never take the pool's
  last thread (at most n − 1 run at once), so a P2 job never waits for a
  P3 job to finish.
- **Yielding** (rule 3): `note_user_input()` (one event) and
  `set_interacting(bool)` (a gesture). At each `Job::checkpoint`, a P2 or
  P3 job waits on a condition variable while the user interacts and until
  input has been idle for 250 ms (`IDLE_AFTER_INPUT`). Each wait is a
  "Paused" interval.
- **Cancellation** (ADR-0005 decision 6): `JobHandle::cancel` sets the
  job's flag and wakes paused jobs. The work checks it at each checkpoint
  (or `Indexer::run` and `Source::stream` check `Job::cancel_flag()`
  between chunks). A job cancelled before it starts never runs.
  `cancel_stops_a_running_job_within_one_chunk` cancels during chunk 3 and
  shows no chunk 4 starts, for P1, P2 and P3.
- **Chunks of at most ~5 ms**: `JobControl::longest_chunk()` records the
  longest stretch of work between checkpoints, not counting pauses. On the
  reference file: index 2–3 ms, review 1.1 ms (see Benchmarks).
- **Panics** in a job are caught and become `JobError::Panicked`; the pool
  carries on.
- **`on_finish`** runs a callback when a job ends (at once if it already
  has). `spawn_after` and the FFI's async `wait` use it.

### Rows

`Document::rows(range, max_chars) -> Vec<Vec<Cell>>`, synchronous:

- Rows come from whichever index covers more of the file's first rows:
  the first 64 KB's, until the real index passes it.
- **One read per call**: `rows_extent` gives the range of the whole
  screenful. It is served from the kept 64 KB if it lies inside them,
  otherwise by one `Source::read_range` (a borrow of the map, or one
  `pread` on a removable drive before its copy is mapped). Rows are then
  parsed with the window variants and kept in a `RowCache`.
- Rows of the first 64 KB stay readable even if a removable drive vanishes
  before they were copied, which answers the open question in the 1.1a
  notes about first paint's rows.

`row_count()`, `estimated_row_count()` (the index's estimate once it has
more rows than the 64 KB, exact once complete) and `progress()`.

### Re-reading with other choices

`Document::reinterpret(choices, rows, max_chars)` runs first paint again
from the kept 64 KB with the user's delimiter, header or encoding, cancels
the old jobs and starts a new index and review. Nothing is reopened (PLAN
1.3). Each reading has a `generation`, carried by progress reports, so the
app can ignore a late report from the old one. A choice that doesn't fit
the BOM is refused and leaves the document as it was.

### Window variants (1.1a review)

For a file with no single slice yet:

- `RowIndex::row_in(row, window, base)`: `window` is the file's bytes
  from offset `base` on. `None` unless the window holds the row's extent.
- `RowParser::parse_in(window, base, span)`, and `_in` versions of
  `value_bytes`, `display_value` and `display_prefix`. Fields keep offsets
  in the file.
- The whole-file methods are now the `_in` methods with `base` 0, so
  there is one implementation.

### The chunked index

`Indexer::chunked(len)` gives a `ChunkedIndexer`: `push(chunk)` for each
chunk in order, then `finish()`. The scanner's state (inside quotes, the
row so far, field counts) carries over from chunk to chunk. Each chunk is
scanned up to its last unit, which may be the CR of a CRLF or the first
quote of `""`, and the bytes from one unit before the scanner's position
(for the "quote after a delimiter" look-back) to the end are carried into
the next chunk: at most a few bytes. A chunk is copied into a reused
buffer behind that carry, one memcpy per 1 MiB.

### FFI (for 1.6)

```swift
let scheduler = try Scheduler()                     // one per app
scheduler.noteUserInput()                           // on every scroll or edit event
scheduler.setInteracting(interacting: true/false)   // around a gesture
let document = try openDocument(path:volume:temp:scheduler:options:observer:)
document.firstScreen()                              // FirstScreen: interpretation, rows, counts
try document.rows(start:count:maxChars:)            // [[Cell]]
try document.rowCount() / estimatedRowCount() / progress() / storage() / interpretation()
document.isFailed()                                 // after a panic: every other call throws DocumentFailed
let job = document.indexJob()                       // or reviewJob()
job.cancel()                                        // from withTaskCancellationHandler (1.6)
try await job.wait()                                // throws JobFailure
document.review()                                   // ReviewResult? once the review is done
try document.reinterpret(options:)                  // FirstScreen
```

`ProgressObserver.indexProgressed(progress:)` is called on the index
thread after each 1 MiB chunk. `LealError` gains `TooLarge`,
`EncodingDoesNotFit`, `DriveDisconnected`, `ChangedOnDisk` and `Internal`,
worded in `OpenErrorText`.

**Signposts** go to subsystem `io.github.robhaswell.leal`, category
`PointsOfInterest`, so they show in the Points of Interest lane of any
Instruments template. I checked them with `log stream --signpost`: "First
paint", "Index" and "Review" intervals, begin and end paired by id, from
the leal-ffi tests.

## Decisions and deviations

- **Names of the window variants.** PLAN writes `RowIndex::row_in(window,
  base)` and `RowParser::parse(window, base, span)`. They are
  `row_in(row, window, base)` (it needs the row) and `parse_in(window,
  base, span)`, keeping `parse(bytes, span)` as it was, since every
  existing caller uses it. `rows_extent(rows)` is new: the one range to
  read for a screenful.
- **The review of a removable file waits for the copy**, rather than
  running alongside the index: it needs the whole file as one slice, which
  exists only once the copy is mapped. Streaming the review over the same
  chunks would mean a chunked review; on a mapped file it already runs
  alongside.
- **P3 is never lowered to background QoS during scrolling** (DESIGN
  §3.10's table). It pauses instead, which is stronger: it does no work at
  all while the user scrolls.
- **P3 jobs may use all but one pool thread.** DESIGN only orders P2
  before P3; without the limit, P3 jobs could fill the pool and a P2 job
  would wait for one to finish. So the pool always has at least two
  threads (see "Changes after review").
- **"Jumping past the indexed region moves the indexer to the front of the
  queue"** (rule 5): the indexer is always running on its own thread with
  nothing ahead of it, so there is nothing to reorder. Showing the target
  as soon as it is reached is 1.6's (it can watch `progress()`).
- **The first paint interval of `Document::from_source`** doesn't include
  opening the `Source` (the caller did that); `Document::open`'s does.
- **`open_document` is synchronous.** First paint is a few milliseconds,
  but on a removable drive it includes one `pread`, which a slow or
  failing drive could stretch. 1.6 decides which thread opens files
  (`NSDocument` can read on a background thread).
- **The app was touched** (`OpenErrorText.swift`, the String Catalog, a
  test file): its switch over `LealError` is exhaustive by design, so the
  new cases need wording to compile.
- **A `test-hooks` feature on leal-core** exposes
  `Source::open_simulating_removable` to the benchmarks, as the brief
  suggested ("the test override from 1.1a"). leal-ffi never turns it on.
  `just check` builds with `--all-features`, so it is compiled and linted.
- **Progress reports aren't throttled**: one per 1 MiB chunk, about a
  hundred over 50 ms for the reference file. The app should coalesce them
  on the main thread.
- **Row lengths that change through the file** make the first-paint
  estimate off: 8% for a test file whose numbers grow from 1 to 5 digits.
  The index's estimate replaces it as soon as it has more rows.

## Changes after review

The review approved the branch (lock order, wake-ups, nothing on the
first-paint path behind background work; its stress tests passed) with
three should-fixes, all done. The branch is rebased onto `main`.

- **Filtered benchmark runs** (`benches/open.rs`). Any filter that left
  out `open/` (the justfile's own `just bench baseline/`) panicked with "the
  P1 load didn't run", because the load started and was checked whatever
  ran. Now the load starts the first time a loaded benchmark's closure runs
  (criterion calls it only if the filter selects it), is checked only if it
  started, and the chunk report runs only if an `open/` benchmark ran.
  `just bench index/` and `open -- baseline/` exit 0; `open --
  open/first_paint_under_load` alone starts and checks the load.
- **A failed state after a panic** (DESIGN §3.9, `leal-ffi`).
  - `JobFailure::Panicked { message }`, instead of a `Failed` that 1.6
    would have had to tell apart by its message.
  - The FFI `Document` runs every export through `call`, which returns
    `LealError::DocumentFailed { path, message }` once the document has
    failed, without touching the core document, and catches a panic in the
    call itself (marking the document failed). A panic in one of the
    document's jobs fails it too: each job of the current reading is
    watched through `on_finish`. `is_failed()` says so. Every `Document`
    export but `is_failed` now throws, since any of them can meet a failed
    document.
  - Swift: `OpenErrorText` words `DocumentFailed`, and gains an exhaustive
    `describe(_: JobFailure)`; two new catalog strings.
  - Tests: Rust tests panic inside a call and inside a watched job (and
    check that normal and cancelled jobs don't fail the document). XCTests
    use two new `test-exports` hooks, `Document.debugPanic()` and
    `debugPanickingJob(scheduler:)` with `Document.debugWatch(job:)`, the
    pattern of `debug_panic`: the wait throws `JobFailure.Panicked`, the
    document is failed, and later calls throw `DocumentFailed`.
- **A pool of at least two threads** (`MIN_BACKGROUND_THREADS`). With
  `.max(1)`, a Mac with 2 performance cores (or the fallback with 4 or
  fewer cores) got a one-thread pool, where a P3 job took the only thread
  and P2 work waited for it. I chose a minimum of two over documenting the
  exception: pool threads run at utility QoS, below the main thread
  (user-interactive) and the indexer (user-initiated), so the kernel gives
  them only cores those two leave free (or efficiency cores), and they
  pause entirely while the user interacts. One more utility thread doesn't
  take a core from the main thread; a P3 job blocking P2 would delay the
  review for as long as it ran. The minimum applies to an explicit
  `background_threads` too. Tests that filled the single thread with one
  blocker now fill every thread (`Blockers`), the P2-before-P3 test now
  checks it by hand-shakes instead of a recorded order, and
  `the_smallest_pool_keeps_a_thread_for_p2` asks for one thread and shows
  a P2 job finishing while a P3 job holds a thread.

`just check-all` passes (460 Rust tests, 15 XCTests), and so do `just
app-test release`, `just test-deep` and `just bench`, including `just
bench index/`.

## Rust notes

- **Threads vs a pool** (`schedule/mod.rs`, `Scheduler::start`). A
  `std::thread` is an operating system thread: `thread::Builder::new()
  .name(…).spawn(closure)` starts one that runs the closure and ends. The
  index gets one per job, so it never waits behind anything. A **pool**
  (`rayon::ThreadPool`) is a fixed set of threads that run small tasks
  handed to them (`pool.spawn(task)`), so starting background work costs a
  queue push, not a thread. The pool size is the limit DESIGN asks for.
  The scheduler keeps its own priority queues and gives the pool a "run the
  next job" task for each job queued (`Shared::dispatch`).
- **Closures that move to another thread: `FnOnce + Send + 'static`**
  (`Scheduler::spawn`). The job's work is a closure. `FnOnce` means it is
  called once (so it may move what it captured, such as the `Indexer`).
  `Send` means it may move to another thread. `'static` means it borrows
  nothing from the caller's stack, which may be gone by the time it runs,
  so it captures `Arc`s and owned values (`move ||`) instead.
- **`Arc` and the lock types** (`Document`, `Shared`, `JobState`).
  `Arc<T>` shares one value between threads; it is freed when the last
  `Arc` goes. Shared values that change need a lock or an atomic:
  - `Mutex<T>`: one thread at a time (the job queues, a job's outcome, the
    row cache).
  - `RwLock<T>`: many readers or one writer. The document's current reading
    is `RwLock<Arc<Reading>>`: readers clone the `Arc` and let go of the
    lock at once (`Document::current`), and `reinterpret` swaps in a new
    one. A reader in the middle of `rows()` keeps the old reading alive
    through its own `Arc`.
  - Atomics: the cancel flag (`AtomicBool`, `Release` when set, `Acquire`
    when read), job ids and the longest chunk (`AtomicU64::fetch_max`).
  - `OnceLock<T>`: set once, then read without a lock: a job's result.
- **Condition variables for pause and resume** (`schedule/input.rs`). A
  `Condvar` lets a thread sleep until another thread says something
  changed, without polling. `wait_until_idle` holds the input lock, checks
  "may I run?", and if not calls `condvar.wait_timeout(guard, left)`,
  which releases the lock while it sleeps and takes it back when it wakes:
  on the timeout (idle long enough), or on `notify_all` from
  `set_interacting` or from a `cancel()`. It always re-checks in a loop,
  because wake-ups can be spurious. `cancel()` takes the same lock before
  notifying, so a job that has just checked its flag can't miss the
  wake-up and sleep through its cancel.
- **Channels** (the tests, `std::sync::mpsc`). A channel is a queue between
  threads: `send` on one end, `recv` (or `recv_timeout`) on the other. The
  tests use them to hand-shake with a job ("chunk 3 started", "go on"),
  so they don't depend on sleeping. The scheduler itself doesn't use
  channels: its jobs are pulled by priority from shared queues, which a
  channel (first in, first out) can't do.
- **Trait objects: `Arc<dyn Platform>`** (`SchedulerConfig::platform`). The
  scheduler doesn't know which platform it has: tests pass a recorder,
  leal-ffi passes `MacPlatform`. `dyn Platform` is "some type that
  implements `Platform`", called through a table of function pointers.
  The trait's methods have default bodies that do nothing, so
  `NoPlatform` is one line.
- **Catching panics** (`schedule/job.rs`, `run_job`).
  `panic::catch_unwind(AssertUnwindSafe(|| work(&job)))` runs the work and
  turns a panic into an `Err` instead of ending the thread. It insists on
  `AssertUnwindSafe` because data the closure was changing might be left
  half-done; that's fine here, because the only thing looked at afterwards
  is the outcome that says "it panicked".
- **`Cell` for one thread's state** (`Job::chunk_started`). `Cell<T>`
  allows changing a `Copy` value through a shared reference without a
  lock, which is only allowed because a `Cell` can't be shared between
  threads: `Job` is `Send` (it moves to the job's thread) but not `Sync`.
- **`PhantomData<U>`** (`scan::Scanner`). The scanner no longer holds the
  bytes, so no field has type `U`, but its methods are still specialised
  for bytes or UTF-16. `PhantomData<U>` is a zero-size field that says
  "this type is about `U`".
- **UniFFI async and `Future`** (`leal-ffi/src/document.rs`, `Finished`).
  An `async fn` returns a `Future`: a value something polls until it says
  `Poll::Ready(result)`. Each `poll` gets a `Waker`; returning
  `Poll::Pending` promises to call `waker.wake()` when it is worth polling
  again. UniFFI turns `Job::wait` into a Swift `async` function and polls
  the future from Swift's side. `Finished::poll` stores the newest waker,
  registers a callback with `JobControl::on_finish` (once), and checks the
  outcome; the callback wakes the task from the job's thread when it ends.
  So no Rust async runtime (such as tokio) is needed, and no thread is
  blocked while Swift awaits. The tests drive it with a 20-line
  `block_on`: poll, and `thread::park` until the waker unparks the thread.
- **Swift callbacks: `#[uniffi::export(with_foreign)]`**
  (`ProgressObserver`). A Rust trait that Swift implements: UniFFI
  generates a Swift protocol, and a Swift object arrives in Rust as
  `Arc<dyn ProgressObserver>`. The trait is `Send + Sync`, because Rust
  calls it from the index thread, so the Swift class must be thread-safe
  (the XCTest's uses a lock).
- **`unsafe` in `platform.rs`**:
  - `unsafe extern "C" { … }` declares C functions; calling one is unsafe
    because Rust can't check what it does with its arguments. Each call is
    one `unsafe` block with a `SAFETY` comment (pointers valid, sizes
    right, strings NUL-terminated and static).
  - `#[unsafe(link_section = "__TEXT,__oslogstring,cstring_literals")]`
    puts a static in a named section of the binary, where `os_log` looks
    for signpost names. The attribute is `unsafe(…)` because a wrong
    section could break the binary.
  - `&raw const __dso_handle` takes the address of the linker's symbol for
    the image's header without reading it, so it needs no `unsafe`.
- **Generic code reused for windows** (`scan::View`, `Units::at`). Rather
  than copy the scanner and parser for "a slice that starts part-way into
  the file", positions stay offsets in the file, and `View` translates them
  to the slice's offsets on each call (a subtraction). With a view of the
  whole file at offset 0 it is the old code, which the index benchmark
  confirms costs nothing.
- **Feature flags** (`leal-core/Cargo.toml`, `test-hooks`).
  `#[cfg(any(test, feature = "test-hooks"))]` compiles an item only for
  leal-core's own tests or when a crate asks for the feature, as leal-bench
  does in its `Cargo.toml`. The app's build never asks, so the hook isn't
  in it.
