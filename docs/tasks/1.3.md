# 1.3 Row index

## What was built

### `leal_core::index` (`crates/leal-core/src/index/`)

The quote-aware, progressive row index of DESIGN §3.3.

| File | What it holds |
|---|---|
| `mod.rs` | The public API: `RowIndex`, `Indexer`, `IndexDialect`, `CodeUnit`, `RowSpan`, `LineEnding`, `Status`, `Progress`, `IndexError`. The module docs give the rules, the seam with 1.2 and what isn't in this pass. |
| `scan.rs` | The scanner: the state machine, the `Units` trait (bytes and UTF-16), the field-count tally, and the `RowObserver` hook for 1.5. |
| `tests.rs` | 40 tests (7 of them property tests), plus 2 unit tests in `scan.rs` and 2 doctests. |

**Public API:**

```rust
let dialect = IndexDialect { delimiter: b',', quote: b'"', code_unit: CodeUnit::Byte, bom_len: 0 };

// On the calling thread (tests, the CLI):
let index = RowIndex::build(bytes, dialect)?;              // Result<RowIndex, IndexError>

// Progressively, as the app will (1.3a puts this on its own thread):
let (index, indexer) = RowIndex::start(dialect)?;          // (Arc<RowIndex>, Indexer)
indexer.run(bytes, &cancel_flag, |progress| { … })?;       // Err(Cancelled) if the flag was set

index.status()               // Status::{Indexing, Complete, Stopped}
index.row_count()            // rows indexed so far (all of them once Complete)
index.row(r, bytes)          // Option<RowSpan { span, line_ending }>: span excludes the line ending
index.row_extent(r)          // Option<Range<usize>>: includes the line ending; extents tile the file
index.field_count_mode()     // Option<usize>: the dominant field count (provisional while indexing)
index.unterminated_quote()   // Option<usize>: the opening quote's offset, once Complete
index.bytes_scanned()
index.estimated_row_count()  // for the scrollbar while indexing (DESIGN §3.10 rule 5)
index.dialect()
```

Constants: `CHUNK_BYTES` (1 MiB) and `MAX_FILE_BYTES` (`u32::MAX`).
Errors: `InvalidDialect` (delimiter and quote must be different ASCII
characters, neither CR nor LF), `BomPastEnd`, `TooLarge` (4 GiB or more),
`Cancelled`.

### How the scan works

One pass, two states. Outside a quoted field it asks
`memchr::memchr3` for the next quote, CR or LF, and counts the delimiters it
skipped over in one go. Inside a quoted field it asks `memchr::memchr` for
the next quote: nothing else matters there.

- **Which quotes open a field.** DESIGN §3.4 makes a quote special only as a
  field's first byte. So a quote found outside opens a field only if it is
  at the row's start or straight after a delimiter. That one-unit look-back
  is all the scanner needs. Once a quoted field closes, the next unit can't
  be a quote (that would have been `""`), so a delimiter before a quote
  really does mean a field starts there. Quotes in `a"b` and in the text
  after a closing quote (`"a"b"c"`, ADR-0003 decision 3) are therefore
  literal, which a plain "toggle on every quote" scanner gets wrong.
- **Line endings.** LF, CRLF and a lone CR each end a row outside quotes.
  The scanner looks one unit past a CR for its LF, and one past a quote for
  `""`, even across a chunk boundary.
- **Rows.** The index stores one `u32` per row: where the row starts. It
  stores one more offset at the end: the start of the row being scanned,
  or, once complete, the end of the file. So row `r` with its line ending is
  `starts[r]..starts[r + 1]`. That is 4 bytes per row: 4.0 MB for the
  reference file's 1,000,001 rows. The line ending isn't stored. `row(r,
  bytes)` reads it back from the last one or two units of the extent. That
  works because a row can't end in CR or LF any other way. The one
  exception is an unterminated quote, which the index records.
- **Dominant field count** (PLAN 1.3, ADR-0003 decision 4). It is counted in
  the same pass: one more than the delimiters outside quotes, for each
  non-blank row. The tally keeps counts in first-seen order, so ties go to
  the count seen first. It skips the hash map when a row has the same count
  as the one before, which is almost every row.
- **UTF-16.** The scanner is generic over a `Units` trait. For UTF-16,
  `memchr` still searches for the byte that holds an ASCII value (the first
  byte of a unit in little-endian, the second in big-endian). A hit counts
  only in that position, with 0 in the unit's other byte. So the 0x0A in
  U+0A22 or U+220A is skipped. Offsets stay byte offsets in the file
  (ADR-0003 decision 6). A final odd byte belongs to the last row.

### Progress and cancellation

- `RowIndex` holds its state behind a `RwLock`. Each chunk (`CHUNK_BYTES`
  of the file, rounded up to whole code units) publishes the rows it
  finished: one write lock to append the new offsets and update the count.
  Then the `Indexer` calls the progress callback and checks the cancel flag.
- Readers only see **finished** rows: a row is published once its end is
  known. So the row `row_count() - 1` always has a line ending while
  indexing.
- Chunk boundaries are fixed (every `CHUNK_BYTES` after the BOM). A chunk
  that ends one unit late, because of a CRLF or `""` across the boundary,
  doesn't move the later ones.
- **Cancellation** (ADR-0005 decision 6) is a `&AtomicBool` the caller owns.
  It is checked before each chunk, so a run stops within one chunk of the
  flag being set. The test sets it from the third progress callback and
  checks that no fourth chunk is scanned. 1.3a's job handle with `cancel()`
  wraps this flag.
- **`Status::Stopped`** is set when the `Indexer` is dropped without
  finishing: cancelled, failed, never run, or a panic on its thread. So an
  index can never stay `Indexing` forever with nobody filling it. The rows
  published before the stop stay readable.

### Seam with 1.2 (to be joined in 1.3a)

The index doesn't use 1.2's types. `IndexDialect` takes four plain values,
and the module docs say where each comes from:

| `IndexDialect` field | From 1.2's detection result |
|---|---|
| `delimiter` | the detected (or user-chosen) `Delimiter`'s byte |
| `quote` | `dialect::QUOTE` (`"`, DESIGN §3.2) |
| `code_unit` | `Utf16Le` / `Utf16Be` for the UTF-16 encodings, `Byte` for every other (all ASCII-compatible, ADR-0005 decision 5) |
| `bom_len` | the detected `Bom`'s length |

`index::LineEnding` duplicates 1.2's `dialect::LineEnding`. 1.3a should
delete this one and use 1.2's. Re-indexing with another delimiter or
encoding (PLAN 1.3) builds a new `RowIndex` over the same bytes, so nothing
is reopened. `reindexing_with_another_delimiter_changes_the_rows` shows that
the delimiter changes the rows as well as the field counts, because a quote
opens a field only after a delimiter.

The index takes `&[u8]`, not a `Source`, so ADR-0006 option C (reads rather
than one map) would only change who supplies the bytes.

### Hook for diagnostics (1.5)

`scan::RowObserver` (crate-private for now) is told about every row as it
ends: its number, span, line ending, next start and field count. Ragged
rows, blank lines and mixed line endings need exactly these facts. The two
places where the scanner learns about field-level quote facts are marked
`HOOK(1.5)` in `scan.rs`: the closing quote (text after a closing quote)
and the unterminated quote. The default observer, `NoObserver`, compiles
away. The tests already use an observer to read each row's field count.
Invalid encoding and NUL need a byte-level look at field contents, which
this pass doesn't do yet.

The whole-file encoding count (ADR-0003 decision 1) is **not** in this pass.
It runs later as P2 work (ADR-0005 decision 4, PLAN 1.3).

## Tests

All in `crates/leal-core/src/index/tests.rs`, written before the scanner.
Against a stub scanner that found no rows, 14 of the 22 tests nextest ran
before stopping failed. Expected answers come from the testkit.
The testkit's reference parser is never used directly (0.2 notes).

- **Generated files** (properties, 256 cases each, 20,000 in `test-deep`):
  clean and messy UTF-8 (`csv_file`), clean and messy UTF-16 LE/BE
  (`csv_file_utf16`), and messy files of both kinds with chunks of 1 to 15
  bytes, so chunk boundaries fall everywhere. For each file, every row's
  span and line ending, every row's field count, the dominant field count
  and the unterminated quote match the generator's `Layout`.
- **Any bytes** (`csv_bytes`, any of the four delimiters, chunks of 1 to
  31): the extents tile the file, every row but the last has a line ending,
  and the chunk size changes nothing.
- **Every corpus sidecar** (42 files): row count, every row's field count,
  the field-count mode, trailing newline, the dominant line ending and
  whether line endings are mixed. Also the offsets of the row-level
  diagnostics: blank lines and ragged rows (row starts), mixed line endings
  (where the line ending starts) and the unterminated quote (the opening
  quote, on the last row).
- **Hand-written cases:** empty and BOM-only files, the final line ending,
  blank lines anywhere, LF/CRLF/CR, quoted newlines, `""`, literal quotes
  in unquoted fields and after a closing quote, unterminated quotes
  (including a quote as the last byte), the BOM, field counts with quoted
  delimiters, mode tie-breaks, re-indexing with another delimiter, UTF-16
  characters whose other byte is `"`, `,`, CR or LF, a final odd UTF-16
  byte, and every chunk size from 1 byte to the whole file.
- **Progress and cancellation:** a callback after every chunk; rows visible
  chunk by chunk and only once finished; a reader on another thread sees
  the count only grow; cancel before the first chunk does nothing; cancel
  during a run stops within one chunk and leaves correct rows; a dropped or
  failed indexer leaves `Stopped`; the row count estimate; `RowIndex` is
  `Send + Sync`.
- **Errors:** an unusable delimiter or quote, a BOM past the end, and a
  4 GiB file. That one checks the length alone, since a test can't
  allocate 4 GiB.

I also checked that the tests catch real mistakes. With the "first byte of
a field" rule removed (every quote opens a field), 7 tests failed, including
all four messy-file properties. With UTF-16's other-byte check removed, 3
UTF-16 tests failed.

`just check` passes: 235 tests, 1 skipped. `just test-deep` passes in
about 40 s (the index's properties take about 22 s of that, in debug).

## Benchmark

`crates/leal-bench/benches/index.rs`, on the 1.2b reference file (100 MB,
1,000,001 rows, already in memory). `index/build` runs on the calling
thread. `index/run` goes through `RowIndex::start` and `Indexer::run`,
with a cancel flag and a progress callback (96 chunks). Both are budgeted
at 500 ms in `src/budgets.rs`, so CI fails if either goes over.

Same machine as the 1.2b baseline: `Mac17,8`, Apple M5 Pro. This is
**not** the reference machine (a base M1 Air, which is slower).

| Benchmark | Median | Throughput | vs `memchr3_scan` |
|---|---|---|---|
| `baseline/memchr3_scan` (1.2b, rerun today) | 29.9 ms | 3.12 GiB/s | 1.0× |
| `index/build` | **54.1 ms** | 1.72 GiB/s | 1.8× |
| `index/run` (progressive path) | 54.7 ms | 1.70 GiB/s | 1.8× |
| *`index/build` without counting delimiters (experiment, not committed)* | *32.8 ms* | — | *1.1×* |

- **Budget: 500 ms. Result: 54 ms**, 9× headroom on this Mac. The M1 Air
  should be about 2–3× slower, which still leaves plenty.
- The state machine itself runs within 10% of the `memchr3` floor. Of the
  extra 24 ms, 21 ms is counting delimiters for the field-count mode, which
  PLAN 1.3 puts in this pass. The count runs over short segments between
  quotes and newlines (about 28 bytes on average). If the M1 Air numbers
  are ever tight, that is the place to optimise (for example, by
  classifying 64 bytes at a time into bitmasks, as the 1.2b notes suggest).
- Publishing progress costs nothing measurable: `run` and `build` are
  within noise of each other.
- UTF-16 isn't benchmarked. It is read-only, rare, and takes the same path
  with one extra check per hit.

## Decisions and deviations

- **`IndexDialect` has four values, not two.** The brief listed the quote
  and the code unit. The scanner also needs the **delimiter**, because a
  quote opens a field only after a delimiter (and for the field counts).
  It also needs the **BOM length**, which says where row 0 starts. That is
  detection's job (for example, a user can reopen a file with a UTF-8 BOM
  as Windows-1252).
- **Line endings aren't stored.** `row(r, bytes)` reads them back from the
  bytes, so the index stays at the 4 bytes per row DESIGN §3.3 gives. The
  price is that `row` takes the bytes. If 1.5 would rather have them
  stored, it costs 1 byte per row.
- **Progress is shared state plus a callback**, not a channel. Readers ask
  the `RowIndex` for rows whenever they like. The callback just says "more
  rows are ready", which is what the FFI's progress callback (DESIGN §3.9)
  will forward. A channel would have needed a consumer to drain it.
- **Files of 4 GiB or more are refused** (`TooLarge`). There is no `u64`
  fallback, since DESIGN §1 puts them out of scope.
- **Lock hold time.** The indexer holds the write lock while it appends a
  chunk's offsets, which takes microseconds. But when the vector of offsets
  has to grow, appending copies it: at 1M rows that is a 4 MB copy, about
  0.3 ms. A reader on the main thread can wait that long, once per
  doubling. That is inside the "reads under 1 ms" rule (DESIGN §3.9). If
  it ever isn't, the fix is to store offsets in fixed-size blocks.
- **Added beyond PLAN:** `estimated_row_count` (DESIGN §3.10 rule 5 sizes
  the scrollbar from it, and the index is what knows the average row
  length) and a second budgeted benchmark, `index/run`, for the path the
  app uses.

## Changes after review

The review approved the branch. The reviewer compared the oracle with the
index on 40,000 generated UTF-8 and UTF-16 files and on edge cases at the
1 MiB chunk boundary, and found no differences. A stress test with 4
concurrent readers was clean. There were two should-fixes:

- **`row(r, bytes)` now checks the bytes' length.** It reads line endings
  from the bytes it is given. A wrong slice, such as first paint's 64 KB,
  used to give wrong spans silently. Bytes of a length other than the
  indexed file's now give `None`, which fits the `Option` the method
  already returns and doesn't panic in product code. A slice of the right
  length but different content can't be detected cheaply, and the doc
  comment says so. Test: `rows_need_the_bytes_that_were_indexed`, which
  also covers the check while indexing.
- **Re-indexing with another encoding is tested**, not only another
  delimiter (PLAN 1.3):
  - `reindexing_without_the_bom_changes_the_rows`: a UTF-8 file with a BOM,
    reopened as Windows-1252 (`bom_len` 0). The BOM bytes become text, so
    the quote after them is literal and the file has two rows instead of
    one.
  - `reindexing_with_another_code_unit_changes_the_rows`: the same UTF-16
    LE bytes read as UTF-16 LE, as bytes, and as UTF-16 BE give three
    different sets of rows.

## Open questions

- 1.5: is reading line endings back from the bytes enough for mixed line

## Rust notes

- **`memchr`** (`scan.rs`, `Bytes::find3` and `find1`).
  `memchr::memchr3(a, b, c, haystack)` returns the index of the first byte
  equal to any of the three, or `None`. It compares 16 or 32 bytes at a
  time with SIMD instructions, so it is much faster than a loop that looks
  at each byte. The scanner calls it again after each hit, with a smaller
  set of bytes when inside quotes.
- **Iterators that compile to SIMD.**
  `bytes[from..to].iter().filter(|&&b| b == value).count()` (`Bytes::count`)
  reads like "count the matching bytes". The compiler turns it into vector
  compares, with no per-byte branch. The `|&&b|` pattern unwraps two layers
  of reference: `iter()` yields `&u8`, and `filter` passes a reference to
  that. `as_chunks::<2>()` (`Utf16::count`) splits a slice into `[u8; 2]`
  pairs and also returns the odd byte left over.
- **Generics, traits and associated constants** (`trait Units`, `Scanner<'a,
  U>`). `Units` says what any "way of storing characters" must provide, and
  `const WIDTH: usize` is a constant each implementation chooses (1 or 2).
  `Scanner<U: Units>` is written once, but the compiler makes a separate,
  specialised copy for `Bytes` and for `Utf16` (*monomorphisation*). So the
  byte version has `WIDTH = 1` built in and pays nothing for UTF-16's
  checks. The `RowObserver` hook works the same way: with `NoObserver`, the
  call does nothing and the compiler removes it.
- **`AtomicBool` and `Ordering`** (`scan::run`). An atomic is a value that
  several threads can read and write at once without a lock and without a
  data race. `cancel.load(Ordering::Relaxed)` reads it. The `Ordering` says
  what *other* memory the read must also see as up to date. `Relaxed` means
  "only this value", which is enough here: the flag carries no data with
  it, and if the indexer sees the store one chunk late, it just stops one
  chunk later. The flag is passed as `&AtomicBool`, a shared reference. A
  shared reference is enough to change an atomic: this is *interior
  mutability*.
- **`Arc` and `RwLock`** (`RowIndex::start`, `RowIndex::read` and `write`).
  `Arc<RowIndex>` is a reference-counted pointer: cloning it gives another
  handle to the same index, and the index is freed when the last handle
  goes. Readers keep one, and the `Indexer` keeps another. `RwLock` lets
  many readers in at once, or one writer. `read()` returns a *guard*, and
  the lock is released when the guard goes out of scope, so you can't
  forget to unlock.
- **Poisoned locks** (`unwrap_or_else(PoisonError::into_inner)`). If a
  thread panics while holding a lock, Rust marks the lock *poisoned*, and
  later `read()` and `write()` calls return an error, in case the data was
  left half-changed. Here every change leaves the state consistent before
  anything that could panic, so we take the data anyway instead of
  unwrapping (which product code mustn't do).
- **Consuming `self` and `Drop`** (`Indexer`). `run(self, …)` takes the
  indexer by value, so it can only be run once; the compiler rejects a
  second call. `impl Drop for Indexer` runs whenever the indexer goes away,
  after `run` returns, on an early error, during a panic, or if it is never
  run. It marks an unfinished index `Stopped`.
- **Callbacks with `impl FnMut(Progress)`** (`Indexer::run`). The caller
  passes a closure. `FnMut` means it may change things it captured, such as
  the counter in the benchmark (`|_| chunks += 1`). `impl` means each
  caller's closure type gets its own compiled copy, so the call is direct
  and can be inlined. The alternative, a channel (`std::sync::mpsc`), would
  send each `Progress` to a receiver on another thread. That suits a
  consumer that waits for messages. Here the reader asks the shared index
  whenever it likes, so a callback is simpler.
- **`let … else`** (`Scanner::scan`). `let Some(q) = … else { …; break; };`
  binds `q` if the value is `Some`, and otherwise runs the `else` block,
  which must leave the loop or function. It keeps the main path unindented.
- **Lossless and checked casts** (`to_u32`, `to_usize` in `mod.rs`). The
  workspace lints reject a silent `as` that could cut off bits, because a
  truncated offset would point at the wrong row. Offsets go into the index
  through `u32::try_from`, after `check_len` has made sure every offset
  fits. They come out with `as usize`, which can't lose anything on a
  64-bit Mac.
