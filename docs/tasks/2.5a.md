# 2.5a App: insert and delete rows and columns

Status: built, reviewed, review findings fixed. The core's structural
edits (tasks 2.4a–c) and their FFI were already there, and undo, redo,
the journal and recovery of them came with 2.5.2. This task is the app's
commands, their enabling, the selection, Find, and tests; the only Rust
change is making the column questions cheap (below).

## What was built

**Edit menu** (after Go to Row…, two groups behind separators; no other
UI, ADR-0002):

| Item | Key | Acts on |
|---|---|---|
| Insert Row Above | — | above the active cell's row |
| Insert Row Below | ⌘↩ | below it (after the last row: appends) |
| Delete Row / Delete Rows | ⌘⌫ | every row of the selection |
| Insert Column Before | — | before the active cell's column |
| Insert Column After | — | after it |
| Delete Column / Delete Columns | — | every column of the selection, one undo step |

- `app/Sources/Window/StructureCommands.swift`: the actions, validation
  (`availability`), the selection afterwards (`selectChange`) and the words
  (`StructureText`). `MainMenu.structureItems()` builds the items.
- `app/Sources/Document/DocumentStructure.swift`: the model's calls into
  the core (`insertRow`, `deleteRows`, `insertColumn`, `deleteColumn`, and
  the `…Refusal` questions), with grid rows turned into logical rows. Each
  command goes to `commandApplied`, the one place undo, the journal and
  the window hear of a command (2.5.2).
- A new row has as many empty cells as most rows (the core's column
  count), so it isn't a short (hatched) row. A new column's cells are
  empty, its header title too.
- **Header row**: grid rows exclude it, so Insert Row Above on the first
  data row inserts at logical row 1 and the header stays; Delete Row can't
  reach it (it can't be selected). Deleting every data row leaves the
  header; Insert Row Below then adds row 1.
- **Several columns** are deleted last-first, each a core command, inside
  one undo group named "Delete Columns" (named before the group closes:
  `NSUndoManager` raises if `setActionName` is called with no group open),
  in the document's history's undo manager (`undoHistory`, so it works
  with no window). The last column is asked about before the group opens:
  an empty group is a nameless Undo and clears Redo. Undoing it, Redo is
  "Redo Delete Columns": `DocumentUndoManager` gives the steps registered
  during an undo or redo the step's own name.
- **⌘↩ chosen as "below"**: DESIGN §4.2 says only "Insert row". Below is
  the "add a record" flow (it can append; above can't). Above has no
  shortcut (none is in DESIGN).

**Enabling, with the reason** (as the menu item's tooltip, the way Treat
As gives its reason; ⌘↩/⌘⌫ that reach the grid beep and VoiceOver hears
it):

| Core refusal | When | Tooltip |
|---|---|---|
| `StillReading` | index not complete and trusted, or a drive's/share's copy not done (ADR-0014 d1) | "Rows and columns can be inserted and deleted once Leal has read the whole file." |
| `Saving` | a save runs (ADR-0014 d1) | "Wait for the save to finish." (2.5.3a's) |
| `AfterUnterminatedQuote` | a row or column after the open quote (ADR-0004 d8) | "A quote in the last row is never closed, so a row (column) inserted after it would be part of its text." |
| `NoSuchColumn` etc. | nothing there | off, no tooltip |

The core answers each (`can_insert_rows`, `can_change_rows`,
`can_insert_column`, `can_delete_column`); the app adds only: off once the
document failed or while a Reload replaces it, and off while a text field
other than the two editors has the focus (below).

**Cost of asking** (review finding): the column questions ran the whole
column plan, a walk over every row's field count, and the menu asks three
times per opening. Now the longest row is found once per version of the
edits (cached in the reading, keyed by the edits' version and a `Weak`
pointer to the overlay), and only the open quote's row, if any, is laid
out with the column, so the quote's tooltip stays exact.
`asking_first_agrees_with_the_commands` checks the answers against the
commands at every column. On the 100 MB reference file (`just bench
column_edits/can_`, M-series Mac):

| `column_edits/…` | before | after |
|---|---|---|
| `can_insert_column` (no edits) | 3.06 ms | 31 ns (asked again) |
| `can_insert_column_100k_edits` | 6.63 ms | 31 ns |
| `can_delete_column_100k_edits` | 6.33 ms | 27 ns |
| `can_insert_column_after_edit` (first ask) | — | 1.89 ms |
| `…_after_edit_100k_edits` | — | 4.74 ms |

A menu opening cost 9–20 ms; now one walk after an edit, then nothing.

**Keys and text fields.** A menu key equivalent wins over a text view's
own key (the window asks views' `performKeyEquivalent` first, then the
menu), so without care ⌘⌫ would delete a row while typing:
- In the in-cell editor and the inspector (`LiteralTextView`), ⌘⌫ is
  claimed in `performKeyEquivalent` and does what the text system binds it
  to (delete to the start of the line). ⌘↩ goes on: the inspector already
  takes it as commit; in the in-cell editor the menu commits the edit,
  then inserts. Menu clicks work while editing (they commit first).
- In any other text field (the find bar; Go to Row's sheet, checked
  through the key window, `keyWindow`, which tests stand in for) the
  items are off, so the keys stay the field's: a disabled item's key
  equivalent isn't consumed.
- In the grid, ⌘↩/⌘⌫ reach `keyDown` only when the item is off (or for
  ⌘ with the keypad's Enter, which isn't the item's key): `GridView`
  hands them to `rowCommandKey`, which runs the command if it can, else
  beeps and announces why. They never open the editor (Return's). In the
  in-cell editor ⌘-keypad-Enter commits, then inserts, as ⌘↩ does.
- A held ⌘⌫ deletes once: key repeats are ignored (grid and menu).

**After a change** (`DocumentChange.structure` now carries a
`StructureChange`: column or first row, inserted or deleted, as applied,
so undo is the other way round):
- the grid, strips, gutter, headers and widths are redrawn (as 2.5.2);
- the selection goes where the change was: the inserted row's or column's
  cell, or the one that took a deleted one's place (clamped to the last),
  keeping the other coordinate, and is scrolled into view — for undo and
  redo too;
- **Find**: after a column's change `FindModel.structureChanged` searches
  again (`searchAgain`, a new core search, without moving the selection);
  after rows' it keeps the search, which catches up keyed by row id (as
  for cell edits), dropping every highlight tile since rows moved
  (ADR-0014 d2), and a waiting Next. 2.5.2 had restarted Find after any
  structural undo;
- **Header titles**: rows undone or redone at logical row 0 with the
  header row on (deleted before it was turned on) read the titles again;
- the inspector reads the active cell again.

hosted; no real sheet: `showSheet` stubbed to fail the test if reached):
the menu's items and keys; rows above/below/at the end with undo, redo,

Find catching up after a row undo and redo; header titles after a row
undo/redo at the header row; Delete Columns refused (asked first, or by
the command) leaving no step and Redo intact, and one step with no

**Undo after a save**: `testUndoAndRedoAfterASaveWriteTheBytesBack`
deletes a row (and, separately, two columns), saves, undoes, saves (the
file's own bytes), redoes, saves (the delete's bytes again).

**Byte fidelity**: `testSavingChangesOnlyTheRowsAndColumnsTouched` saves
after each command on a CRLF file with a quoted field and compares the
exact bytes (an inserted row `9,,\r\n`; `"Ostrava"` keeping its quotes);
`testSavingKeepsOddBytesInRowsLeftAlone` with an escaped quote, spaces
and a lone CRLF among LFs.

## Manual checks for Rob (on screen)

1. In a CSV with a header, click a cell, ⌘↩: an empty row below, selected;
   type, Return; ⌘Z twice takes the value, then the row ("Undo Insert Row").
2. Shift-click three rows: Edit shows "Delete Rows"; ⌘⌫ deletes them, ⌘Z
   puts them back (the title loses "— Edited").
3. Editing a cell, ⌘⌫ deletes the text before the cursor, no row; ⌘↩
   commits and inserts a row below.
4. In the find bar ⌘⌫ clears the text, no row goes. Find something, delete
   a row with a match: the count drops without restarting; Insert Column
   After: it recounts.
5. Delete Column on two selected columns, ⌘Z: both back in one step; the
   Edit menu then says "Redo Delete Columns". Header titles follow.
6. A file of a few hundred MB: while Indexing…, the six items are off with
   a tooltip; during a large save too ("Wait for the save to finish.").
7. `a,b\n1,"open\n` (unclosed quote), last row selected: Insert Row Below
   and Insert Column After are off with the quote tooltip; Above works.
8. Save after a row insert and a column delete: in a text editor, only
   those rows/columns differ.
9. With VoiceOver, ⌘↩ while the file is still read: a beep and the reason.

## Rust notes

The one change, `crates/leal-core/src/document/columns.rs`
(`can_change_column`, `Widest`): the reading keeps the longest row in a
`Mutex<Option<Widest>>` (a lock, as the app may ask from more than one
thread). `Widest` holds a `Weak<Overlay>`: a pointer that doesn't keep
the edits alive; `Weak::ptr_eq` tells whether the edits are still the
ones it was worked out for, and since a `Weak` keeps its allocation
reserved, a later version can never reuse that address. The app uses
what 2.4 built:
- `StructuralEdit` (`crates/leal-ffi/src/document/editing.rs`) is a
  `uniffi::Object`: Swift holds a reference to a Rust value it can only
  ask (`inserts()`, `firstRow()`), shared through an `Arc`, so the undo
  history and the journal keep the same command without copying it.
- The `can_…` methods return `Result<Option<EditRefusal>, LealError>`:
  the outer `Result` is "did the call work", the inner `Option` is
  "`None` = allowed, `Some(reason)` = refused". Swift sees it as a
  throwing function returning `EditRefusal?`, which is why
  `DocumentStructure.swift` handles an `EditRefusal??` (a failed call
  counts as refused).
